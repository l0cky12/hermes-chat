# Repository Git runs a fixed helper over the owner's own ssh, with structured requests

The Repository screen (#66) reviews, and later stages and commits, pushes and opens pull requests for, a Git checkout on the Hermes server. Every Git operation runs on the server, in the folder the screen shows, never in a checkout on this computer. It goes through the owner's own `ssh`, as the Terminal does (ADR 0022). ssh runs one constant remote command: `python3 -I -c` with a helper program built into the app (`src-tauri/src/repo_git_helper.py`, and since ADR 0043 `repo_worktree_helper.py`), zlib-compressed and base64-encoded so the command stays under Linux's 128 KiB limit for one argument. The request travels on ssh's stdin as one JSON object. The helper builds `git` (and, for pull requests, `gh`) argument lists itself and runs them without a shell. The answer comes back as one JSON object on stdout.

So nothing the owner types, and nothing in a file name, a commit message or a pull request body, is ever read by a shell on either machine. The webview can ask only for the operations Rust's `repo_git::Request` names. There's no "run this command" request.

## Why not the dashboard's own Git routes

Hermes at `f0d9488` (deployed, read over SSH on 2026-11-03) has Git routes for the official desktop app's review pane: `hermes_cli/web_routers/git.py` over `hermes_cli/web_git.py`. They cover status, per-file diffs, stage and unstage of a whole file, commit, push, `gh pr create` and a PR list. They're the obvious contract, but they can't meet this feature's requirements:

- **Hooks are bypassed.** Every call runs with `noninteractive_git_env()` (`hermes_cli/_subprocess_compat.py`), which pins `core.hooksPath=/dev/null` and sets `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` to `/dev/null`. A commit through `POST /api/git/review/commit` never runs `pre-commit` or `commit-msg`. The issue says hooks must never be bypassed implicitly.
- **The server's credentials aren't used.** The same environment blanks `credential.helper` and the global config. On this server, HTTPS pushes authenticate through `gh auth git-credential`, configured in `~/.gitconfig`, so `POST /api/git/review/push` can't push. The issue says to use the existing server-side credentials.
- **A commit can include files the owner didn't pick.** `review_commit` runs `git add -A` when nothing is staged, and nothing checks that the index is still the one reviewed.
- **Pull requests can't be edited.** `review_create_pr` runs `gh pr create --fill`, with no title, body or base, and pushes first, swallowing a failed push.
- **No hunks, no context, no old paths.** Diffs are fixed at three lines of context. There's no partial staging. Status drops a rename's old path, so a staged rename lists only its new path, and the deletion it carries isn't listed.
- `review/stage` passes the file to `git add` as a pathspec, so a file called `*.ts` would stage every TypeScript file. With no file at all, it stages everything.

The Repository screen uses none of these routes. A Hermes that changed them to run with hooks and the owner's config, took literal paths, refused `add -A`, and took expected HEAD and index values, would be a better contract than ssh. That is the backend design this decision records as missing:

- `POST /api/git/review/commit {path, message, expectHead, expectIndex}` runs `git commit -F -` with the owner's config and hooks. It refuses (409) when HEAD or the index changed or nothing is staged, and returns the hook output and the new commit.
- `POST /api/git/review/stage|unstage {path, files[], expectIndex}` takes literal paths.
- A `POST /api/git/review/apply {path, patch, reverse, expectIndex}` route stages hunks.
- `POST /api/git/review/create-pr {path, base, head, title, body}` never pushes.

## Considered options

- **The dashboard Git routes.** Rejected, as above.
- **Hermes's terminal tool, in a chat.** Rejected, as for the Terminal (ADR 0022): it runs as the agent, through Approvals, in a chat's history.
- **ssh with a quoted command line per operation** (`ssh host git -C '<path>' add -- '<file>'`). ssh hands its command line to the remote login shell, so every value would depend on quoting being right for whatever shell the owner has. Rejected for the constant command plus JSON on stdin.
- **A Rust SSH library.** Rejected, as for the tunnel: the system `ssh` brings the owner's config, agent, keys and known hosts.
- **Run Git on this computer.** Never: the repository is the server's.

## Consequences

- **What it needs on the server:** OpenSSH that the sign-in's key can reach without a prompt, `python3` 3.8 or newer, and `git` 2.31 or newer (porcelain v2 status with branch headers, `restore --staged`, `rev-parse --path-format`), all on the PATH a non-interactive ssh gets. Pull requests need `gh` signed in there, and a GitHub remote. A server without `python3` reports `unsupported` and says so.
- **Target.** By default the screen uses the Terminal's target, else the sign-in's SSH target. For a URL sign-in, which has neither, the owner types one, and it's kept on this computer (`hermes-chat.repo-target`). The screen trusts the owner that the target is the Hermes server.
- **No prompts.** ssh runs with `BatchMode=yes`, `-T` and `ClearAllForwardings=yes`. A key with a passphrase needs the agent. An unknown host key fails as `ssh-host-key`, and the screen says to accept it once in the Terminal. Host key checking is left to the owner's config, unlike the tunnel's `accept-new`.
- **It works while Hermes is away.** The screen needs ssh, not the dashboard connection.
- **It is the SSH user's Git.** The SSH user's `~/.gitconfig`, hooks and credential helpers apply, exactly as when the owner runs `git` over ssh by hand. The dashboard's `HERMES_DASHBOARD_FILES_ROOT` lock and credential denylist (ADR 0012) don't apply, as they don't to the Terminal. It can do nothing the owner's own `ssh` can't.
- **Reading changes nothing.** Status and diffs run with `GIT_OPTIONAL_LOCKS=0`, so a read doesn't refresh the index under an agent working in the same checkout. Every path goes to Git with `--literal-pathspecs`, so `*.ts` names one file. A path must be inside the checkout: no absolute path, no `..`, and no folder on the way that links out of it. Settings that would change how a diff reads or a patch applies (`diff.noprefix`, `diff.mnemonicPrefix`, `diff.srcPrefix`, `diff.dstPrefix`, `diff.relative`, `diff.external`, `apply.whitespace`, colour, path quoting) are pinned for every call. The owner's hooks, identity and credentials aren't.
- **Stage 1 (read-only).** The screen shows the top folder of the checkout that holds the folder typed, the branch or detached HEAD, its upstream with ahead and behind as of the last fetch, and any merge, rebase, cherry-pick, revert or bisect in progress. Files are listed as Conflicts, Staged, Changed (not staged) and Untracked, with a staged rename's old path, line counts, and binary and submodule marks. A file's diff is asked for one side at a time (staged, unstaged, untracked as all added, or a conflict's combined diff with the index stages Git holds), with 0, 3, 10 or 25 lines of context, or the whole file. Notices cover binary files, renames, copies, new and deleted files, mode changes, submodules, conflicts, and diffs over 2 MiB, which are cut. Up to 5,000 files are listed; more are counted as cut.
- **Stage 2 (staging and committing).** Every write names the HEAD and index it was made for. It holds the index's own lock (`index.lock`, as Git takes for any change to the index) from its checks until it's done, so no other Git process can change the index in between. Another agent's `git add` meanwhile fails as it would against any running Git command. The write goes to a copy of the index (`GIT_INDEX_FILE`), installed only if it worked. The lock is released however the helper ends; a dropped ssh's hangup is turned into a normal exit. The helper checks them first and refuses with `stale`, changing nothing, when either moved. The index stamp is the SHA-256 of `git ls-files --stage -z`. Status reads these stamps before and after listing, and lists again if they moved, so they belong to exactly the list shown.
  - **Files** are staged only as they were listed: each carries the SHA-256 of its executable bit and working-tree bytes (or none, for a deletion, which then must still be gone), and a file that changed since, a `chmod` included, is refused. What's staged is the bytes and executable bit that matched the stamp, written with `git hash-object` (through the file's clean filters, as `git add` would) and `git update-index --cacheinfo`. It isn't whatever the file holds a moment later. Files over 32 MiB are stamped by size, modification time, inode and mode instead of hashed, and checked again after they're read. Folders and submodules are never staged here. Paths are literal; there is no "stage everything". Unstaging is `git restore --staged`, or, before the first commit, `git update-index --force-remove` (which, unlike `git rm --cached`, doesn't refuse a file staged and then edited again), and never touches the working tree. A rename is unstaged with its old path.
  - **Hunks** can be staged and unstaged one at a time for a text change to a file that exists on both sides, shown whole and byte for byte. The screen names the hunk by its position. The helper reads that diff again, refuses if its bytes changed, cuts the hunk from it itself (no patch text comes from the webview), and applies it with `git apply --cached --recount` (`--reverse` to unstage, `--unidiff-zero` for a diff with no context). New, deleted, renamed, binary and mode-changed files, submodules, conflicts, and cut or lossy diffs go whole.
  - **Submodules can't be hidden.** Status, each file's diff, the preview, `rawSha` and the read-back all run with `--ignore-submodules=none`, which overrides `diff.ignoreSubmodules` and each submodule's own `ignore` setting. Otherwise a staged gitlink could be left out of the preview while Git still committed it.
  - **The commit preview** is the helper's `preview`: every staged file (renames paired), the whole staged diff (cut at 2 MiB, with the file list still complete), the message exactly as it will be committed, the branch, the HEAD it goes on top of, the author Git will use, and the commit hooks that will run.
  - **Commit** sends the preview's HEAD, index stamp, the ref HEAD pointed at (`headRef`: `refs/heads/<branch>`, or `HEAD` when detached), and the SHA-256 of `git diff --cached --raw --no-abbrev` as `rawSha`. The helper refuses if any of them changed (two branches can share a commit, so a switch to another branch at the same commit is refused too, rather than committing there), if nothing is staged, if there are conflicts, or while a merge, rebase, cherry-pick or revert is in progress, since committing would finish part of it. It then runs `git commit --cleanup=verbatim -F -` with the message on stdin. It never runs `-a`, `add -A`, `--no-verify` or `--allow-empty`. Hooks run as Git runs them, on the index copy, with the SSH user's config, and get ten minutes. A hook's `git add` goes into the commit, and the copy it left becomes the index. A refused commit drops the copy, so the index is as it was. A commit that landed and was then cut off (a timeout, or a hangup during a slow post-commit hook) still installs the copy, so the index never disagrees with the new commit. The index lock is held for the whole commit. What Git and the hooks print is captured as one stream and shown, after a commit or a refusal.
  - **Reading back.** After a commit, the helper checks that the new commit's only parent is the HEAD that was checked, and compares the commit's own `diff-tree --raw` with the preview's. If a hook changed what was committed (a formatter that runs `git add`, say), the screen says so and lists what the commit holds.
  - **Failures** are told apart: `hook` (from Git's own trace, `GIT_TRACE2_EVENT`: a hook it ran exited non-zero), `operation`, `identity`, `locked` (index.lock), `conflict`, `nothing-staged`, `empty-message`, `stale`, `lost` (a commit landed on another parent), and the transport's own. A commit whose answer is lost (timeout or ssh failure) reads HEAD again and says whether a commit was made. It's never retried on its own.
  - **The check-then-commit gap** is inside one helper process: microseconds between checking the stamps and Git taking `index.lock`. A write in that gap is caught afterwards by the read-back: the parent check and the `rawSha` comparison.
  - **Suggested messages** come from Hermes's legacy `llm.oneshot`, as Ask Hermes to edit does (ADR 0029), only when the owner asks. It is sent the recent subjects, the staged file list and the staged diff (cut at 60,000 characters), and runs on the profile's Text generation model. The answer fills the message box, where it can be edited like anything typed, but only if the box hasn't changed since it was asked for. It needs Hermes connected; nothing else in the screen does.
- **Stage 3 (push, pull requests, status).** Push and Create PR are separate actions, and each shows where it goes first.
  - **Where.** The helper's `publishInfo` gives the branch, its upstream (`branch.<b>.remote` and `.merge`), every remote with its push URL, and the commits a push would send. A user name or password in an `http(s)` URL is taken out before anything leaves the helper. A push goes where Git's own `simple` push would. The remote is the branch's `pushRemote`, else `remote.pushDefault`, else the upstream's remote, else `origin`, else the only remote. The remote branch is the upstream's only when it has this branch's name on that remote; otherwise it's the same name. A branch made with `git switch -c fix origin/main` tracks `main`, but its push goes to `fix`, never to `main`, and the screen shows the upstream apart. Ahead and behind come from the tracking ref, so they're as of the last fetch: the screen never fetches. A remote that pushes somewhere other than it fetches from is different, since its tracking ref says nothing about where pushes go. Then the push URL is asked (`git ls-remote`) what it has. If the answer isn't a commit known here, how far ahead the branch is isn't claimed, and Push stays offered. `publishInfo` also says whether the push destination has a branch of that name at all (`remoteBranchExists`: the tracking ref, or the push URL's answer). A new branch made at a commit the remote already has under another name is ahead by 0, but it isn't "nothing to push": Push stays offered and creates the branch, which a pull request needs.
  - **Push** sends the exact commit shown, `git push --porcelain <remote> <sha>:refs/heads/<branch>`, only if that branch is still checked out at that commit. It never uses `--force`, `+` or `--no-verify`, so a pre-push hook runs. It always passes `--no-follow-tags` and `--recurse-submodules=no`, so `push.followTags` can't send tags the confirmation didn't show, and `push.recurseSubmodules` can neither push submodules too nor (`only`) push them instead of the branch. The confirmation's push URL (without credentials) goes with the request, and a remote that now pushes somewhere else (`git remote set-url` meanwhile) is refused as `stale`. Branch and remote names are checked (`check-ref-format`, an existing remote not starting with `-`, even one configured that way), so none can be read as an option. A remote whose push goes to more than one URL (`remote.<name>.pushurl` several times) isn't pushed to from here. The screen lists its URLs and says so. A branch with no upstream gets `branch.<b>.remote` and `.merge` after a successful push. Then the remote is asked what it has, with `git ls-remote` against its push URL (which may differ from where it fetches), and the screen says whether that matches. If that check fails, the push is still reported as done, with the check's failure beside it. Credentials in URLs are taken out of Git's output before it's shown. It uses the SSH user's own credentials: on this server, the `gh auth git-credential` helper in `~/.gitconfig`.
  - **Push failures** are told apart. A hook's refusal is known from Git's trace. The others are read only from Git's and the remote's own lines (`fatal:`, `error:`, `remote:`, the porcelain ref lines), never from whatever a hook printed: `rejected` (the remote has commits this branch doesn't; nothing is forced, and the screen says to bring them in first), `remote-rejected` (a protected branch or a server-side hook), `auth`, `network`, and `hook` (pre-push). A push whose answer is lost isn't retried. The screen asks the remote itself (the helper's `remoteHead`, an `ls-remote`) whether it now has the commit, and says which.
  - **Create PR** runs `gh pr create --repo <owner/repo> --base <base> --head <branch> --title <title> --body-file -`, with the title, description, base and draft flag written in the screen, and the description on stdin. The repository comes from the remote's GitHub URL as written in the config, so gh never guesses it from other remotes. The form sends the repository it showed, and a remote that now names another is refused as `stale`. It never pushes. It first checks that the local branch the form was written for is still checked out at the commit shown, and refuses with `stale` if another process committed or switched branches since. Then it asks the remote (`git ls-remote`) whether it has the branch at that commit, and refuses with `not-pushed` if not. An open pull request for the branch is shown instead of making a second one. Only pull requests from this repository's own branch count: a fork's branch with the same name (`isCrossRepository`) doesn't. After creating, it reads the new pull request back with `gh pr view`. If that read fails or times out, the screen shows the new pull request's link and the error, and offers no second Create; Refresh finds it in GitHub's list. Its failures are `bad-base` (GitHub has no such branch: GitHub lists that among other reasons, so it's matched first), `no-commits`, `auth`, and `pr-api` with gh's own words. A failure after a successful push never pushes again, because only Push pushes.
  - **Status** is `gh pr view <n> --json …,statusCheckRollup` when the card opens and on Refresh status: state, draft, base and head, head commit, review decision, mergeability, and each check (runs and commit statuses) with its link. It never polls.
  - **gh failing doesn't hide Push.** In `publishInfo`, gh missing, signed out, or slower than its 60 s limit is reported in the pull request card. The branch, remote and commits still come back, so Push works with Git's own credentials.
  - **Pull requests are GitHub only,** through `gh` on the server. Another host's remote can be pushed to, and the screen says pull requests need a GitHub remote.
  - **Dropped connections.** sshd drops connections during key exchange when too many start at once (its MaxStartups). Before signing in, nothing has run. Rust tries a read once more after such a drop, half a second later. A write is never tried again.
- **Errors are told apart** by kind: ssh's `ssh-auth`, `ssh-host-key`, `ssh-unreachable` and `ssh`; `unsupported`, `timeout` and `bad-reply` from the server; and `bad-path`, `not-found`, `not-repo`, `stale`, `busy`, `git` and `internal` from the repository. Each shows ssh's or Git's own words beside a hint.
- **A late answer can't replace the current one.** Each status and diff read is numbered. An answer for an earlier folder, target or file is dropped. A write that finishes after another folder or target was opened changes nothing there: not its list, not its ticks. A suggested message is asked under the connection and profile shown (the app's project scope). If either changes before the preview comes back, Hermes isn't asked. If it changes before Hermes answers, the answer, or the failure, is dropped.
- **Stored on this computer:** the folder opened last and the five most recent (`hermes-chat.repo-path`, `hermes-chat.repo-recent`), and the target (`hermes-chat.repo-target`), in webview local storage. No file contents, diffs or Git output are kept.
- **Each operation is a new ssh connection,** usually under a second on a LAN. Each request waits at most 60 s, a commit 11 minutes, a push about 7 minutes, gh's reads 4 minutes, and creating a pull request 6 minutes.
- **Verification limits.** The helper is tested by running the exact remote command through `sh -c` against real repositories (`src-tauri/tests/repo_git.rs`). ssh itself, GitHub and gh are exercised only by hand, against the real server and a private sandbox repository (`docs/screenshots/repository/README.md`).
