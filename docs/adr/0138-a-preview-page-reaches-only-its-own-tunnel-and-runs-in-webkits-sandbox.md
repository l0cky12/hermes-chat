# A Preview page reaches only its own tunnel and runs in WebKit's sandbox

A page in the Preview on Linux runs in WebKit's own processes (ADR 0081). Those processes run as the owner, so ADR 0105's check let them use any relay port, the sign-in tunnel's included. A page could scan the ephemeral ports, find the sign-in relay and drive Hermes with the owner's sign-in (#470). A link could also open a server page on any port: the dashboard's 9119, ssh's 22 or a database (#484). The web process ran outside WebKit's bubblewrap sandbox, which the 4.1 API leaves off unless asked (#484). Separately, the window's REST relay let the window read Hermes's config, provider keys and all, and two path tricks slipped past its guards (#478).

## Decisions

- **The sign-in relay serves this process alone.** For each connection, `loopback_peer::admits` finds the peer socket's row in `/proc/net/tcp{,6}`, as before, and takes its inode. The sign-in tunnel's relay (`Peers::ThisProcess`) admits the connection only when that inode is one of this process's own sockets, listed in `/proc/self/fd`. Only Rust uses the sign-in relay: reqwest and the WebSocket clients, all in this process. A server page's relay still admits any program run by the owner's account (`Peers::Account`), since WebKit's network process loads the page.
- **A server page never opens on a port that isn't for web pages.** `server_page::server_page` refuses the dashboard's port, the database and broker ports the dev-server list already hides (`dev_servers::NOT_WEB`), and the Fetch standard's bad ports (ssh, mail, X11 and the rest). WebKit's own block never sees those ports, because the page loads through an ephemeral port on this computer. The refusal is a `notWeb` error, so the Preview shows why and offers no Try again.
- **A Preview page runs in WebKit's sandbox.** `page_context` turns on `webkit_web_context_set_sandbox_enabled` before the context starts a web process. WebKit then starts each web process under bubblewrap, with no access to the owner's files beyond what WebKit grants. Arch's (2.54.2) and Debian 13's (2.54.0) webkit2gtk-4.1 packages depend on bubblewrap and xdg-dbus-proxy. Where bubblewrap can't run, the web process ends and the Preview says that WebKit's process for the page ended.
- **The relay drops credentials from the config.** Hermes answers `GET api/config` with the config as written, provider keys included. The relay removes every value whose key Hermes treats as a credential (`_is_secret_config_key` in `hermes_cli/config.py`: `api_key`, `token`, `password`, names ending in `_key`, `_token`, `_secret` and the like) before the window gets it. It refuses `GET api/config/raw` and the two lists Rust reads for the window, `api/providers/oauth` and `api/providers/custom-endpoints` (ADR 0133).
- **The relay refuses a path with a dot segment in any spelling.** The relay's allow-lists judge the path the window sent, and reqwest sends the path the URL parser makes of it. The parser resolves `.` and `..` spelled as `%2e`, and reads `\` as `/`. `relay_url` refuses a segment that decodes to `.` or `..`, splitting on both slashes, so the path Hermes routes is the path the allow-list judged.
- **The credential-file check judges the path as it resolves.** `protected_server_path` drops empty and `.` segments and resolves `..` before it looks at the file's name and folders, so `/x/.env/.` is `.env`.

## Considered options

- **A per-launch token on every sign-in relay request.** The relay copies bytes and never parses HTTP. A token would mean parsing each request and each WebSocket handshake, and stripping the token before it reaches Hermes. The inode check needs no change to what the clients send.
- **Point reqwest and the WebSocket clients at ssh's Unix socket, so the sign-in tunnel has no TCP port.** ADR 0105 rejected this. It adds a second transport, and Windows keeps the TCP path.
- **Block the page's requests to loopback with a WebKit content filter.** A server page itself loads from `127.0.0.1:<its port>`, so the filter would need a rule per open page, compiled again on each open, and every request type would rely on WebKit's rule matching. The relay is the one place every connection passes through. A `decide-policy` check sees navigations only, not `fetch` or `WebSocket`.
- **Turn the sandbox on only after a bubblewrap probe.** A failed probe would leave pages unsandboxed with nothing to show for it. A failing sandbox shows as an ended page instead.
- **Move every config read into Rust.** The window reads five fields from `api/config` in four places. Dropping the credentials in the relay keeps those reads unchanged and keeps the keys out of the window.

## Consequences

- **Partly supersedes ADR 0105.** Its decision "One check for both tunnels" no longer holds: the sign-in relay admits only this process. Its consequence "A program run by the owner's account can still use it, as can the webview" now holds for server-page relays only.
- **Partly supersedes ADR 0133.** Its consequence "The relay still passes any `GET` the window sends" no longer holds for the two provider lists and the raw config.
- **A sandboxed page needs a session bus whose desktop portal answers.** WebKit asks `xdg-desktop-portal` through `xdg-dbus-proxy` when it starts a sandboxed web process. On a session where the portal hangs in activation, each call waits out D-Bus's 25-second timeout and the page doesn't load. An unsandboxed page never asks. A desktop session runs the portal, and a dead accessibility bus only adds a warning (checked on WebKitGTK 2.54.0).
- **On Windows the sign-in relay serves this process alone too.** The peer's row in the TCP table names the process that holds it (ADR 0105), so `Peers::ThisProcess` compares that process with the app's own; there is no inode to look up. The Preview there isn't this view (ADR 0081).
- **macOS is unchanged.** `admits` says yes to every connection there.
- **A server page can still reach another server page's relay**, since both run as WebKit's network process. Each server page is a page the owner opened on their own server.
- **Verification.** `only_this_app_reaches_the_dashboard_through_the_tunnel_not_another_program_of_the_owners` (`tunnel.rs`), `ports_for_the_dashboard_and_other_services_than_web_pages_are_refused` (`server_page.rs`), `a_page_runs_inside_webkits_bubblewrap_sandbox` (`page_view.rs`, ignored: it needs a display and a session bus), and in `tests/transport.rs` `the_config_reaches_the_window_without_its_credentials`, `the_relay_never_reads_the_raw_config_or_the_lists_rust_reads_for_the_window`, `an_endpoint_id_that_is_a_dot_segment_once_decoded_is_refused_before_it_reaches_another_route` and `an_artifact_write_refuses_credential_files_odd_paths_and_too_much_text`.
