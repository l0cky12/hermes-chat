# Profiles are managed in Settings; renames re-key this computer's data and deletes forget it

Issue #447: the app could switch profiles (the chat list's header, ADR 0001) and clone one (ADR 0074), but making a blank profile, renaming one, changing its description or model without switching to it, and deleting one needed the Hermes CLI or Hermes's own dashboard. The deployed Hermes (`f0d94882`, `hermes_cli/web_routers/profiles.py`) has a route for each, so no Hermes change is needed. ADR 0074 had rejected "a Profiles tab in Settings" because nothing in Settings made or removed a profile; now something does.

## Decisions

- **A Profiles tab in Settings, before Persona.** It lists every profile `GET /api/profiles` returns, in Hermes's order: the id (and `default`'s display name first, "Main (default)"), In use, Default, Gateway running, the switcher's unread count, the distribution, model and provider (or "No model set"), the skill count, and the description cut to one line with an `auto` tag when Hermes wrote it. It reads the list when it opens, on ⟳, and after every change. The switcher still only switches: the tab's **Open** runs the switcher's own question (a running reply or a waiting Approval) and then the app's guard for unsaved edits.
- **New profile is blank**; copying stays with Clone, which opens from a row's menu with that row as the source and selects the clone afterwards. The name is checked as typed (Hermes's id rule, its reserved names, `default`, the names listed: `nameIssue` in `profiles.ts`, which Clone shares), and Hermes's own 400 is shown word for word. The model pickers read Settings → Model's catalogue (`GET /api/model/options`). A model Hermes didn't set (`model_set: false`) is said in Hermes's words with **Set model…**, not as a failure. The new row is selected and **Open it now** offered; the app never switches by itself.
- **Edit saves each field through its own route, in order: description, model, then the name**, so the earlier calls use the old name. A failed field keeps the dialog open, marked in Hermes's words; the fields that saved stay saved. The persona isn't edited here: a link opens Settings → Persona on that profile, so there is one persona editor with its own guard (ADR 0117). The row menu's Edit persona, Memory and Skills open those tabs with their picker already on the profile.
- **Renaming `default` sets only `display_name`.** The field is labelled Display name, Hermes keeps the id `default`, and the display name shows in the switcher, the Profiles row and the profile pickers. Each `GET /api/profiles` the app makes keeps it in the transport's snapshot.
- **A rename re-keys this computer's data, only after Hermes answers ok.** `renameProfileLocally(connection, from, to)` (`profileLocalData.ts`) moves every per-profile key of that connection from `from` to `to`; another connection's profile of the same name is untouched. Renaming the profile in use moves the app to the new name in place, keeping the chat on screen. A rename is noted before it is sent (`hermes-chat.profile-renames`) and the note cleared once the data moved or Hermes refused; a note left by an app closed in between is offered once in the tab, when the list shows the old name gone and the new one there ("Move this computer's drafts, tags and pins…"). No rename while a reply runs in that profile, or while a queue is about to send: Save says which.
- **One list of per-profile data, walked three ways.** `profileLocalData.ts` lists every place this computer keeps a profile's data, in its four shapes: keys per profile or chat (chat list, Saved copies, outbox, queue, held messages, branches, drafts, persona edits and versions), keys per connection whose value names profiles (the profile shown last, the profiles pulled older, inbox dismissals), `{scopes}` documents (projects, Outputs, snoozes, Cleared, pins, Stop waiting, imports, worktree chats, the project context ledger, and the tags and project defaults files every window shares), and the display prefs kept per profile (the chat to reopen, the model pick, templates tied to a project). The same walk moves a profile (rename), drops it (delete), or drops a whole connection (`forgetConnection.ts`, ADR 0112). It moves the in-memory copies too: persona edits, drafts the store couldn't write, messages on their way, failed-write queues. A test reads the app's source for every storage key it names, and fails on one this list doesn't name or `NOT_PER_PROFILE` doesn't explain. Sharing the list fixed a gap in removing a connection: its pins, Cleared marks, Stop-waiting marks and context ledger were left behind before.
- **Delete asks for the typed name** and lists what goes on the server and on this computer, with the counts the app can read: chats (Hermes's own `total`, archived included), own skills (the row's count) and scheduled jobs (`cronJobs.ts`). A count it couldn't read is left out. Queued and Failed messages that would be lost are counted first. **`default` can't be deleted**, and the menu says why. **Deleting the profile in use switches to `default` first** through the switcher's question and the app's guard, with Settings left open; if the owner stays, nothing is deleted. After Hermes answers ok, `forgetProfileLocally` removes this computer's data for that profile only. `settlement_pending: true` counts as deleted, with Hermes's `retry_command` shown and a Copy button; a 404 (another client deleted it) counts as deleted too, and the local data goes.
- **A route the server lacks disables that action alone.** Diagnostics gains a Profiles row (`capabilities.ts`), checked by reading `GET /api/profiles`; without it the tab shows the usual note in its place. Each change is a capability *action*, known by method and path. Nothing is written to find out (ADR 0044), so an action is learnt missing from its own first attempt: Hermes's 404 or 405 to it marks that action lacking, the transport refuses it from then on before sending (`RouteMissingError`), the tab disables it with the route named, and the Diagnostics row and the copied report list it. The Profiles capability stays supported, and the Clone dialog's create and delete, on the same routes, are refused only when their own action is lacking. Check again lets them be tried again.
- **Hermes saves "Write for me".** `describe-auto` writes the description itself, marked as Hermes's (`hermes_cli/profile_describer.py`: `write_profile_meta(..., description_auto=True)`), so the field can't hold it unsaved as #447 sketched. The field shows what Hermes saved, says so, and a Save with an edit replaces it as the owner's.
- **What the relay passes** (`src-tauri/src/transport.rs`): `PUT api/profiles/{id}/description` with exactly `{description}`, `PUT api/profiles/{id}/model` with exactly non-empty `{provider, model}` (`profile_field_write`), and `POST api/profiles/{id}/describe-auto` with exactly `{overwrite: bool}` (`profile_describe_auto`). `PATCH` and `DELETE` were already relayed for any `api/` path.
- **Keyboard and words.** The list is a listbox: Up and Down move, Enter edits, Delete deletes, Shift+F10 or the Menu key opens the row's menu; each dialog keeps focus inside and returns it to the row. Every word comes from the catalogue (ADR 0100), and a pseudo-locale test checks the tab. Settings search names the tab by what it does and by the profiles' names.

## Considered options

- **Re-key by moving every key that contains the old name.** Rejected: a profile name is a substring of other names and of chat ids, and another connection can have a profile of the same name. The scope's profile position is matched exactly.
- **Check each write route ahead with a GET, reading 405 as "the route is there".** A GET can't write, and FastAPI answers 405 for a path whose routes take other methods. Rejected for now: `PATCH` and `DELETE` share `/api/profiles/{name}` and `POST` shares `/api/profiles` with the list, so a 405 can't tell which one is there.
- **A second profile switcher in Settings.** Rejected (ADR 0001): Open calls the one switch path.
- **Guard the edit dialog's unsaved fields with Settings' tab guard.** The dialog is modal, so nothing behind it can be reached while it is open; it asks itself before closing with changes.
- **Export and import a profile, and Hermes's sticky default (`POST /api/profiles/active`).** Out of scope, as #447 says: both work with the server's disk or its CLI, not this app's.

## Consequences

- Making, renaming, describing, setting the model of and deleting any profile no longer needs the server.
- A new kind of per-profile data must join `profileLocalData.ts`, or its test fails.
- Verification: unit tests of the API against FakeHermes's profile routes (`manageProfiles.test.ts`), of the local data walks (`profileLocalData.test.ts`), of the tab in the running app (`profileSettings.test.tsx`, `profileSettingsTranslated.test.tsx`), and of the relay rules (`transport.rs`). The real app was driven against a throwaway `f0d94882` dashboard for the PR's screenshots, with the renames and deletes read back from the server.
