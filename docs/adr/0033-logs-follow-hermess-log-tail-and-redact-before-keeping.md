# Logs follow Hermes's log tail, and every line is redacted before it is kept

Diagnosing a dropped connection or a failing agent meant reading log files outside the app. The Logs screen (issue #76) shows two kinds of source, one at a time, picked by name: this app's own diagnostics, and the profile's Hermes logs.

The only supported way to read Hermes's logs is the dashboard's `GET /api/logs?file=&lines=&profile=` (`hermes_cli/web_routers/status.py`, the same at `bf0203a` and `f0d9488`). It answers `{file, lines}`: the last `lines` lines, at most 500, of one of the profile's files under `$HERMES_HOME/logs/`. It has no cursor, offset, stream or rotation signal. The dashboard's own Logs page polls it every 5 seconds.

## Decisions

- **Following is polling the tail.** While a Hermes log is on screen and the app is connected, it asks for the last 500 lines every 2 seconds, one request at a time. Each answer is matched against the previous one: the longest run at the end of the old answer that starts the new one marks where the new lines begin. No overlap means lines may be missing, and a note in the list says which case it looks like. A file shorter than 500 lines was rotated or emptied. A full answer means more than 500 lines came between two reads. The app never guesses the missing lines.
- **Sources are Hermes's own names.** `agent`, `errors`, `gateway` and `mcp` (`agent.log`, `errors.log`, `gateway.log`, `mcp-stderr.log`). The `gui`, `desktop`, `update` and `handoff` logs belong to the official desktop app and `hermes update`, and the route reads `update` and `handoff` from the wrong home for a non-default profile, so they aren't offered. A server without the route (404), or without a file name (400 "Unknown log file"), is reported and not asked again. Other failures, such as a refused permission or a lost connection, are shown and retried.
- **Gaps are notes in the list.** A stop is noted where reading picks up again, with the times and the reason: a lost connection, a failed read, or another source shown. It is followed by the rotation or missed-lines note if the answers don't overlap. Notes show whatever the filters are.
- **A ring buffer for each source.** Each Hermes log keeps its newest 5,000 lines and this app keeps its newest 2,000. The screen says how many older lines were dropped. Listeners hear of changes at most every 100 ms, and rows off screen skip layout (`content-visibility: auto`), so a burst is one render.
- **Pausing freezes the view, not the reading.** Pause, or scrolling up, a click or an upward key in the list, shows what was there at that moment while reading carries on, and counts the new lines. Follow shows everything again and goes to the newest line.
- **Redaction happens before anything is kept.** Each line loses its terminal CSI codes (colors, cursor moves), so a code can't hide a secret from the patterns. Then known secret shapes are replaced with `[redacted]`: private keys, `Authorization` and cookie headers, bearer tokens, URL credentials (any user part before `@`, with or without a password, but an SSH login), tickets, keys and `auth=`/`sig=` values in URL queries, JWTs, common provider key prefixes, bot tokens, and values of keys named like a secret. Then the other control characters and bidi overrides are written out (`\x1b`, `‮`). The screen, Copy, Export and the support bundle use only that text. Hermes's own `RedactingFormatter` has already run on most lines, but `mcp-stderr.log` is raw stderr, and the app doesn't rely on the server. The bundle says redaction covers known shapes and may miss a secret written another way.
- **Plain text only.** Lines are React text children, never HTML.
- **Two times.** Each line shows when this app received it, in this computer's time, UTC, or hidden. The time inside a Hermes line is the server's clock in its own zone, which Hermes doesn't name, so the app doesn't convert it.
- **This app's diagnostics** are the connection's changes (with the route and profile), the chat list's sync failures, every toast shown, console warnings and errors, uncaught errors and unhandled rejections. They are in memory only, for this run of the app, across sign-ins.
- **Connection attempts are the one thing kept on disk** (#270). A launch that failed to connect left no trace once the app was closed, and closing a stuck app is what most people do. So each time the app opens a connection, at launch or to reconnect, it keeps one JSON line in `connection-attempts.jsonl` in the app's data folder: when it began and how long it took; each route tried, by its kind (LAN, Tailscale, web address, SSH) and its id, never its address; the steps each route reached (keyring, DNS for a URL or the tunnel for SSH, status, sign-in, ticket, WebSocket, then `gateway.ready`) and how long each took; and how it ended, with the error. Rust says when each step starts (`connect_steps.rs`, the one list of steps; a step's own time limit for one of several routes, #269, runs inside it); the webview builds the line (`attempts.ts`) and hands it to Rust to keep (`connection_attempts.rs`).
  - **No address, secret or header value.** First, in the error as it came, every word holding the connection's password, token or a header value goes whole, line breaks and all. Then `redact()`, and line breaks become spaces. Then the shapes of any address: a URL, `user@host`, IPv6, IPv4, a dotted host name (underscores too), ssh's "hostname X" and "host X port 22". Only then the connection's own addresses and username, so a short one can't split an address and leave part of it; a value shorter than four characters only goes as a whole word. A text that still looks like it holds an address is withheld. Rust checks every line again before it touches the disk: known fields only, a UUID for ids, a route id's shape, steps in order, and error texts of at most 300 characters with no control character, `://`, `@`, IPv4 or IPv6 address. A line refused for a text is kept without its texts, on screen too; a write that fails otherwise (a full disk) keeps them and is noted in this app's diagnostics. Message bodies, the server's id and the route's target are never in a line.
  - **The newest 50.** Every write, from any copy of the app, takes a lock beside the file, replaces the line with its id or adds it, keeps the newest 50 by start time, and replaces the file whole (mode 0600). The file can't grow past 50 lines, even after a crash; lines that don't read are dropped at the next write.
  - **Stopped is not failed.** A stop while Rust opens a route, or while the app waits for `gateway.ready` (setup's Stop, switching connections, quitting), ends the attempt as stopped.
  - **Written as it goes.** The line is written again at each step, so an attempt the app was closed during is on disk at the step it was on. Each line names the launch that made it; one left unfinished by another launch reads "Didn't finish: Hermes Chat was closed while it was connecting, at status".
  - **Read in Logs.** Logs → Connection attempts reads the file each time Logs opens, one row per attempt, and the support bundle has it as its own part, ticked or not. Setup's connection test and the checks of a preferred route aren't recorded: they would push the owner's attempts out.
- **The support bundle** is one text file with the sources ticked in its preview: this app and each Hermes log read since Logs opened, with every line kept, whatever the filters show. The preview lists the sources, line counts, what was dropped, how many of each kind of secret were redacted, and the file's first 400 lines. Nothing is uploaded: Save opens the native Save dialog (`logs_export`). Hermes's own `/api/ops/debug-share`, which uploads to a paste service, isn't used.

## Considered options

- **Tailing the files over SSH or the Terminal**: this would read beyond the supported API, and wouldn't work for a direct-URL sign-in.
- **Asking Hermes to filter** (`level`, `search`): its search reads at most 2,000 lines and its level filter changes the tail, which breaks the overlap matching. The app filters what it kept.
- **Keeping logs on disk**: a file of redacted-but-maybe-not-clean text is a liability, and the owner saves what they want. Still rejected for this app's diagnostics and Hermes's logs. The record of connection attempts is the narrow exception (#270): closed fields, route ids instead of addresses, error texts scrubbed of addresses and checked again by Rust, no message bodies, 50 lines.
- **Keeping only a closed list of error kinds** (no text at all) for connection attempts: it can't leak, but an error nobody listed, such as an unfamiliar Windows socket error, would read "other", and that is the case the record is for.
- **Writing the attempts from Rust alone**: Rust sees one route at a time and not the wait for `gateway.ready`, and `redact()` is the webview's.

## Gaps

- Overlap matching works on text, since Hermes gives no offsets. A run of identical lines can hide a repeat of itself, and more than 500 lines in 2 seconds (250 a second) can't all be read. A server change that adds a byte offset or a since-cursor to `/api/logs` would close both gaps.
- Polling stops while another source is shown or Logs is closed. What was read goes when Logs closes or the profile changes.
- Redaction is pattern-based. A password in a sentence, or a key with an unknown prefix and an unrevealing name, can get through.
- An address in a connection attempt's error is taken out when it is one of the connection's own, or has an address's shape. A single-word host name that is neither, such as one a server's answer names, can get through.
- Rust reports each step over a channel with when it started, measured from the start of that route; the webview adds that to the time it began the route, and times the end of a route, and `gateway.ready`, itself. A duration is right to within the time a command takes to reach Rust. A step whose message comes after its route ended still goes in its place.
- After a failed launch the app tries again every 60 s while Offline (#269), so 50 attempts cover under an hour; the launch's own attempt then drops off the record.
