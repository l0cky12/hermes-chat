# Extra request headers for a gateway in front of the dashboard, kept in the keyring and never sent to another site

A direct URL connection (ADR 0004) can carry **extra request headers**, so a gateway in front of the dashboard, such as Cloudflare Access with a service token (`CF-Access-Client-Id`, `CF-Access-Client-Secret`), lets the app through. The owner edits them as name and value pairs on the sign-in screen, under the URL. Rust sends them on every request to the dashboard: the password sign-in, the WS ticket, every REST call, and the `/api/ws` handshake. The SSH tunnel never sends them, since it goes straight to the dashboard on the server's loopback.

- **Where they go.** Only Rust talks to the dashboard (ADR 0003), so the headers are added there, to the reqwest client's default headers and to the WebSocket handshake request. The webview never makes a request with them. Images in a reply load in the webview, and composer thumbnails are read from disk, so neither carries them.
- **Redirects.** reqwest strips only its own credential headers (`Authorization`, `Cookie` and a few more) when a redirect leaves the host, so custom headers would follow it. With extra headers set, a redirect is followed only within the dashboard's origin (scheme, host and port). One to another origin stops there and fails with an error naming that origin; this is also what a Cloudflare Access login redirect looks like. Without extra headers, redirects are followed as before.
- **What is refused.** A name must be a valid HTTP token. A value is ASCII letters, digits, punctuation, spaces and tabs on one line, up to 8 KB, with spaces and tabs around it dropped, so no line break can inject a header. At most 32 headers. A name set twice, ignoring case, is refused rather than merged or overridden. Names the transport or HTTP sets itself are reserved: `Host`, `Content-Length`, `Content-Type`, `Transfer-Encoding`, `Connection`, `Upgrade`, `Cookie`, `TE`, `Trailer`, `Keep-Alive`, `Expect`, `Origin`, and any `Sec-WebSocket-*` or `Proxy-*`. `Authorization` is allowed, for gateways that want a bearer token. Rust checks all this when connecting. Errors name the header, never its value.
- **Storage.** Names and values are kept as JSON in the system keyring, beside the password, never in local storage, together with the URL they were signed in to. They are read back only for that URL. A sign-in to a new URL whose headers the keyring can't save therefore never sends the old URL's headers to the new one. They stay after Sign out, so the sign-in screen still has them. Once the owner changes the URL there, the values filled in from the keyring are cleared, names kept, so they can't be sent to another server either; signing in with none deletes the entry. Settings shows the names only, and says so when the keyring couldn't save them.
- **Logs.** Values are marked sensitive in Rust, so they print as `Sensitive` in debug output, and errors never include them. The app installs no logger. tungstenite traces the whole handshake request at `trace` level, values included, so a logger added later must keep tungstenite below `trace`.
- **Proxies.** reqwest used a proxy set in the environment (`HTTP_PROXY`, `HTTPS_PROXY`), so over plain `http://` that proxy saw the headers and the password. Since ADR 0139 no dashboard request goes through a proxy.
- **TLS.** The app had no TLS compiled in, so `https://` and `wss://` dashboards couldn't connect at all. Gateways such as Cloudflare Access are HTTPS only, so reqwest and tokio-tungstenite now use `native-tls`: the system's OpenSSL and trust store, already among the Arch prerequisites.

## Considered options

- **Send them through the SSH tunnel too.** Rejected: nothing sits between the tunnel and the dashboard, and the headers would reach a server that doesn't need them.
- **Strip the headers on a cross-origin redirect and follow it.** Rejected: the dashboard's cookies and the sign-in body would still go to another site, and a gateway's login page isn't anything the app can use.
- **Keep the names in local storage and only the values in the keyring.** Rejected: splitting one list across two stores adds a way for them to drift apart, for no gain the owner would see.
- **rustls instead of native-tls.** Rejected for now: native-tls links the system OpenSSL, which the Arch prerequisites already install and the system keeps updated, rather than compiling a crypto library into the app.
