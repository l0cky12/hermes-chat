# The global shortcut is registered the way the desktop allows, and only what registered is shown

> **Superseded** (#169). The global shortcut was removed: it didn't work on every desktop (Hyprland with Quickshell among them), and a key the owner binds in their desktop to `hermes-chat --toggle` does the same job. `x11_grab.rs`, `portal.rs`, the `fake_portal` example, the shortcut's commands and its Settings section are gone, as is the `x11rb` dependency. What stays is the single window over the session bus name `net.l0cky12.HermesChat` (`remote.rs`): a second launch, `hermes-chat --show` and `hermes-chat --toggle` bring the running window forward, as the tray (ADR 0034) and chat links (ADR 0037) rely on. An older version's `global-shortcut.json` is deleted at startup (`summon::forget_old_shortcut`).

Issue #78 asks for a shortcut that brings Hermes Chat forward from any other app. A global shortcut doesn't work the same way on every Linux desktop. X11 lets an app grab a key, and the X server refuses with `BadAccess` when another app already has it. Wayland lets no app grab keys. A Wayland desktop either offers the XDG desktop portal's GlobalShortcuts interface (KDE Plasma, GNOME 48 and later, and Hyprland through xdg-desktop-portal-hyprland) or offers nothing (Sway, and older desktops). Under XWayland, an X11 grab sees keys only while an X window is focused. It would look registered and never fire from a Wayland app.

## Decisions

- **One mechanism per session, chosen at startup.** On an X11 session (no `WAYLAND_DISPLAY`, `XDG_SESSION_TYPE` isn't `wayland`, and `DISPLAY` is set), the app grabs the key itself on the root window (`x11_grab.rs`, with `x11rb`). Every grab and release waits for the X server's answer, so the key is reported taken when it is, and is free once a release returns. The key is grabbed at its keycode in the keyboard layout (XKB group) in use, read from XKB's own key map at any shift level. It is grabbed again when the owner switches layout or the keymap changes. A layout without the key gets no grab, rather than another layout's key. On Wayland, the app asks the portal for GlobalShortcuts. If the portal doesn't offer it, nothing is registered, and Settings gives bind lines for the desktop instead. The app never grabs through XWayland.
- **Settings shows what registered, not what was chosen.** The status line reports X11's answer, or the key the portal says the desktop set (`trigger_description`). It follows `ShortcutsChanged` when the owner changes the key in the desktop's own settings. If the portal binds without a key (Hyprland never sets one), Settings says so and gives the `global` bind. That bind uses the name `hyprctl -j globalshortcuts` lists for the shortcut.
- **A registration that ends by itself stops counting as working.** If the desktop closes the portal session (`Session.Closed`), the portal restarts, the connection to it closes, or a layout change leaves the X11 key grabbed by another app, Settings shows the shortcut as failed and offers Retry. It never goes on saying "Working". A loss that arrives after a bind succeeded but before the app takes the registration is kept, so that registration is refused and released instead.
- **Choosing the key again asks the portal again.** The desktop may set another key than the one asked for, so on the portal, choosing the saved key again or pressing Reset binds again in a new session. On X11 a working grab already is that key.
- **A change registers first and releases the old key last.** The new key is saved only once it registered, and the old one is released only then. On the portal, each change binds in a new session and closes the old session after. A conflict, a refusal in the desktop's dialog, or an error leaves the working key in place. Settings shows the failure with Retry, which tries that key again. A saved key that fails at startup shows the same way, with "No global shortcut works now."
- **A press counts as "in front" by the focus just before it.** An X11 grab taking effect sends the focused window a FocusOut, so a window that lost focus within the last 400 ms counts as having been in front. Without this, hiding when in front only worked on every other press.
- **Recording lets go of the X11 grab.** While Settings records a new key, the X11 grab is released and then taken back. Otherwise pressing the current key would hide the window instead of reaching the recorder. The portal's key belongs to the desktop and can't be paused.
- **Activation shows the one window, or hides it only when asked.** A press un-minimizes, shows and focuses the window, then puts the cursor in the selected pane's composer. Drafts stay as they were. If Settings or another screen covers the chat, it stays open with its edits, and focus stays where it was. A press while the window is visible, not minimized and focused hides it only when **Hide when already in front** is on. On Wayland the window takes focus with the portal's activation token, or with the token the desktop gave `hermes-chat --show`. Without a token, Hyprland and Sway are asked to focus the window through `hyprctl dispatch focuswindow pid:…` and `swaymsg [pid=…] focus`, since both ignore a focus request that has no token.
- **Dedicated commands, and one instance.** `hermes-chat --show` brings the window forward. `hermes-chat --toggle` also hides it when it's already in front. Both reach the running app over the session bus name `net.l0cky12.HermesChat` that `--screenshot` already uses. `--screenshot` isn't reused for this. With no app running, the command starts one. A plain `hermes-chat` with one already running shows that one and exits, so a hidden window is never duplicated. The name is taken in `main`, before any window exists, with a request the bus answers atomically. Of two launches at once, one gets it and the other forwards its request. Requests that arrive while the owner is still starting are kept until its window is ready. If the owner doesn't answer, the new launch starts anyway and queues for the name, as before. An update's restart sets `HERMES_CHAT_NEW_INSTANCE`, so the new app starts while the old one still owns the name. `npm run app` sets it too, so a development build runs beside an installed one.
- **Storage.** `global-shortcut.json` in the app's config directory (`$XDG_CONFIG_HOME/net.l0cky12.hermes-chat/`) holds the shortcut as `Ctrl+Alt+H` (or `null`) and `hideWhenActive`. It applies to this computer, for every server and profile. It never holds a command. A key that doesn't parse, or one without Ctrl, Alt or Super, turns the shortcut off at load.
- **Every way of choosing a key is checked.** Recording, Reset, Retry, and the screenshot shortcut's own default button all refuse keys that the other shortcut already uses.
- **Off by default.** A key grabbed from every app, or a portal dialog at first launch, shouldn't appear unasked. Reset sets Ctrl+Alt+H.
- **Released on exit.** The X11 grab is released and the portal session closed when the app exits, before an update's restart starts the new app. The screenshot service on the bus is left alone.

## Considered options

- **tauri-plugin-global-shortcut** (2.4, with global-hotkey 0.8): on X11 it sends `XUngrabKey` without flushing it. In testing, a released key stayed grabbed, so a changed or turned-off shortcut went on taking the key from other apps. Under Wayland it registers through XWayland and claims success, but only receives keys while an X window is focused.
- **Only desktop bindings**: they work everywhere and from a cold start, but the app couldn't detect a conflict or show what registered. Bind lines are still offered on Wayland, beside the portal.
- **Keeping the setting in the webview's display preferences**: the shortcut must register before the webview loads, and on the sign-in screen, so Rust owns it.

## Gaps

- The portal path was tested against a stand-in portal (`src-tauri/examples/fake_portal.rs`) that follows the GlobalShortcuts spec on a private bus. It wasn't tested against xdg-desktop-portal-hyprland, KDE or GNOME. How those desktops name the app, whether they remember a binding across launches, and whether Hyprland's `hyprctl -j globalshortcuts` output matches what the app reads are all unverified.
- Hyprland lists the shortcut under the app id the portal gives it. For an app that isn't sandboxed, that id can be empty (`:hermes-chat`), and the app doesn't register one.
- An app-local shortcut in another program (an editor's Ctrl+Alt+H, say) isn't a conflict the X server or a portal reports. The global key wins in that program.
