# The inbox is worked out from what the app already reads, and its dismissals are kept here

> **Updated by [ADR 0171](0171-an-approval-is-answered-in-the-inbox-with-the-chats-own-card-and-a-notification-opens-or-denies-it.md).** A waiting Approval in the profile shown shows the chat's own card under its entry, answered there the chat's way. Every other entry still only opens its chat.

The inbox lists, for every profile on the server signed in to, the chats with a reply running, an Approval waiting, a failure or a Failed message, and something new and unread. It adds no store of its own on the server and no event stream of its own. Each entry is worked out from three sources the app already has or reads cheaply:

1. **The shown profile, over its socket.** Replies running, Approval cards (one entry per card, keyed by its request id), error rows, Failed messages, and Unread chats in its list.
2. **The other profiles, over dashboard REST.** The two-minute check that already counts Unread chats for the profile switcher (`GET /api/sessions?profile=`, one page of 50) now keeps that page's chats, so each Unread one becomes an entry. Failed messages come from the outbox this computer keeps for each profile.
3. **What is live across the server: legacy `session.active_list`.** On the dashboard's legacy socket it lists every live session in the dashboard's process, in every profile, with `status` `waiting` (a server→client request is open), `working`/`starting` or `idle`, and `session_key`, the stored session id (`tui_gateway/methods_session.py:1143`, `session_registry.py:648-686` at the deployed `bf0203a`). Rows carry no profile. A session this app started or resumed is known by its runtime id (the row's `id`), which names its profile for sure. Any other is looked up by its stored id in every profile (`GET /api/sessions/{id}?profile=`), three sessions per check at most, the ones tried longest ago first, four profiles at a time. It is placed only when exactly one profile has it; a copied profile keeps the same ids, so two answers mean it can't be told. An answer is kept for that runtime session while it stays live; the same chat running again, perhaps in a profile copied since, is looked up afresh. No answer, or a profile that answers with an error, leaves it to the next check. A session that can't be placed isn't listed, and the inbox says how many. For a chat the shown profile has resumed on this connection, or one holding a waiting card, the chat's own state wins over the check, which may be older; when the connection drops, the check's rows for the shown profile are dropped too.

Each entry has a key from stable ids (profile, stored session id, Approval request id, outbox row id), so a reconnect, a resume that lists an Approval again, or a repeated check reports the same entry, and it shows once. Dismissing an entry keeps its key and its event time on this computer, for the connection (server and username), in local storage. An entry dismissed shows again only when it has something newer: a completed chat with later activity, or a background chat waiting again later. Dismissing an Approval card also dismisses, up to that moment, the chat's "waiting" entry, the form the same Approval takes once the owner has switched away and only a check says the chat waits; with several cards in a chat, only once every one is dismissed. The other way round, a "waiting" entry dismissed in a background profile also covers the cards that resuming its chat then shows, as long as Hermes reports no activity in the session after the time dismissed; once shown, those cards are dismissed under their own keys, so a dropped connection, which drops the session's live row, doesn't bring them back. Hermes gives an Approval no time of its own, so a new request that comes without the session's last activity moving on stays covered too. Dismissals are kept 30 days, 1000 at most; older ones are dropped when read. Dismissing never marks a chat read, never settles or unsettles it, and never archives or restores it.

The inbox never answers an Approval, retries a failed reply or resends a message. An entry opens its chat, in its profile, the way the profile switcher does, and puts focus on the Approval card, which the owner answers there with the existing rules: only Hermes's current request, broader grants confirmed first. The card's own guards are unchanged.

## Considered options

- **`GET /api/profiles/sessions` or `/api/profiles/sessions/sidebar`**, one merged read of every profile. Rejected for the same reason as for the switcher's dots: one merged page can push a quiet profile's chats out, and the per-profile page keeps each request scoped.
- **Resuming other profiles' chats on the shown profile's socket to read their `open_requests`.** That would attach those sessions to this connection, so their events and Approvals would arrive here, and Hermes's orphan reaping would follow this connection. Rejected: looking must not change what the server does. `session.active_list` tells waiting from working without attaching anything.
- **`approval.pending`.** Needs a runtime session id on this connection, so it has the same problem.
- **Placing a live session by the chats the checks read.** Cheaper, but a profile's page holds only its 50 most recent chats and not every profile is read each time, so a copy of the id in another profile could take the entry, and opening it would open the wrong chat. Rejected for the lookup by id.
- **Keeping dismissals on the server** (for example as a session flag). Hermes has no such field, and `unread` is shared with every client, so using it would change the chat for the owner's other clients. Rejected.
- **Notifying on the desktop for other profiles.** Not done: the desktop notifications stay as they were, for replies finishing and Approvals arriving on the shown profile's socket while the window isn't focused.

## Consequences

- Running and waiting work is seen only for sessions live in the dashboard's own process: chats run from this app, the official desktop app or the dashboard's chat tab. A chat running in the CLI, a messaging gateway or cron runs in another process, and shows only once it is Unread.
- A background chat waiting on the owner shows as waiting without saying what is asked. Opening it resumes it, which shows the card.
- `session.active_list` is asked at most every 15 seconds, with the two-minute check and every 30 seconds while the inbox is open. A Hermes without it answers "method not found" once, and is asked no more; the inbox says it can't see running work in other profiles.
- The other profiles' Unread chats come from the 50 most recent; a profile with more says so.
- A failure in one source marks its entries "as last seen" and names it; the others keep working. With no connection, everything is as last seen.
- A failure (an error row) is seen only on the socket and Hermes keeps no record a check could read, so one seen in a profile is kept, by row id and a fingerprint of its text, until the owner is back in that profile. No text is kept.
- An entry for a chat older than the profile's month-long list opens it the way a search result does: the chat is added to the list, Settled.
- Approval and error entries have no time from Hermes, so they show when this app first noticed them, for as long as it runs.
- Expired Approvals stay in the inbox as expired, not actionable, until dismissed or until the chat is loaded again, which drops the card.
