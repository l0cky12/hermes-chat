# Outputs are the files Hermes's tools say they wrote, indexed on this computer as metadata only

> **Superseded by [ADR 0170](0170-the-outputs-screen-is-removed-and-artifacts-open-from-the-preview.md)** (#570). The Outputs screen and its index are gone. Its rules for what counts as an Output no longer run anywhere. The `outputs` capability and its check stay for extensions that name it.

Outputs lists the files Hermes made in a chat, a project or a whole profile, so the owner can find them without reading a long transcript or browsing the server. Hermes has no record of "files this session produced": the official desktop app's Artifacts page scrapes every path and URL out of replies and tool output. This app counts a file only when a tool says, in its own structured result, that it wrote it:

| Tool | Result field (deployed `bf0203a`) | Output |
| --- | --- | --- |
| `write_file` | `resolved_path`, `files_modified`, `bytes_written` (`tools/file_tools.py`) | the file, with the size written |
| `patch` | `files_created` (`tools/patch_parser.py`) | each file it created, even when a later part of the patch failed; files it only edited aren't Outputs |
| `text_to_speech` | `file_path`, `file_paths` (`tools/tts_tool.py`) | each audio file, on the dashboard's machine |
| `image_generate` | `agent_visible_image` for a non-local terminal, else `image` (`tools/image_generation_tool.py`) | the saved image, where the tools run if Hermes says so, else on the dashboard's machine; a provider URL isn't a Server file |

Otherwise a failed call (`error`, or `success: false`) made nothing. A path in a reply, in `MEDIA:` text the model wrote, in terminal output, or in any other tool's result is a mention, not an Output, since nothing confirms the file was made. A producer's result that doesn't name a file it wrote (an older Hermes, or a result Hermes cut short) is counted, and the chat's discovery is labelled partial. An older `write_file` result without `resolved_path` takes the path from the call's own arguments when that path is absolute. The owner can add any Server file by its path, checked first; it shows as "Added by you".

## Reading Hermes

- **Which machine:** `write_file` and `patch` write where the profile's tools run, which is its SSH workspace when it has one. `text_to_speech` and `image_generate` save on the dashboard's own machine (`HERMES_HOME`), unless an image result gives `agent_visible_image`, the same file as the tools see it. An Output on the dashboard's machine is marked `host`: its availability comes from the managed files listing (`GET /api/files`), and its preview reads `GET /api/files/read` within the Server files limits (text 1 MiB, images 10 MiB). Every other Output uses the agent fs routes below. For a profile without an SSH terminal, both are the same disk.
- **Stored rows:** dashboard REST `GET /api/sessions/{id}/messages?profile=…&order=latest&inline_images=false`, newest first, 100 rows a page, at most 2,000 rows a chat and 25 chats a run, the most recently active first. Legacy `session.resume` isn't used, because it drops most tool results (it keeps `content` only for `write_file`, `patch` and `skill_manage`). Each page goes through `hermes_get_limited` with a 4 MiB cap: a page over it is read again in smaller pages, and a single row over it is skipped and counted. Each chat has a 64 MiB budget for all its pages, counted in UTF-8 bytes; a page refused for its size spends its whole limit, so a run of oversized rows stops too, and a smaller page is tried with whatever budget is left. Past the budget, older rows aren't read and the chat is labelled partial. Each page is cut down at once to the producer rows' result fields and the `path` argument of `write_file` calls, so a patch's diff or a written file's contents aren't held while the rest is read. A chat is read again only when its last activity changed, or the owner reads more chats.
- **Where a file is now:** `GET /api/fs/list?path=<folder>&profile=…` (or `GET /api/files?path=<folder>` for a `host` Output), one listing per folder and machine, at most 40 folders per check, when Outputs opens or changes scope, when the owner presses Refresh, and when the owner adds a file (opening was added by ADR 0064). A file is Available when its folder lists it, Missing when it doesn't or the folder is gone, Not allowed for `EACCES` or a 403, and A folder now when the name is a folder. These are the agent fs routes, which follow a profile's SSH workspace, so this is the machine the tools ran on. The preview pane reads through the same family (ADR 0007), so an Output opens there.
- **Going to the message:** an Output keeps its `tool_call_id`. Live `tool.start` sends the same id as `tool_id`, and `session.resume` sends it on each tool row, so the chat's tool row carries it and "Go to the message" scrolls to it, opens it and focuses it.

## What this computer keeps

One versioned document, `hermes-chat.outputs` in webview local storage, kept apart by connection and profile (the same scope as projects and drafts). For each chat it holds the last activity it was read at, when it was read, why its discovery is partial, and its Outputs. For each Output it holds the path, how it was made, the tool, call id, stored row id, stored time, the size the tool reported, and the last availability check. It never holds file contents or chat text. It is capped at 1,000 Outputs per chat (the newest; the chat is labelled partial), 3,000 per profile, dropping the chats read longest ago first, and 200 added files per profile, and at the 8 most recently used connection-and-profile scopes. The caps apply to what the screen holds in memory as well as to what is saved. A chat whose Outputs are dropped for the profile cap keeps its entry, marked so, and isn't read again by a profile-wide run, so runs don't push each other's chats out round and round; showing that chat on its own reads it again. A chat's record, which says it was read, isn't dropped for space: dropping one would make runs read it again ahead of chats never read. Records are bounded by the profile's chat list instead, which this computer already keeps a copy of. Each time the shown profile's list is read from Hermes on this connection, and changes, the chats no longer in it (deleted, archived and not shown, or older than the list reaches) are forgotten, whether or not Outputs is open; one listed again is read again. Records of a profile not shown, or kept while the list can't be read (offline, or never read on this connection), stay until it is. A record with no Outputs serializes to roughly 110 to 200 bytes; one with Outputs adds about 200 to 400 bytes per Output. The caps bound counts, not bytes, so there's no fixed byte ceiling. Version 1 of the document (written before Outputs knew which machine a file is on) has its chats read again, keeping only the files the owner added. A storage that refuses the write leaves the index in memory and says so. Clear local cache doesn't remove it, since it holds no chat text, and Refresh rebuilds it.

## Identity, duplicates and versions

An Output's key is its chat, its tool call (or stored row, when there is no call id) and its path. Reading a chat again, after a reconnect or a restart, makes the same keys, so no card is added twice. The same path written by two calls is two Outputs, two versions. The screen numbers them by stored time, and only the newest is what the path holds now. The same path on the dashboard's machine and where the tools run is two files, not two versions. Previewing an older version shows the current file, and the screen says so.

## Concurrency

Each run and each check is numbered, and a newer one replaces the one under way. A profile switch or signing out lets go of that profile's index: its run, check or addition stops, whatever it reads afterwards is dropped and never saved, and a Refresh's check after its run never starts. So an index left behind can't overwrite what a newer one for the same profile saved. Every request names its profile, so a run left behind can't read another profile's rows. Opening Outputs or changing the scope starts a run for the chats that changed. A chat changing while Outputs is open, such as a reply streaming, waits for Refresh.

## Considered options

- **Scrape paths from replies and tool output, as the official desktop app does.** Rejected: it lists every path a reply mentions, and pip caches and log lines need special cases. The issue asks for confirmed outputs only.
- **Count `MEDIA:` lines in replies.** Rejected for now: the model writes them, and the gateway sends them on to Telegram or Discord, but nothing says the file was made in this chat. A `text_to_speech` result's `media_tag` is covered by its `file_path`.
- **Check every Output with the managed files routes (`GET /api/files`), which report size, modified time and type.** Rejected: they list the dashboard's own machine (ADR 0012), which for a profile with an SSH terminal backend isn't where its file tools wrote. They are used only for the files Hermes saves there itself.
- **Read every file's size with `read-text`.** Rejected: it reads up to 512 KB of each file just to learn its size.
- **Copy previews or files into local storage.** Rejected: storage is small and unencrypted. Only metadata is kept.
- **Download from Outputs.** Deferred to issue #94, which adds Download to the Server files screen (path, destination, progress, Cancel, overwrite confirmation). Outputs links to a file's folder in Server files and adds no transfer code of its own.

## Capability gap and backend design

Hermes has no stat route in the agent fs family. So an Output's size is only what its tool reported (`bytes_written`), and only `write_file` reports one; there's no modified time or type from the server. Proposed backend: `GET /api/fs/stat?path=&profile=` through the same `_fs_backend(profile)` and `_agent_fs_path` checks as `/api/fs/read-text`, answering `{exists, isDirectory, size, mtime, mimeType}`, with the same 403 for sensitive paths and 404 for none. A batch form (`POST /api/fs/stat` with up to 200 paths) would let Refresh check every Output in one request. A per-session artifact record written by the tools themselves (path, sha256, size, tool call) would make discovery exact and would also tell versions apart by content. Until then, the client works as above.

## Consequences

- Files made by `terminal`, `execute_code`, `browser_*`, MCP tools or delegated subagents aren't found. The owner can add them by path.
- "Show its folder in Server files" opens the dashboard's machine (ADR 0012). That is right for `host` Outputs. For a file tool's Output in a profile with an SSH terminal backend, the folder may not be there.
- A `host` Output can't be previewed past the Server files limits, and a file Hermes's managed root lock (`HERMES_DASHBOARD_FILES_ROOT`) puts out of reach shows as Not allowed.
- Missing can also mean that Hermes hides the name from `/api/fs/list` (credential files and folders such as `node_modules`). `write_file` refuses credential paths anyway.
- A chat with more than 2,000 stored rows has only its newest rows read, and is labelled partial.
- The profile scope reads 25 chats at a time. "Read more chats" reads the next 25.
