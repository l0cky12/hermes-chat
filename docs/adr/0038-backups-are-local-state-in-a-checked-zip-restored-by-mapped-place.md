# Backups are this computer's state in a checked zip, restored per category into places the owner maps

Reinstalling or moving to another computer lost drafts, queued messages, templates, tags, project membership and settings (#75). Hermes keeps chats, projects, folders, memory, persona, skills, scheduled jobs, toolsets and models on the server, so a new computer gets those just by signing in. What it doesn't get is what this app keeps on this computer only (README, What is stored where).

## Decisions

- **What a backup holds.** Eight categories, each read and written through the same checks as the store that owns it:
  - Settings (for the whole computer): the display, startup, model pick, favorites, status bar, screenshot shortcut and preview width fields of `hermes-ui-prefs`, the appearance (`hermes-chat.appearance`, custom themes included) and the terminal target. Not each profile's chat to reopen, which is a copy of the server's list.
  - Templates (for the whole computer). A project-scoped one names its place, so it is restored only with that place.
  - For each connection and profile: drafts, queued messages, project membership (the owner's grouping: which chats are in each project, the project the list shows and the projects last listed; never the membership sync's bookkeeping with Hermes, ADR 0109, which a restore keeps as stored), project defaults, tags and Saved filters, and branch origins (`links` only: the attempts whose answer was lost are settled against the server's list and mean nothing elsewhere).
- **What it never holds**, said in the export and restore dialogs and written into the manifest: passwords, extra header values and any other credential (they stay in the keyring), the sign-in itself, server data, Saved copies and cached lists, Failed messages, attachments and screenshots (a queued message keeps its text, its files are dropped and counted), unsaved persona edits, import history and inbox dismissals. There is no option to include credentials: the keyring is the only place they live (ADR 0003, ADR 0104).
- **Format: a plain zip of JSON.** `manifest.json` has `format: "hermes-chat-backup"`, `schema: 1`, the creation time, `places` (`p1`, `p2`… each a connection's mode, target and username with a profile), and for each category its file name, record count and SHA-256. Each category file is `{category, records: [{place?, key, value}]}`. Schema changes go through `MIGRATIONS` in `backup.ts`, one step per version; a newer schema is refused whole, saying to update.
- **The archive side is in Rust** (`backup.rs`). The webview never names a path: the Save and Open dialogs pick it, and the recovery backup goes in the app's data folder. Entries are stored, not compressed, so a zip bomb can't be smaller on disk than it reads. Reading refuses an archive over 32 MB, over 32 entries, an entry over 16 MB (read one byte past the limit, whatever its header says), any name that isn't a flat `name.json` of lower-case letters, digits and dashes (so no `..`, folder, absolute path or backslash), folders, symlinks, duplicates, compressed entries and non-UTF-8 text. The zip CRC catches a damaged entry; the manifest's SHA-256 catches a changed or swapped one. Nothing in an archive is run or written out as a file.
- **Validate whole, then preview.** Restore reads the manifest, checks every listed file's checksum and record count, and every record's place, before showing anything. Any failure refuses the whole backup with nothing written. A category this version doesn't know is listed and skipped. A value this version wouldn't keep as it is (a setting it would reset, a template it would drop) is skipped and counted.
- **Places are mapped, never guessed.** Every scoped record is for a place. A place goes to a profile of this computer's connection only when its connection is identical (mode, target, username) and the server lists the profile. Anything else waits for the owner to pick a profile or "Don't restore"; Restore stays disabled until every place is decided, and two places can't go to one profile. A remapped place rewrites every scope, including a template's project.
- **The archive side writes safely.** The temporary file beside the destination is created with O_EXCL and mode 0600, so a file or symlink already there is never opened; the finished file is renamed over the destination.
- **Policies per category.** Merge: what this computer lacks is added, what it has the same is left, and a conflict keeps this computer's, except where the two combine (project membership is the union of chats per project; branch origins the union of links). Replace: for the places restored, the category becomes the backup's, and what this computer has there that the backup doesn't is removed. Don't restore. The preview counts each case per category before anything is written. Templates keep one per name, so one whose name is taken here is skipped and counted.
- **A recovery backup first.** Before writing, a full backup of this computer's current state is saved to `$XDG_DATA_HOME/net.l0cky12.hermes-chat/backups/recovery-<ms>.zip`, mode 0600, the newest five kept. If it can't be saved, nothing is restored. It keeps every record as this computer stores it, without the checks an export applies (a queued message keeps its files' paths), so nothing a restore replaces or removes is missing from it. Archives are written with the reader's own limits, so a recovery backup is never one a restore would refuse.
- **Each category is written whole or not at all.** Each is read again and compared with what the preview planned over; if it changed meanwhile (a draft typed in another window, another instance's tags), it fails and nothing of it is written. localStorage categories delete first and then write, and if a write is refused (a full store) they undo in the order that needs no room: keys that weren't there go first, then the old values come back. If even that fails, the report says how many items couldn't be put back, and the recovery backup has them. Only the places restored are rewritten: every other scope in a document keeps its stored text, fields this version doesn't know included, and a key whose value this version can't read is left alone. Tags and project defaults go through their file's compare-and-swap (`defaults_file.rs`), so another instance's write in between fails the category instead of being overwritten. A document a newer app wrote is left alone. Once a profile's membership is Hermes's (moved there, ADR 0109), its chats here are Hermes's copy, so a restore that would change them fails the category instead. Restored project defaults take a revision past both, so an open project screen sees the change. Categories don't depend on each other, so one failing leaves the rest restored: the report says which.
- **Nothing restored is sent.** Restored queues are written paused, with a note to check and resume; the app also pauses every queue it loads after a restart (ADR 0018). Drafts are text in a composer.
- **The app reloads after a restore that wrote anything.** The stores keep what they read in memory, so the report's only way out is Reload, which signs in again from the keyring. So a restore waits while a reply runs or an Approval waits, in any profile the inbox can see, while a message is still being sent (its text is only in memory until its chat starts), and while a draft or queue couldn't be saved to this computer. This is asked again just before writing. A restore that wrote nothing leaves the app as it was.

## Considered options

- **A custom or encrypted format.** Rejected: the data is already in plain form on this computer, the owner keeps the file, and a zip of JSON can be inspected and checked with standard tools.
- **Including the sign-in, or the password behind an opt-in.** Rejected: the keyring is the only place credentials live, and restoring a sign-in would point the app at a server without Setup's test (ADR 0009). The owner sets up first, then restores.
- **Mapping by profile name across any connection.** Rejected: two servers can both have `default`, and the issue asks to map rather than guess.
- **One transaction across every category.** Not possible without a journal: localStorage and the two files have no shared transaction, and a crash between them can't be rolled back from the webview. Per-category atomic writes, the change check and the recovery backup are what this ships.
- **Server-side backup** (chats, memory, skills). Out of scope: Hermes has its own export; this app shows nothing it can't read back.

## Consequences

- A backup is personal data in plain form; the export says so.
- A backup made on one computer restores on another only after Setup there, and only into places the owner maps.
- Remote-server backup, Failed messages, attachments and persona edits stay out until separately supported. Saved connections (#88, PR #125) change how a connection is identified; when that lands, mapping should offer each saved connection, keyed by its stable id.
