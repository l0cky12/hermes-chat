# The memory map draws Hermes's learning graph read-only, and marks every link as stored or guessed

> **Proposed** (#98). Nothing here is built. The owner's answers to the open questions at the end decide whether and how it is built.

Issue #98 asks for a view of how remembered facts relate to projects, people and source chats, with provenance and timestamps, as a graph and an equivalent list. Selecting a fact should open its memory record. Relationships Hermes stores must look different from ones that are only suggested, and nothing inferred may be saved as a fact. Its blocker, the memory editor (#70), is built (ADR 0020, ADR 0040, and `0057-skills-memory-and-persona-show-any-profile-and-skills-move-between-profiles.md`).

## What Hermes offers

Read in the Hermes source at the deployed `f0d94882` (2026-11-02) and at upstream `28ad7672` (2026-11-07). The graph route, its answer's shape, the node routes and `tools/memory_tool.py` are the same at both. One difference: when it looks for skills, `f0d94882` skips only folders named `.archive`, `.hub`, `.locks`, `node_modules` or `.git` anywhere in the path. `28ad7672` skips `EXCLUDED_SKILL_DIRS` below the skills folder, which adds `.curator_backups`, `.venv`, `site-packages` and others. So on the deployed server a skill in a curator backup can show up as a learned skill.

- **`GET /api/learning/graph?profile=`** (`build_learning_graph` in `agent/learning_graph.py`). The app already reads it for memory entry ids (ADR 0057). It answers:
  - `nodes`. One node per memory entry, MEMORY.md's first, then USER.md's. Each has `kind: "memory"`, an id `memory:<memory|profile>:<index>:<fingerprint>`, `memorySource`, and a `label`. The label is the entry's first line without leading `#` and spaces, cut to 80 characters plus `…`. The id's index counts across both files (`learning_mutations._parse_memory_id`), so it is not the entry's place in its own file. The fingerprint is the first 12 hex digits of a SHA-256 of the entry's text.
  - Also one node per *learned* skill: `kind: "skill"`, with the skill's name as id and label, `category`, `useCount`, `state`, `createdBy` and `pinned`. A learned skill sits in the profile's own skills folder and has `created_by` of `agent` or `learn`, or a use count above 0. Loading a skill into a prompt counts as a use. External-folder skills are left out. Hermes reads the built-in skills first and skips a later skill with a name it has already seen, then drops the built-in ones. So a profile skill with a built-in skill's name is not in the graph.
  - `edges`, each a bare `{source, target}` with no kind. Two sorts come out of the code. **Skill to skill**: one of the two skills names the other in its `related_skills` front matter, and both are in the graph. The pair is stored as `(min, max)` by name, so `source` and `target` are alphabetical and don't say which SKILL.md named the other. This link is stored, in a SKILL.md. **Memory to skill**: for each entry, up to four skills with a score above 0 (`_memory_skill_edges`). The score is the count of shared tokens, runs of at least three letters or digits, between the skill's name and the entry's label and first 1,200 characters, plus 6 when the skill's name appears in that text. Hermes computes these on every request and stores them nowhere. They are guesses.
  - `memory`. One card per entry: `title`, `body` (the first 1,200 characters), `fingerprint` and `timestamp`.
  - `clusters` and `stats`: counts by category, and density figures such as `edges_per_node`, `isolated_pct` and `top_categories`. The map doesn't use them.
- **Timestamps.** A memory card's `timestamp` is its file's last change time, in whole seconds, plus the entry's place in that file. The first entry carries the file's time, and the fifth carries it plus 4 seconds. That spreads the entries out on Hermes's own timeline. It is not when any entry was written. When a file can't be read, its entries are left out of the graph. A skill's `timestamp` is the first of `last_activity_at`, `last_used_at`, `last_viewed_at`, `last_patched_at` and `created_at` that Hermes's usage record has, else the SKILL.md's change time.
- **`created_by` is not authorship.** `tools/skill_usage.py` calls it a curator opt-in flag, not proof of authorship. `curator adopt` sets it to `agent`, `/learn` sets `learn`, and a hub install sets `installed`.
- **No provenance and no entities.** The memory tool keeps no chat id, time or author with an entry. MEMORY.md and USER.md are plain text, with entries split by a line holding only `§`. No node or edge names a project, a person or a chat. The only origin Hermes records for a memory write is `foreground` or `background_review`, and only on a write it holds for approval (`tools/write_approval.py`, `current_origin`), never on the entry.
- **Size.** `memory_char_limit` (2,200) and `user_char_limit` (1,375) are defaults that a profile's config can raise, and short entries pack many to a file. Learned skills have no cap. The graph comes back whole, in one answer, with every entry's first 1,200 characters. It can't be paged.
- **Chats can be searched for words an entry holds.** `GET /api/sessions/search?q=&profile=` searches Hermes's full-text index of messages, and that index covers each message's `tool_calls` (`messages_fts` in `hermes_state_common.py`). The memory tool takes `add`, `patch` and `remove`, alone or in a batch of `operations`. `replace` is refused and writes nothing. A `patch`'s `content` is only the span that replaced `old_text`. Edits made from this app go through `PUT /api/learning/node` and leave no tool call at all. A search answers at most 100 chats (20 by default) and matches each word as a prefix.
- **External providers.** No dashboard route reads what Honcho or another provider stores, such as its peers or conclusions. ADR 0045 configures providers and shows none of their contents.

So the projects, people and source chats that #98 names don't exist on the server. Only memory entries, learned skills, one stored kind of link and one guessed kind do.

## Decision (proposed)

- **What it shows.** Settings → Memory gets a **Map** beside its entry editor, for the profile picked in the tab (ADR 0057). Map draws `GET /api/learning/graph` for that profile: memory entries and learned skills as nodes, and Hermes's edges between them. It shows nothing Hermes didn't send, and makes up no projects, people or chats.
- **One typed model, two views.** The answer is parsed once at the boundary into a model. The graph and the list both render from it, so a filter gives the same set in each:

  ```ts
  type MapNode =
    | { kind: "memory"; id: MemoryNodeId; file: MemorySource; positionInFile: number; label: string }
    | { kind: "skill"; name: SkillName; category: string; useCount: number; curatorMarker?: string; usageTime?: number };
  type MapLink =
    | { kind: "stored"; skills: readonly [SkillName, SkillName]; by: "related_skills" }
    | { kind: "guessed"; memory: MemoryNodeId; skill: SkillName; by: "hermes-word-overlap" };
  type MapFile = { file: MemorySource; lastChanged?: number };
  ```

  The kind of a link comes from the kinds of its two ends. Skill to skill is stored, as an unordered pair. Memory to skill is guessed. Any other edge, or one whose end isn't in `nodes`, is dropped and counted. If Hermes ever stores a memory-to-skill link, this rule shows it as guessed, which understates it and never overstates it. When Hermes adds a kind to its edges, the parser reads that kind instead. The app never runs Hermes's word scoring itself. `positionInFile` is counted from the order of each file's nodes, not from the id's index. `MapFile.lastChanged` is the timestamp of the file's first entry, which is the file's change time.
- **Stored and guessed look different.** A stored link is a solid line. Its row says "Related skills: one names the other in its SKILL.md". A guessed link is dashed. Its row says "Suggested by Hermes from shared words, not stored". Guessed links are off by default, behind a **Show suggestions** switch. Colour is never the only difference.
- **Provenance says what is known.** A memory entry's row and detail show its file by the editor's names, **Agent notes** or **User profile**, and its place in that file. The file's "Last changed" time shows once, at the head of each file's group, and is never shown as the time an entry was written. Each entry says "Source chat: Hermes doesn't record this". A skill shows its use count, its time labelled "Last recorded activity, or when its SKILL.md last changed", since the answer doesn't say which of the two Hermes used, and Hermes's `created_by` marker as it is, explained as the curator's marker and not who made the skill. Every label is shown as plain text, never rendered (ADR 0020).
- **Selecting a node.** A memory entry opens that entry in the Memory editor, with ADR 0020's checks and its question before leaving an unsaved edit. A skill opens Settings → Skills with its own profile picker set to the map's profile, then opens the skill (ADR 0030). Switching that picker goes through its usual question when Skills holds an unsaved edit. The map edits nothing itself.
- **Nothing derived is written.** Map sends no write. It has no "accept suggestion" control, because Hermes has nowhere to store a relationship. Nothing about the map is kept on this computer: memory text stays off disk (ADR 0020), and the model lives in the screen's state only.
- **Refresh.** Map reads the graph when it opens, on Reload, after the editor confirms a save or delete, and when the tab's profile changes. Each read is tied to the connection generation (ADR 0044) and to the profile picked in the tab. An answer is dropped if either has changed, because picking a profile in the tab opens no new connection. A refresh replaces the map only. It never touches the editor's unsaved text. An entry that is gone leaves the map. The editor's own read before its save finds the same thing and keeps the owner's text, as it does now.
- **Filtering, keyboard and motion.** The filter matches label, file, category and link kind, and the count reads "12 of 40". The list is the full keyboard surface. In the graph, Tab reaches the nodes in list order, arrow keys move to linked nodes, and Enter opens one. The walk keeps a visited set, so a cycle of related skills (A to B to C to A) never traps it. The layout is computed once, within a fixed number of steps, and is not animated. `prefers-reduced-motion` turns off zoom and pan easing.
- **Size and narrow windows.** Hermes can't page the graph, so incremental loading becomes a node limit in the app, set from measurement when it is built. Under the limit the whole graph is drawn. Over it, the graph shows the memory entries and the skills linked to them. If that is still over the limit, it shows the memory entries alone. If they are over it too, the graph is off and only the list shows. Each cut says how many nodes it left out. The list still has everything. A window too narrow for the graph shows only the list, with a note saying why. This is how #98's "large graphs load incrementally" is met. The download itself stays whole.
- **Duplicates and gaps.** Two entries with the same first line share a label. Their rows add the file and position ("Agent notes, entry 4"). Two entries with identical text share a fingerprint, so Hermes resolves both ids to the first one, and its next write to that file keeps only one (`_resolve_fingerprint`). The map shows both, and says that selecting either opens the first. A profile skill shadowed by a built-in skill's name isn't in the graph, and the map can't show it.
- **Unsupported.** A graph route that answers no such route (404 No such API endpoint, 405) puts `CapabilityGate`'s note over the Map view only. The entry editor keeps working, through the socket where it already falls back (ADR 0057). Map is a read, so it adds a read-only capability, `memoryMap`, with no connect-time probe, since the graph answer carries entry text and has no size cap. The capability is settled by the app's own reads of the route (ADR 0044's second source): the Map's, and the read the Memory editor already makes for entry ids. The reason the capability stores never quotes an answer. The capability gets its own section in `docs/compatibility.md`. The Rust relay gets no new write.

## Proposed Hermes changes

#98 asks for links Hermes doesn't have. The app can't make them real by itself. These Hermes changes would. Each is a proposal for upstream, not something this app can rely on until a build has it.

1. **A kind on every edge**: `edges[].kind` of `"related_skills"` or `"lexical"`, so clients read the difference instead of inferring it.
2. **Provenance per memory entry.** The memory tool records `{session_id, at, origin}` for each `add` and `patch`, in `memories/.provenance.json` keyed by fingerprint, written under the memory file lock. `PUT /api/learning/node` records the dashboard as the origin. The graph route returns this record on memory nodes. It drops a `session_id` whose chat was deleted, so a deleted chat never shows through the map.
3. **Entities as stored records.** Projects and people as records Hermes keeps, with memory-to-entity links the agent writes through a tool call that a person can see and refuse. Until then, the app shows no entities.

## Considered options

- **Extract people and projects from memory text in the app**, with a model or with rules. Rejected. The result is guesses about personal details. Hermes has nowhere to keep reviewed results, so the review would have to happen again on every open, and #98 forbids keeping inferred edges as facts.
- **Find each entry's source chat by searching its words.** Not in the default design. An entry made by one `add` can be found by searching its words and checking each chat found for a memory tool call whose `add` content equals the entry. An entry changed by a `patch`, or edited from this app or another dashboard client, has no call holding its whole text. A search also stops at 100 chats. So the result can only ever be "this chat added these exact words", and it fails silently for edited entries. This is open question 2.
- **Graph only, with no list.** Rejected. A graph can't be read with a screen reader or sorted, and #98 asks for list parity.
- **Hermes's own render** (`agent/learning_graph_render.py`). It draws the graph as terminal text for Hermes's TUI. It has no nodes to select.
- **A separate Memory map screen on the rail.** Rejected for now. The map is a view of the memory the Memory tab already picks a profile for and edits. A second place would need its own profile picker.
- **Ask Hermes in a chat to describe its memory.** Rejected, as in ADR 0020. The answer depends on the model and adds a turn to a chat.

## Consequences

- The map is honest about how little Hermes records: entries, learned skills, one stored link and one guessed link. It answers "which of my skills does this memory touch" but not "where did Hermes learn this".
- Storage scope: nothing on this computer, and nothing new on the server. It works on any profile with the profile-scoped learning routes (`f0d94882` and later). An older server shows the note on Map alone.
- Verification when built: tests against `fakeHermes.ts`'s graph route, extended with skill nodes and both edge sorts, for an omitted timestamp, two entries with the same label, two with identical text, an entry deleted between the graph and the editor, a cycle of related skills, a late answer for the previously picked profile, list and graph parity under each filter, keyboard reach of every node, a node count past the limit, and a refresh during an unsaved edit. Then the real app through the verify-hermes-chat skill against a throwaway `f0d94882` dashboard with synthetic memory and skills, and the existing chat, recovery, approval and profile-isolation tests. Nothing in this ADR has been run yet.

## Open questions

1. **Build this now, or wait for Hermes?** Built today, the map shows entries, learned skills and guessed links. It shows none of the projects, people or chats #98 names. Is that worth building, or should #98 wait for the Hermes changes above?
2. **Possible source chats.** Should an entry offer "Find chats that added these words", on demand for one entry at a time, labelled as a guess, and saying that edited entries can't be found this way?
3. **Skills on the map.** Should the map show learned skills, or memory entries only? Without skills there are no links at all.
4. **Upstream.** Should the Hermes changes above go to `NousResearch/hermes-agent` as an issue? That posts outside this repo, so it is the owner's call.
5. **Closing #98.** The pull request for this ADR says `Fixes #98`, as the owner asked, so merging it closes the issue though nothing is built. Keep that, or change it to `Refs #98` and keep the issue open for the build?
