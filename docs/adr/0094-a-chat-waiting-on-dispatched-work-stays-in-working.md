# A chat waiting on dispatched work stays in Working

Issue #287. A reply can hand work to another agent and end its turn: a kanban task (`kanban_create`) or background subagents (`delegate_task` in background mode). Hermes wakes the chat with a new turn when the work comes back, and that turn writes the real answer. Until now the chat counted as Working only while a reply ran, so it dropped into the Inbox as soon as the dispatching turn ended, as if it were finished.

## Decisions

- **Dispatched work keeps a chat in Working.** A chat is Working while a reply runs, or while it has dispatched work, and Hermes isn't waiting on the owner (`isWorking`). Its dispatched work is the kanban tasks created from it that are still outstanding, and its subagents that are queued or running after its reply ended. The chat leaves Working only when no reply runs and no dispatched work is outstanding. It then goes to the Inbox as new, as a finished reply does. If the wake turn dispatches more work, the chat stays in Working.
- **What each kanban status means is one table** (`dispatched.ts` `TASK_MEANS`). `triage`, `todo`, `scheduled`, `ready` and `running` are outstanding. `blocked` and `review` need the owner: the chat goes to the Inbox with the reason ("A dispatched task is blocked." or "…is waiting for review."). `done` and `archived` are over. A task the board no longer has, or whose board can't be read, is not outstanding: the app never keeps a chat in Working on a task it can't see. Hermes retries a crashed or timed-out task, which goes back to an outstanding status, so the chat keeps waiting.
- **Where the app learns it.** A `kanban_create` result in the chat adds the task at once, with no request. Each task the app tracks is read with `GET api/plugins/kanban/tasks/{id}?board=` every 30 seconds, and straight away when a `status.update` of kind `process` names it. The text only picks which task to read; the task's status decides. Every board is read (`GET api/plugins/kanban/board?board=`) when the app connects or switches profile, then every 5 minutes, and tasks whose `session_id` is one of the shown profile's chats are kept. A task is filed under the session id its chat had when the task was made, so it matches the chat's whole compression lineage (`_lineage_ids` from the chat list). Subagents come from the chat's Subagents tree (ADR 0072).
- **The kanban routes need nothing new.** On 2026-11-07 the live server (Hermes 0.22.6) served the kanban plugin under `api/plugins/kanban/`, answering 401 without the dashboard sign-in and 200 with the same session cookie the app already sends. The Rust relay already allows `GET` on any `api/` path.
- **A finished task holds the chat for 20 seconds, or until the wake turn starts.** Hermes checks for finished tasks every 5 seconds. Without the hold, a poll that saw `done` first would move the chat to the Inbox and straight back to Working when the wake turn began. The wake turn's start clears the finished task. With `subscribed: false`, a session that isn't live in the dashboard, or a reply the owner stopped, no wake turn comes, and the chat goes to the Inbox when the hold ends.
- **A task nobody ever started stops counting after 7 days.** The live board holds `todo` and `ready` tasks from months ago that no worker picked up. Counting them would pin old chats in Working for good. A `ready` task no worker has picked up after 10 minutes keeps the chat in Working, and its tooltip asks whether the Hermes gateway is running, since the dispatcher runs inside the gateway by default.
- **The row shows an hourglass.** A reply running shows the spinner, as before. Dispatched work with no reply running shows a still hourglass whose label says what it waits on ("Waiting on 1 dispatched task", "Waiting on 2 subagents", "Waiting on 1 task and 1 subagent"). There is no Unread dot while the chat waits.
- **Stop waiting** in the row's menu ignores the work outstanding at that moment, on this computer only, by its task and subagent ids (`hermes-chat.stop-waiting`, per connection and profile). The chat goes to the Inbox. A newer dispatch has new ids and counts again. Nothing is sent to Hermes, and nothing is cancelled there.
- **The Rail inbox and the Office.** A waiting chat is running work in the Rail inbox, with the summary "Hermes is waiting on work it handed off.", and has no Completed entry until the wake turn ends. A task that needs the owner is an entry that waits on the owner, with the reason as its summary. The Office shows the chat's reply desk as waiting, in the Workroom with its team.
- **Disconnected, the waiting state is as last seen.** The app makes no kanban requests while disconnected, and keeps the tasks it last saw, so no chat moves on stale data. Snoozed, Settled, Pinned and Archived chats stay where they are, as they do while a reply runs.

## Considered options

- **Reading every board every 30 seconds**, as the issue first proposed. The live default board is about 700 KB and isn't compressed. One small task read per tracked task does the same job between the slower board reads.
- **Hermes's live session list.** `session.active_list` reports the dispatching session as idle, and nothing in `session.info` mentions outstanding work.
- **Keeping dispatched work only for chats this app opened.** The board names each task's chat, so a restart or a chat started elsewhere is rebuilt from it at the cost of one board read per board.

## Consequences

- Background subagents count only for chats this connection has resumed, whose Subagents tree it holds. After a restart, a chat whose background subagents still run goes to the Inbox as before. Reading `subagent.roster` for the other chats is a follow-up.
- Background terminal processes started with `notify_on_complete` also wake a chat, and don't count yet.
- **ADR 0063**: Working now also holds a chat waiting on work it handed off. **ADR 0019**: the Rail inbox's running entries include those chats. **ADR 0077**: the Office has a waiting desk state.
