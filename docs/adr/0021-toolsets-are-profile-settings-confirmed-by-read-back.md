# Toolsets are the profile's setting on Hermes, changed one at a time and confirmed by read-back

> **Amended by [ADR 0169](0169-diagnostics-checks-toolset-switches-and-approval-answers-with-writes-that-change-nothing.md)** (#571). Diagnostics sends the same write check when it opens, so Toolset switches no longer waits for this screen to show Supported or Not supported. The rest of this ADR stands.

Settings → Toolsets shows and changes which toolsets Hermes offers the model in the profile shown, through the dashboard's own routes at `bf0203a` (`hermes_cli/web_routers/tools.py`): `GET /api/tools/toolsets?profile=` to read, `PUT /api/tools/toolsets/{name}?profile=` with `{"enabled": true|false}` to change one. The setting is the profile's `platform_toolsets.<platform>` in its config.yaml (`stt.enabled` for speech-to-text). For every toolset but the platform-restricted ones the platform is `cli`, which is what Hermes builds this app's chats with (`tui_gateway/agent_factory._load_enabled_toolsets`), and also the CLI's, the TUI's and the official desktop app's. Each change is checked against a fresh read first and reported as saved only when a read afterwards shows it.

## Considered options

- **Per-chat toolsets.** Rejected: Hermes has no per-chat toolset setting on the dashboard. The legacy socket's `tools.configure` writes the same `platform_toolsets.cli` and then rebuilds the chat's agent (`_reset_session_agent`), which would change a chat under a running reply and still change every other chat too.
- **Write the whole list with `PUT /api/config`.** Rejected: it merges a client's copy over the stored config, so a change made elsewhere between the read and the write would be lost, and it would bypass `_save_platform_tools`, which keeps MCP server entries and reconciles `agent.disabled_toolsets`. The toggle route changes one name under Hermes's config lock.
- **Keep toggles on this computer.** Rejected: Hermes would never see them. A switch that isn't on the server is no switch.
- **Trust a 200.** Rejected: Hermes can save a toolset on and still resolve it off (an `agent.disabled_toolsets` entry naming a composite such as `debugging` strips its tools). The read-back decides; the answer only adds the install Hermes started.

## Consequences

- The server has no revision or ETag for the toolset list, so "check, then write" leaves a short window in which another client's change to the same toolset can be overwritten. A change to a different toolset is never lost, since each write names one toolset and Hermes rewrites the list under its lock. One change is in flight at a time for the whole app: the queue belongs to the connection's toolset API, not the screen, so leaving and reopening Settings still shows it saving and waits for it, and a later change is checked against what the earlier one left.
- Whether the server takes changes is asked without changing anything: a `PUT` for a name no toolset has, with `enabled` that isn't a boolean. FastAPI answers 422 before the route runs; a server that took the body would still answer 400 for the name before reading the config. A server without the route answers its own 404 or 405, and the screen then shows each toolset's state without switches.
- The Rust relay passes only `PUT api/tools/toolsets/<name>` with exactly `{"enabled": bool}` (and that probe), not the same prefix's `env`, `provider`, `model` or `post-setup` routes, which write keys or run installs.
- Hermes's save clears the platform's `no_mcp` entry on any change (`_save_platform_tools`: "saving from the picker is consent"), so MCP servers turned off that way come back for new chats. Rust reads the profile's config and gives the webview only which platforms have `no_mcp` (and whether coding focus is on); the screen asks first, and says once read back that MCP servers are on again. When it can't read that, it says so and asks too. What the owner confirmed is checked again inside the write queue, right before the `PUT`; if another client set `no_mcp` meanwhile, or an install became due, nothing is sent and the owner is asked again.
- Turning a toolset on also removes its name from `agent.disabled_toolsets` (`_save_platform_tools`, #49995), the profile's list of toolsets off on every platform, so it comes back on Hermes's other platforms too. Rust also passes those names (toolset names only). A toolset named there is marked "Off on every platform", turning it on asks first, and the saved note says once read back that it left the list. Composite names there, which no switch undoes, are listed above the toolsets; a switch they override reads back as a mismatch. Hermes reads a list saved as a string with `ast.literal_eval`; Rust reads only plainly quoted names from one, and for anything else (escapes, other literal forms) says it can't be sure, so turning any toolset on says that and asks first. A platform's `platform_toolsets` entry saved as a string is read the same strict way for `no_mcp`; if it can't be read for certain, any change for that platform says so and asks first. Strings are stripped the way Python's `str.strip()` does, and a string Hermes wouldn't read as a list but that holds a `[` counts as unclear too. A save is said to have cleared `no_mcp` or the `agent.disabled_toolsets` entry only when the config read afterwards can tell.
- An error answer is classified by status: a 4xx is answered before Hermes writes, so it is a refusal; a lost answer or a 5xx stays unconfirmed unless the read afterwards shows the change, since the save may have gone in even when the effective state reads otherwise.
- Hermes's `configured` only checks keys. For the toolsets with providers, the screen also reads each one's provider readiness (`GET /api/tools/toolsets/{name}/config`) and marks the toolset Needs setup when a provider Hermes would use isn't ready (every active one: web's search and extract can each have their own) (for example Local Whisper without its package), or, with none active, when none is.
- Turning a toolset on can make Hermes start a background `hermes tools post-setup` install on the server. At `bf0203a` it does so only for `cua_driver` (Computer Use) while it isn't installed; the screen asks first in that case, asks too when it couldn't check, and reports `post_setup_started` afterwards. Other providers that report needing setup, such as web's `ddgs`, aren't installed by the toggle.
- A first change through Hermes's route saves the profile's whole resolved list explicitly, plus Hermes's own `known_builtin_toolsets` and `known_plugin_toolsets` bookkeeping; every other config field is kept. That is what `hermes tools` does too; how toolsets added by a later Hermes are treated then follows Hermes's own `known_builtin_toolsets` record.
- A change doesn't reach a chat Hermes already has open: agents keep the toolsets they were built with. The screen says so, and says when a reply is running in the profile.
- The list is the profile's default for new chats, not a guarantee of what each gets: `_load_enabled_toolsets` first honours a `HERMES_TUI_TOOLSETS` pin in the server's environment, which no route reports, and `agent.coding_context: focus`, which swaps in a coding selection in a code workspace. The screen names the pin always, and says when the profile has focus mode on.
