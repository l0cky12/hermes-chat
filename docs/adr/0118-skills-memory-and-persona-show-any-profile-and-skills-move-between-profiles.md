# Skills, Memory and Persona show any profile, and skills copy and move between profiles through Hermes's routes

Settings → Skills, Memory and Persona each showed only the profile the app shows. The owner wants to pick which profile each tab shows from a list in the tab, see all of that profile's skills, memory and SOUL.md, and, in an edit (Select) mode, pick several skills and copy, move or delete them, the same for memory, and to put one profile's persona on another. The deployed Hermes (`f0d94882`, research checkout `~/.cache/hermes-src-168`) has profile-scoped routes for each part, so the app uses those and never writes the server's files itself.

## Decisions

- **One picker per tab.** Skills and Memory (its built-in files) each show a profile list where the profile's name was: every profile `GET /api/profiles` lists, the app's own marked "(in use)". Each starts on the app's profile and goes back to it when the app switches profile. Picking another goes through the same question as changing tab (ADR 0020, 0030), so an unsaved edit is never dropped without asking. Persona uses its own picker, which ADR 0117 added while this was under way: it asks before picking another profile with an unsaved edit, and the question before leaving names the profile being edited. External memory already has its own per-profile list (ADR 0045) and is unchanged.
- **Copying a skill** is `POST /api/skills?profile=<to>` `{name, content, category}` (`_create_skill`). The name is the one SKILL.md's front matter declares, and the category is the one Hermes lists, so the copy lands where the original is. Hermes runs its own name, front matter, size and security checks, and refuses a name the target profile already has; that refusal is shown as Hermes words it. A name or category Hermes wouldn't take for a new skill (`VALID_NAME_RE`, such as a `DevOps` category folder) is refused before sending, rather than dropping the category and creating the copy at the top level. The copy is read back from the target (`GET /api/skills/content`) and counts only if it has exactly what was sent. A lost answer is settled by that read. **Only SKILL.md is copied**: Hermes has no route that copies a skill's folder, and the file routes are read-only here (ADR 0012), so files under `references/`, `templates/`, `scripts/` or `assets/` stay behind, and the question says so.
- **Deleting a skill archives it**: `DELETE /api/learning/node?profile=` `{id: <name>}` (`learning_mutations._delete_skill` → `skill_usage.archive_skill`). Hermes moves the folder to the profile's `skills/.archive/`; `hermes -p <profile> curator restore <name>` on the server brings it back, and the screen says so. Hermes archives only a profile's own (Local, `provenance: agent`) skills: it refuses Skills Hub, external-folder and pinned skills, and built-in ones unless `curator.prune_builtins` is set. Hermes finds the skill to archive by the name its front matter declares (`_find_skill_dir`), so a Local skill that the list names by its folder path, because two skills declare the same name, can't be archived either: sending the path finds nothing, and sending the shared name could archive the other one. The screen offers Move and Delete only for Local skills listed by their own name, says why the others are left out, and the app never sends a path to archive; Hermes's refusal is shown if it still refuses one. A name that starts `memory:` is never sent, since Hermes would read it as a memory entry. A deletion counts once the list read back no longer has the skill. The hub's uninstall route isn't used (ADR 0030).
- **Moving a skill** is a copy, then an archive of the original, only after the copy reads back from the target. A refused or unconfirmed copy leaves the original where it is; a copy that read back whose original couldn't be archived is reported as in both profiles.
- **A missing copy route doesn't hide Skills.** Diagnostics marks a capability unsupported when Hermes answers one of its writes with no such route (ADR 0044). The Skills capability owns only the edit and switch writes under `api/skills/`, not `POST api/skills`, so a server without the copy route still lists, switches and edits skills, and the copy's refusal is shown per skill.
- **One at a time, and said per skill.** Select mode works through the picked skills in order, each read back before the next, and then lists what became of each. Skills that went are unpicked; the rest stay picked to try again. The list is read again afterwards.
- **Memory for any profile.** `f0d94882` has the `learning.*` calls as profile-scoped REST: `GET /api/learning/graph?profile=` for the entries' ids, `GET /api/learning/node?id=&profile=` for one entry, `PUT` and `DELETE /api/learning/node?profile=` to edit or remove one, each through the same `agent.learning_mutations` under the memory tool's lock as the socket calls (ADR 0020). So the screen reads and edits any profile's memory with them, with the same checks and read-backs as before. On a server without these routes (their 404 or 405), it uses the socket calls, and only for the profile the dashboard runs as, as before.
- **Deleting several memory entries.** Picked entries are held by their text, as Hermes names an entry by it, since an entry's id also holds its position, which shifts as others go. Select mode removes the picked entries one at a time: each is left alone if its text is no longer in its file as read, Hermes refuses a stale id under its lock, and memory is read back once at the end to confirm which went. If Hermes's answer is lost, the rest aren't tried. **Memory entries can't be copied or moved** to another profile: Hermes has no call that adds an entry (ADR 0020), and writing the file directly would skip the lock. The screen says so and suggests asking Hermes in a chat on that profile.
- **Copying a persona.** Persona's routes already take any profile (ADR 0014), and Persona shows any profile (ADR 0117). "Copy to another profile" reads the target's SOUL.md first and asks before replacing it, showing both sizes. It copies the shown profile's SOUL.md as Hermes has it saved, read again just before, and refuses while there's an unsaved edit; starting to type drops the question. One write to a profile's SOUL.md at a time: the question waits for a save to the target still under way (an editor left while saving), and a copy isn't sent while one is. The write is the same check-then-write and read-back as a Save against the target's SOUL.md as just read, and what it replaced is kept under the target's Earlier versions on this computer. When Hermes may have written the copy but it can't be confirmed (the answer and the read-back both failed), the target's previous SOUL.md is kept there all the same, and the screen says the copy may have landed.
- **What reaches the server.** The Rust relay passes two more writes: `POST api/skills` with exactly `{name, content}` and optionally `category`, the name and category each one folder name as `VALID_NAME_RE` allows (`skill_create_allowed`), and `PUT api/learning/node` with exactly `{id, content}` where the id is a memory node (`memory:<memory|profile>:<index>:<12 hex digits>`, `memory_entry_edit_allowed`). A skill's id is its name, so skills are still edited only through `api/skills/content` with its checks. `DELETE` was already relayed for any `api/` path but the file routes.

## Considered options

- **Copy a skill's whole folder through the file routes.** Rejected: the file routes are read-only here (ADR 0012), and writing a skill's files that way skips Hermes's checks and its index cache.
- **Delete through the hub's uninstall, or `rm` over SSH.** Rejected: uninstall is for hub skills only, and a hard delete can't be undone. Archiving is Hermes's own reversible delete.
- **Copy memory entries by appending to the target's MEMORY.md through `/api/fs/write-text`.** Rejected, as in ADR 0020: no precondition and no memory lock, so an entry the agent wrote meanwhile could be lost. Hermes would need an "add entry" route (for example `POST /api/learning/node` `{source, content}` under `_mutate_memory`).
- **One Profile picker for all of Settings.** Rejected: the app's profile decides the chat list; picking what a Settings tab shows shouldn't switch it.

## Consequences

- Each tab can show and change any profile on the server without switching the app's profile.
- A copied skill's supporting files aren't copied; a moved skill's stay in the source profile's archive.
- Hermes checks a new skill harder than one already on disk: at `f0d94882` its front matter must parse as YAML and its description must fit the 60-character skill index. So a skill that works in its own profile, made earlier or by hand, can be refused as a copy (seen on the live check: a description with an unquoted colon, and one of 63 characters). The screen shows Hermes's reason, and a move then leaves the original where it is.
- Archived skills come back only from the server (`hermes curator restore`); Hermes Chat has no restore.
- On a server older than `f0d94882`, Memory shows only the served profile's memory, and Delete for skills says the server has no archive route.
- Verification: the tests use fakes of these routes (`fakeSkills.ts`, `fakeHermes.ts`), written from the `f0d94882` source. The same requests were sent to a throwaway `f0d94882` dashboard with synthetic data (2026-11-04): another profile's memory graph, entry read, edit and delete, each stale-id refusal and the unknown-profile 404; a skill copy with its category, its read-back and the duplicate-name refusal; and the archive of a Local skill and the refusal for a built-in one. Each answered as the fakes do.
