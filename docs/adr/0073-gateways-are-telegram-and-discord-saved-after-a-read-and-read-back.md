# Gateways are Telegram and Discord, saved after a read and read back

The owner wants to set up Hermes's Telegram and Discord gateways from the app: which are on, their bot tokens, who may talk to the bot, and whether it's connected (#104). The deployed Hermes (`f0d94882`, research checkout `~/.cache/hermes-src-168`, `hermes_cli/web_routers/messaging.py`) has three routes for this, each taking `?profile=`, so no Hermes change is needed:

- `GET /api/messaging/platforms` lists every platform Hermes knows. For each it gives `enabled`, `configured` (its required settings are there), `gateway_running`, a `state` (`disabled`, `not_configured`, `gateway_stopped`, `pending_restart`, `connected`, `fatal`, …) with the gateway's last `error_code` and `error_message`, and its settings (`env_vars`). A setting that holds a secret comes back only as a redacted preview, `«redacted:1234...abcd»`. An allowlist (`*_ALLOWED_USERS`) comes back as its value.
- `PUT /api/messaging/platforms/{id}` `{enabled, env, clear_env}` writes the profile's `.env` and `platforms.<id>.enabled` in config.yaml. Hermes checks the whole request before it writes anything: a key that isn't the platform's (400), a redacted preview sent back (400), and Telegram's token shape (400). It answers `{ok, platform, hot_served}`.
- `POST /api/messaging/platforms/{id}/test` reports the platform's state in words (`{ok, state, message}`). It sends no message.

## Decisions

- **Its own tab, Settings → Gateways**, after MCP servers, with a sub-nav of the platforms (Telegram, Discord) as General and Memory have, and each platform shown as a card of rows (ADR 0059): Status, Turned on, its settings in Hermes's order, Check status, and Save. Settings search names the tab and opens it, as for MCP servers, rather than mounting a form holding a typed token among the results.
- **Telegram and Discord only.** Hermes lists about 30 platforms. The others need flows this screen doesn't have (WhatsApp's QR pairing, webhooks with public URLs, OAuth apps), and the issue asked for these two. The list is filtered to them, in Hermes's order, and a Hermes that lists neither says so.
- **Any profile, from the same picker as Skills, Memory and MCP servers** (ADR 0118), starting on the profile in use. Every call names the profile in its query, and the screen is keyed by it, so an answer for a profile no longer shown is dropped. A bot (ADR 0066) is a profile, so this is where a bot's Telegram token goes.
- **A secret is write-only, and a row left alone keeps it.** A setting whose value Hermes doesn't send (every one but the allowlists) shows Hermes's preview, or "Not set". **Replace** opens an empty masked field; **Remove** marks it to be cleared; **Keep current** undoes either. Only Save sends anything. An empty Replace field is a keep, so an untouched or emptied field never clears a token. A value that looks like Hermes's preview pasted back is refused before sending. The token goes from the field into the `PUT` body and nowhere else: the screen never reads one back beyond Hermes's preview, never logs one, and drops what was typed once Hermes may have it (saved, or not confirmed). A refusal keeps the field, to fix and send again.
- **Save always sends `enabled`.** Hermes turns a platform on by itself when its token is saved and `enabled` was never written. Sending the switch as shown keeps a new token from turning a platform on, and Turned on is the only thing that does.
- **Hermes has no revision to check a save against, so the save reads first and reads again.** Before the `PUT`, the save reads the list and compares the platform with what the screen showed: `enabled`, and each setting's set/unset, preview and allowlist value. If any differ, nothing is sent; the screen shows what Hermes has now, keeps the owner's draft, and says to check it and save again. After the `PUT`, it reads again and calls the change saved only if the read shows all of it (the switch as sent, a replaced setting set, a removed one unset, an allowlist equal to what was typed). A 4xx changed nothing. A lost answer is settled by the read: saved if it shows the change, otherwise "Hermes didn't confirm it".
- **When the change takes effect is said.** Hermes's gateway reads the settings when it starts. A save while the profile's gateway runs says to restart it on the server, unless Hermes answers `hot_served` (a multiplexer that picked it up). The status row shows Hermes's state: Off, Needs setup, Gateway stopped (with Hermes's start command), Restart needed, Connected, Connecting, Retrying, Not connected. The app doesn't start or restart the gateway: Hermes has routes for it, but a restart drops every platform's connection and running work, and the issue asks not to.
- **Three problems read apart**, each with its kind first and Hermes's words after, redacted:
  - **Permission refused**: a 403 on a save, a check or a read (Hermes's config lock refusal, `config_refusal_http`), or Discord's `discord_intents_required` (the bot isn't allowed a privileged intent).
  - **Token turned down**: a 400 about a token on a save that sent one (Telegram's shape rule), a preview pasted back, or the gateway's `telegram_auth_error` / `discord_auth_error`.
  - **Missing on the server**: the gateway's `missing_dependency` (python-telegram-bot or discord.py isn't installed where Hermes runs), or its `adapter_unavailable` for a platform whose token is set, with Hermes's extra to install. Live at `f0d94882` with lazy installs off, Discord without discord.py reports `adapter_unavailable` ("check the plugin, dependencies, and credentials"), not `missing_dependency`: Hermes builds the adapter only once the library imports. With a token set, the library or the plugin is what's left.
- **Redaction.** Every text from Hermes on this screen (a refusal's `detail`, the gateway's `error_message`, the status check's `message`) has the secrets saves sent while the app runs, anything shaped like a Telegram or Discord bot token (inside Telegram's `/bot<token>/` URLs too), and what Logs redacts (ADR 0033) taken out before it's shown or kept. The API object keeps the last 50 secrets sent, in memory only, for this: an error read later can echo one that doesn't look like a token. A value shorter than 4 characters is taken out only where it stands alone.
- **Check status** is the `POST …/test` route: Hermes's state in words, and then the list read again so the status row and the problem's kind are current. It sends no message.
- **What the relay passes** (`transport::gateway_write`): `PUT api/messaging/platforms/{telegram|discord}` with a JSON object of only `enabled` (a bool), `env` (non-blank, one-line values of at most 4096 characters under that platform's own `TELEGRAM_…` or `DISCORD_…` names) and `clear_env` (those names); and `POST api/messaging/platforms/{telegram|discord}/test` with no body. No other messaging route, platform or key is relayed: not the WhatsApp or Telegram onboarding routes, and not `/api/gateway/*`.

## Considered options

- **The switch saves at once, as Toolsets' switches do.** Rejected: a token and the switch are often changed together, and two writes would need two conflict checks and could half-land. One Save sends both.
- **Check Telegram's token shape in the app.** Rejected: Hermes does, and says why; a copy of its rule here could refuse a token a newer Hermes accepts.
- **A Test message.** The issue asks for an optional message to a chosen destination. Hermes has no route that sends one (its test route only reports the state), so there is no button. It needs a Hermes route that takes a platform, a destination and a message, sends exactly that once, and answers with an id so a retry can't send it twice.
- **Every platform Hermes lists.** Rejected for now, above. The data shape doesn't depend on the platform, so adding one is a list entry plus whatever its setup needs.

## Consequences

- Telegram and Discord are set up for any profile from the app, with tokens that never come back to the screen.
- A change made by another client between the read before a save and the write is lost (Hermes's route has no precondition); the window is one request long, and the read after the write shows the result.
- A Hermes without `/api/messaging/platforms` (405, or FastAPI's own 404) shows "This Hermes server has no messaging gateway routes. Updating Hermes adds them."
- Verification: Rust tests of the relay rule (`relays_the_gateway_save_and_status_check`, `relays_no_other_gateway_write`), and tests of the API and the screen against FakeHermes's messaging routes (`fakeGateways.ts`), written from the `f0d94882` source. The real app was driven against a throwaway `f0d94882` dashboard with dummy tokens (2026-11-05): the list, a token Hermes refused by its shape, replace, a Discord token saved with the switch off (Hermes kept it off), the switch, a change made on the server meanwhile, remove while the gateway ran (restart needed), and Check status. With the gateway running, Telegram's own API turned the dummy token down (`telegram_auth_error`, after Hermes lazily installed python-telegram-bot), and Discord without discord.py, lazy installs off, read as missing on the server. A live bot connection was not run: it needs a real bot token and a Telegram or Discord account.
