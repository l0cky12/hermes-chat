# Diagnostics checks Toolset switches and Answering Approvals with writes that change nothing

> **Accepted** (#571, #572). It amends ADR 0044's "Nothing is written to find out" for two named requests, and ADR 0021's write check, which Diagnostics now sends too.

Connection diagnostics showed Toolset switches and Answering Approvals as "Unknown, not checked yet", and they stayed so until Settings → Toolsets opened or this app answered a real Approval. No read can check either: one is a `PUT` route, the other a JSON-RPC method that settles an Approval. The owner asked for Supported or Not supported on open, with no toolset changed and no Approval answered.

## Decisions

- **Two write checks, sent only while Diagnostics is open.** Opening Settings → Diagnostics sends them for whichever of the two this connection hasn't settled, and Check again sends both. The connection's own check, 2 seconds after it opens, still only reads, so a connection that never opens Diagnostics writes nothing to find out. Each check is a `WriteCheck` on its capability in `capabilities.ts`: what it sends, and how it reads Hermes's answer or failure. It starts from unknown, so a capability found missing earlier is checked again rather than refused here, and what it finds covers the whole capability, as Settings → Toolsets' own check does.
- **Toolset switches.** The request Settings → Toolsets already sends (ADR 0021): `PUT /api/tools/toolsets/__hermes_chat_probe__?profile=` with `{"enabled": "probe"}`. At Hermes `f0d94882`, `toggle_toolset` (`hermes_cli/web_routers/tools.py`) takes a `ToolsetToggle` body whose `enabled` is a bool, so FastAPI answers 422 before the route runs. A Hermes that took the body would refuse the unknown name with 400 before loading the config. Either is Supported. Hermes's own 404 or a 405 is Not supported. A 2xx is Unknown, since no Hermes should take it. The relay already lets exactly this body through (ADR 0021).
- **Answering Approvals.** `approval.respond` with `session_id` and `request_id` both `__hermes_chat_probe__`, and `choice: "deny"`. At Hermes `f0d94882`, `tui_gateway/methods_prompt.py` resolves the session with `_sess` (`tui_gateway/session_registry.py`), which finds no live session by that id, logs one warning ("session-scoped RPC rejected"), and fails 4001 "session not found". Its fallback, `_approval_respond_session_fallback`, then looks for a live session with a pending Approval under that request id, and for a live session stored under that session id. A made-up id matches neither, so it returns the 4001 before `resolve_gateway_approval` runs. Nothing is settled or changed. 4001 means Hermes has the method. JSON-RPC "method not found" is Not supported. A Hermes that answers `{resolved: 0}` without checking the session has the method too. The source at `bf0203a`, the build the owner deploys, isn't on this machine; FakeHermes models its `approval.respond`, which also fails 4001 for a session it doesn't have.
- **Turn isolation decides whether the method reaches the Approval.** With turn isolation (`dashboard.turn_isolation`), each turn runs in a compute-host child, and its Approvals wait there (`tui_gateway/compute_host_bridge.py`). The parent still has `approval.respond`, so the request above finds it, but an answer sent that way doesn't reach the waiting Approval. No request that changes nothing can tell the two apart, so the check also reads the profile's config, `GET /api/config?profile=`, alongside it. Hermes reads `dashboard.turn_isolation` with `is_truthy_value` (`tui_gateway/server.py`, `_load_dashboard_process_isolation_config`), and the check reads it the same way. On: Not supported, and the row says the app answers in reply to Hermes's request instead. While the row says Not supported, the app refuses `approval.respond` before sending it, so an answer goes only as that reply, which Hermes passes on to the child (#318, `settleApproval` in `transport.ts`). Off, or a config that doesn't name it (a Hermes from before turn isolation): Supported. A config that can't be read: Unknown, saying why, and the app keeps sending `approval.respond` and then the reply. A real Approval's answer marks the row Supported only when it settled something; `{resolved: 0}`, which turn isolation also gives, leaves the row as it was.
- **The probe name.** Both use `PROBE_NAME`, the name the app's other checks use where they must name something, so a log line on the server says where it came from.

## Considered options

- **Remove the two rows.** Rejected: the owner wants to know ahead of time whether the switches and shared answers work.
- **A Check button on each row.** Rejected: the owner asked for the answer on open, and Diagnostics is where the owner goes to find out.
- **Say Supported with turn isolation, with the caveat in the row's text.** Shipped first, then rejected in review: the badge claimed what the answer can't do there, and the caveat sat below it.
- **Send the checks on every connection.** Rejected: ADR 0044 keeps a connection to reads, and the answer matters only to someone looking at Diagnostics.

## Consequences

- Each time Diagnostics opens on a new connection, Hermes gets one refused `PUT`, one refused `approval.respond` and one read of the profile's config, and logs a "session-scoped RPC rejected" warning for the `approval.respond`. Only `dashboard.turn_isolation` is read from the config, and nothing of it is kept.
- The config is the profile's. Hermes reads `dashboard.turn_isolation` from the config of the session's profile, or the launch home's, so a session bound to another profile than the one connected may differ.
- A Hermes behind a gateway that blocks `PUT` shows Toolset switches as Not supported or Couldn't check, as a blocked read does today.
- If a later Hermes settles `approval.respond` without a session, a made-up request id still matches no Approval. If it ever answered a made-up request id by settling the oldest Approval, this check would answer it with deny. FakeHermes models that case for an empty request id only, and the check never sends one.
- Checked live on 2026-11-13 against a throwaway Hermes `f0d94882` dashboard with no real data (`src/hermes/capabilities.live.test.ts`): both rows showed Supported, Hermes wrote no `config.yaml`, and its logs held the one "session-scoped RPC rejected" warning for `approval.respond`. No Approval was waiting there, so that run shows the answer, and the source above shows a waiting one isn't reached.
