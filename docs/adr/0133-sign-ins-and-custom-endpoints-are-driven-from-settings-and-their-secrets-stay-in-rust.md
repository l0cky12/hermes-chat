# Sign-ins and custom endpoints are driven from Settings, and their secrets stay in Rust

> **Partly superseded by [ADR 0154](0154-a-preview-page-reaches-only-its-own-tunnel-and-runs-in-webkits-sandbox.md)** (#478). The relay now refuses `GET` on the two lists Rust reads, and drops credentials from `GET api/config`, so the consequence "The relay still passes any `GET` the window sends" no longer holds. The rest of this ADR stands.

The owner wants to set up every way a profile reaches its models from the app, not only API keys (#241). Settings → Providers already lists, adds and removes Provider keys (ADR 0095). The investigation on #241 found that the deployed Hermes (`bf0203a`) already has the routes for the other two parts: device-code sign-in to subscription providers (`hermes_cli/web_routers/oauth.py`) and OpenAI-compatible custom endpoints (`config_env.py`). No new server API is needed.

Two of those answers carry part of a secret. `GET /api/providers/oauth` puts a `token_preview` (the last characters of the token) in each provider's status, and `GET /api/providers/custom-endpoints` puts an `api_key_preview` in each endpoint. Saving an endpoint, and checking one first, sends its API key.

## Decisions

- **Two more sections in the Providers tab, below the keys.** Subscription sign-ins lists each provider Hermes knows, signed in or not. Custom endpoints lists the profile's endpoints, with a form to add one. Each section reads its own list, so a server without one of the routes still shows the other parts.
- **Rust reads both lists and drops the previews.** `hermes_provider_sign_ins` and `hermes_custom_endpoints` keep only what the screen shows: names, flow, signed in, whether Hermes can sign it out, the server command for an external provider, and an endpoint's address, model, whether it has a key and whether it is the default. No part of a token or key reaches the window. The app never calls `POST /api/env/reveal`.
- **Saving an endpoint is a Rust command that checks first.** `hermes_save_endpoint` checks the form, has Hermes probe the endpoint (`POST …/custom-endpoints/validate`), and saves it (`POST …/custom-endpoints?profile=`) with the models Hermes found, at the address that served them: Hermes tries the address typed and its `/v1` twin, and chat goes to the one saved. A blank model takes the first one found. A blank key is sent blank, so adding an endpoint again under a name Hermes has clears the old key, not sends it to the new address. A check that doesn't pass saves nothing and comes back as `checkFailed` with Hermes's reason, the key taken out. The owner can then press Add anyway, since an endpoint may list no models and still work. A failed answer to a request that carried the key isn't shown, as for keys. The relay still refuses `POST` to both routes, so this command is the only way the window can save an endpoint.
- **The writes without secrets go through the relay.** Starting a sign-in (`POST …/oauth/{id}/start`) and activating an endpoint (`POST …/custom-endpoints/{id}/activate`) are let through only with no body and one path segment of the right shape (`provider_account_write`). Polling, cancelling, signing out and removing an endpoint use the relay's existing `GET` and `DELETE`. Hermes answers a removal with the endpoints left, key previews and all, so the relay passes on only `{"ok":true}` for a `DELETE` under `api/providers/custom-endpoints/`. Activating does no more than Settings → Model's `POST api/model/set` already can.
- **A sign-in shows the code and opens the page.** Sign in asks Hermes for a device code, shows it, and opens Hermes's `verification_url` in the default browser (ADR 0082), with Open the page again in case the browser didn't come forward. The screen then long-polls Hermes (`wait=20`) until the sign-in leaves `pending`, at most once every 2 seconds against a Hermes that answers at once. Approved means only that Hermes says so: the screen reads the list again and shows signed in only if it says `logged_in`. Denied, expired and failed sign-ins say why. Cancel, and leaving the screen, cancel the sign-in on Hermes too, as Settings → MCP servers does, so Hermes can't finish one the owner gave up on. Since Hermes may have approved it before the cancel reached it, the screen then reads the list, and says so if it signed in after all.
- **Every change is confirmed by the list.** After signing out, activating or removing, the screen reads the list again, and the note says what the list shows, whatever the write answered. Hermes's 409 on sign-out (nothing stored) and 404 on removing an endpoint it no longer has are left to the list to settle.
- **Provider changes queue together.** Signing out and the endpoint writes join the per-profile queue the key changes use, and the model list is read again after each, so the model picker follows. A finished sign-in also reads the model list again.
- **`external` providers aren't driven.** `anthropic`, `claude-code`, `qwen-oauth` and `copilot-acp` have no sign-in route in Hermes. The screen shows the command to run on the server (`cli_command`). Groq isn't a chat provider in Hermes's catalog. It is added as a custom endpoint at `https://api.groq.com/openai/v1`.
- **The main model's own `base_url` row is left out.** Hermes lists it as `direct-config`, and its activate and remove routes answer 404 for it. Settings → Model shows it.

## Considered options

- **One Rust read for keys, sign-ins and endpoints together** (the investigation's `provider_accounts`). Rejected: the keys already load through `providerSetup()`, and one read would hide every part when one route fails.
- **A Rust command for every write.** Rejected: start, poll, cancel, sign-out, activate and remove carry nothing secret, and nine commands would add wiring without guarding anything. The relay check keeps the two `POST`s to their exact shape.
- **Reading the lists through the relay and dropping the previews in TypeScript.** Rejected: the previews would still reach the window.
- **Keeping a sign-in running after the screen closes**, so a code entered later still signs in. Rejected for now: it matches Settings → MCP servers, and the screen can't show the result once it's gone.

## Consequences

- A profile can be signed in to Nous Portal, ChatGPT or Codex, MiniMax and xAI Grok from the app, and an Ollama, LM Studio, vLLM or Groq endpoint can be added, made the default and removed.
- The relay still passes any `GET` the window sends, so a script in the window could read Hermes's own lists, previews and all. That is true of every `GET` route today. This ADR keeps the app's own code from doing so.
- See `docs/compatibility.md`, "Subscription sign-ins" and "Custom endpoints".
