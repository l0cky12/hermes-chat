# Transcript imports go through Hermes's own session import, are known by ids from the file, and are read-only here

Older command-line chats and exported chats can be brought into a profile (#86). Hermes at the deployed `bf0203a` already imports sessions: the dashboard's `POST /api/sessions/import` (`hermes_cli/web_routers/sessions.py`), which its own backups and `hermes sessions export` files go through. It takes session objects with their messages, checks all of them before writing any (`_validate_import_payload`), writes them in one transaction, and skips any id it already has. So the app imports through that route, and doesn't seed chats with `session.create`, which would make live sessions with an agent behind them.

## Decisions

- **Formats, versioned.** Two, chosen in the dialog, each read by its own parser:
  - **Hermes Chat Markdown export, version 1**: the file `exportChat.ts` writes (#25). It is recognised by its `# title` and its note `> Exported from Hermes Chat on YYYY-MM-DD HH:MM UTC.` Blocks are read from their header lines (`**You:**`, `**Hermes:**`, `**Hermes, thinking:**`, `**Tool:**`, `**Approval asked:**`), counted only outside code fences and after a blank line, as the exporter writes them. Thinking becomes the `reasoning` of the next assistant row. A tool call becomes an assistant row with one `tool_calls` entry (`import-call-N`) and a `tool` row with its output. An Approval has no place in Hermes's history, so it is left out and counted. The note naming a message's attachments stays in that message's words, since the names are all the file has. A later change to the export format needs a new version here, not a looser parser.
  - **Hermes session export (JSON or JSONL)**: what `hermes sessions export` writes (`render_sessions_export`, one session object per line), or a JSON array of them. A JSON file from this app's Export (ADR 0076) is one such session in a JSON array, so this parser reads it with its times; its `hermes_chat_export` notes are ignored, and its messages' `attachments` names are counted and not imported, since Hermes has no place for them. Only these session fields are kept: `id`, `title`, `model`, `started_at`, `ended_at`, `end_reason`. Only these message fields are kept: `role`, `content`, `timestamp`, `tool_calls`, `tool_call_id`, `tool_name`, `reasoning`, `reasoning_content`, `finish_reason`, `active`, `compacted`, `display_kind`. The rest isn't imported, and the preview names what mattered: token and cost totals (they would count in the profile's usage, ADR 0008), the working folder (another client continuing the chat would run there), the system prompt, model settings, parent links and platform ids.
- **Size limits are Hermes's own**, checked before sending so the owner hears why in plain words: a 25 MB file (also the Rust read limit, and the route's body limit), 500 chats, 10,000 messages in a chat and 50,000 in all, 5 MB per chat and 25 MB in all (`_IMPORT_MAX_*` in `hermes_state.py`).
- **Validate everything, then write once.** The whole file is parsed and checked first: valid JSON on every line, a session id that is a plain token (`[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}`, never a path), each id once, a role on every message, times Hermes accepts (`coerce_epoch`'s range), a code fence that closes, tool arguments that are JSON. A Markdown export has no end marker, so a cut-short one is caught by what the exporter always writes: a final line break, an `Output:` block or one of its fixed no-output notes after every tool call, and a command block and an outcome line in every Approval. A file cut exactly at the end of a block still reads as a shorter chat; its digest is different, so it never replaces the full one. Any failure stops the import with the line, and nothing is sent. Hermes checks every session again and answers 400 with each error, writing nothing; probed live with one bad session beside a good one, and the good one wasn't written.
- **Identity and duplicates.** A JSONL chat keeps its session id. A Markdown chat gets `YYYYMMDD_HHMMSS_<first 12 hex of the file's SHA-256>`, with the export's time, in the shape Hermes mints and its salvage recognises (`hermes_state_ids.py`). Re-reading a file gives the same ids. The server-side marker is the session row itself: Hermes skips an id it has (`skipped_ids`), so importing again never copies, from any computer. Before importing, the preview reads each id's `mutation-snapshot`, and the chat row for ones that exist, and shows "Already imported" or "Already in Hermes" (for a JSONL chat whose original is on this server). Only the ones Hermes doesn't have are sent. This computer also keeps a ledger, `hermes-chat.imports` in webview storage, per connection and profile: each file's digest, name, format, time, state (`started` or `done`) and the ids it made, at most 200 files per profile, never chat text. It drives "You imported this file on …" and "an import of this file started … and its outcome wasn't known". The server's skip is what prevents duplicates; the ledger only explains them. No sync engine.
- **Titles get "(imported …)".** Hermes keeps titles unique in a profile (`sessions.title` is UNIQUE), and its import doesn't de-duplicate them: one clash rolls back the whole import as 503 `storage_unavailable`. This was found live, importing a chat's own export beside it. So every imported chat's title is `<title> (imported <its session id>)`, which is unique because the id is. (A shorter suffix, the id's last six characters, was tried and dropped in review: two files can hold different ids ending alike under one title, and the second file would then fail every time.) The preview shows the titles as they will be, and says why.
- **The write is fenced like every session edit.** Hermes refuses an import without `request_id` and `expected_revision` (409 `client_upgrade_required`, probed). The fence is the first session's revision: its `mutation-snapshot` (`runtime_revision` 0 when it isn't there). A `revision_conflict` reads it again once. Hermes keeps a receipt per request id; the same request sent again answered with the first receipt (probed).
- **Read back, and recover from a lost answer.** After Hermes answers, every chat is read back (`mutation-snapshot`, then `GET /api/sessions/{id}`), and only chats Hermes has count as imported. One it said it imported but doesn't have is shown as such. If the answer is lost (a dropped connection, a timeout, anything but a 4xx), the same request is sent once more, with the same request id and revision. If the first was written, Hermes answers with its receipt, which says which chats it made and which it skipped. If not, this one is the import. If that answer is lost too, the read-back says how many of the chats Hermes has, but none is counted as made by this import, since one Hermes has may be from before. The summary offers Try again, which sends the same chats with a new request id; Hermes skips the ones it has, so nothing is copied. A 4xx is a refusal, and Hermes wrote nothing.
- **Provenance and the original export.** Every imported chat has `source = "import"`. Hermes stores that as given and treats it as local history that can be edited (`authorize_history`, `LEGACY_LOCAL_SOURCES | {'import'}`), so rename, pin, archive and read marks work as for a command-line chat. The original source of a JSONL chat (`cli`, `telegram`, …) shows in the preview. Hermes has no column for it, so it isn't kept. The original file isn't copied anywhere. The ledger keeps its digest and name, so the owner can match a chat to the file they kept.
- **Read-only here, and how to continue.** Hermes can resume an imported session, but a Markdown one holds only words, and a JSONL one is cut off from the platform and process it ran in. So this app treats every chat with Source `import` as a record. Its pane has no composer. A note in its place says it's read-only and to start a new chat to continue. It starts Settled. That is the read-back marker from the server, so it holds on every computer. A chat imported by Hermes's own CLI also has `source = import`, and is read-only here too.
- **Nothing a file names is touched.** The Rust command `import_pick_file` opens the native Open dialog and reads only the file picked: a regular file, at most 25 MB, UTF-8, with a byte order mark dropped. The webview never names a path. Attachment names, `file://` URLs in content parts, paths in tool arguments and folder fields stay text, or are dropped. No tool call is run. Nothing is uploaded.
- **The relay passes this one write.** The Rust relay allows `POST api/sessions/import` only with a JSON body whose `sessions` is a non-empty list of objects that each say `source: "import"` (`import_body_allowed`). The webview can't use the route to make a chat look as if it came from another platform.
- **Profiles.** Every request names the profile the preview was made in. Switching profile drops the preview with a message, so nothing goes to the wrong profile. A summary that arrives after a switch updates that profile's ledger and project, not the one now shown. Imported chats can go into one of the profile's projects, which is kept on this computer like any membership (ADR 0007).

## Checked live

On 2026-11-03, against a throwaway `hermes dashboard` from the deployed checkout `bf0203a` (`HERMES_HOME` under `/tmp`, password gate on `127.0.0.2`, never the owner's `~/.hermes`):

- `mutation-snapshot` of an id Hermes doesn't have: `{"exists": false, "runtime_revision": 0}`.
- No fence: 409 `client_upgrade_required`. Fenced at revision 0: `imported_ids` with the id, revision 1. The same request id again: the same receipt. A new request at revision 0: 409 `revision_conflict`.
- A new session and an existing one in one request: `imported_ids` the new one, `skipped_ids` the existing one.
- One session without a role beside a good one: 400 with `errors: [{index: 1, error: "messages[0].role must be a non-empty string", session_id: …}]`, and the good one's snapshot still `exists: false`.
- Importing the Markdown export of a chat into the profile that has it, under the same title: 503 `storage_unavailable`. `errors.log` had `sqlite3.IntegrityError: UNIQUE constraint failed: sessions.title` from `_import_session_row`, and nothing was written. The app read back, found none of the chats, and said nothing was imported. With the "(imported …)" title it imported.
- A profile that has never had a chat has no `state.db` yet. Hermes's reads, `mutation-snapshot` included, answer 503 `Session store is not initialized` for it (`_open_session_db_at_path` won't create a store on a browse), while the import's write creates it. So the app reads that answer as "no sessions, revision 0". With that, importing into a new throwaway profile worked, and a second run skipped both chats.
- A message without a `timestamp` is dated when it is imported (`_insert_message_rows`), which is why the parsers give every row one.
- Stored rows came back with their role, content, timestamp, `tool_calls` and `tool_name` as sent; the session row with `source: import`, title, model and `started_at`.
- `src/hermes/importTranscripts.live.test.ts` repeats this with real export files.

## Considered options

- **`session.create` with seeded `messages`.** Rejected: it makes a live session with an agent, stamps a source this app picks for chats it starts, and has no skip of ids Hermes has, so a retry would duplicate.
- **Keep imports on this computer only, as a local read-only viewer.** Rejected: other Hermes clients and computers wouldn't have them, search wouldn't find them, and the dedupe would depend on this computer's storage.
- **Make imported chats resumable.** Rejected for now. A JSONL export from Hermes is Hermes's own format, so continuing one is plausible. But a Markdown one isn't, and Hermes has no way to mark the difference, so the app can't tell them apart from another computer. Continuing means starting a new chat.
- **Per-chat checkboxes in the preview.** Not built: ids Hermes has are already left out, and a file can be split. Add them if partial imports of large files turn out to matter.

## Backend gaps

- **A read-only or provenance flag.** Hermes has no column to say a session came from a file, which file, or its original source, and nothing to stop another client from continuing it. Design: `sessions.import_origin` JSON (`{format, digest, original_source, original_id}`) written by `import_sessions`, and a `read_only` flag the gateway's `prompt.submit` honours.
- **A dry run.** The route can't check a payload without writing. Design: `POST /api/sessions/import?dry_run=1` answering the validation errors and which ids would be skipped.
- **Title clashes.** `import_sessions` inserts the title as given, so a title the profile already has fails the whole request with an IntegrityError that the route answers as 503 `storage_unavailable`, which reads as a storage fault. Design: de-duplicate titles as `set_session_title`'s callers do (a numbered suffix), or answer 409 `title_conflict` naming the session.
- **Deleted ids.** Hermes refuses the whole file if any of its ids was deleted on this server ("a deleted session is not restored"). The app can't see that in advance, so the refusal names it. Design: report those under `skipped_ids` with a reason instead.

## Consequences

- An imported Markdown chat's messages all carry the export time, and the chat says so. A JSONL chat keeps its times.
- Tool output is stored, but Hermes clients show it only for edit tools, as with any chat.
- Server versions other than `bf0203a` weren't tested. A dashboard without the route answers 404 or 405, and the import says this Hermes can't import transcripts.
