# Worktrees are made by the Repository helper and recorded beside the repository

> **Superseded by [ADR 0043](0043-worktrees-are-made-on-the-server-by-the-repository-helper-and-recorded-in-the-repository.md)** (#159). Its helper and screen were replaced. Worktrees it made, its `hermes-chat/worktrees.json` record and its `refs/hermes-chat/recovery/*` refs are left on the server as they are; the Repository screen lists those worktrees as not made by this app.

Parallel coding chats need their own working copies (#82). The Repository screen can now make a Git worktree of the server's repository on a branch of its own, run the repository's setup once, start a chat working in it, list the worktrees with their chats, changes and unpushed commits, and remove one only after a preview, with its changes kept first. Every Git operation runs on the server, in the repository the screen has open, through the Repository screen's helper over the owner's own ssh (ADR 0110). Nothing runs in a checkout on this computer.

## Why not the dashboard's worktree routes

Hermes at `f0d9488` (deployed, read on 2026-11-04) has `POST /api/git/worktree/add` and `/remove` (`hermes_cli/web_routers/git.py` over `hermes_cli/web_git.py`), made for the official desktop app. They can't meet the issue's rules:

- **Hermes removes idle trees there on its own.** `worktree_add` puts every tree in `<repo>/.worktrees/<slug>` and records the repository in the profile's `worktree_repos.json`. Hermes's six-hourly sweep (`cron/scheduler.py`, `_worktree_maintenance_repos` → `hermes_cli/worktree_ops.py` `_prune_stale_worktrees`) archives an idle tree in `.worktrees/` to `refs/hermes/archive/…` and removes it once it's past its age tier, dirty or not, unless a process is inside it. A quiet chat would make its worktree disposable, which the issue forbids.
- **The branch and folder aren't the ones previewed.** The branch name is rewritten (`_sanitize_branch` drops characters), the folder is the first free `slug`, `slug-2`, … (`_unique_dir`), and a repository folder that isn't one yet is `git init`ed with an empty commit (`_ensure_repo`).
- **It can change the source checkout.** `existingBranch` naming the default branch runs `git switch` in the repository's own checkout.
- **Removal has no ownership.** `worktree/remove` takes `force` and runs `git worktree remove --force`. Nothing records who made a worktree or which chats use it, and nothing keeps uncommitted work first.
- **Hooks and the owner's config are off,** as for the other dashboard Git routes (`noninteractive_git_env`, ADR 0110).
- **There is no setup.** Hermes's own worktrees copy `.worktreeinclude` entries (`_copy_worktree_includes`). The dashboard routes don't.

A Hermes route that took an exact folder outside `.worktrees/`, refused to rewrite names, never switched the source checkout, kept an owner and chat list, and removed only after keeping changes would be a better contract than ssh. That is the backend design this records as missing:

- `POST /api/git/worktree/plan {path, branch, newBranch, base}` → `{path, baseSha, setup[], stamp}`, changing nothing.
- `POST /api/git/worktree/add {path, id, branch, newBranch, base, stamp}`, idempotent by `id`, refusing a stale `stamp`, never under `.worktrees/`, and recording `{id, owner, chats[]}` in a per-repository store that the sweep never touches.
- `POST /api/git/worktree/attach|detach {path, id, session_id}` under the same lock as removal.
- `POST /api/git/worktree/remove {path, id, stamp}`, refusing while any chat is attached or the tree is protected, and writing `refs/…/recovery/…` before `git worktree remove`.

## What the helper does

The helper gets eleven new operations (`repo_worktrees_helper.py`; Rust `Request::Worktree*`). As before, the webview can ask only for these. Every value it sends is checked, and Git runs with argument lists the helper builds, never through a shell.

- **Where.** A worktree goes in `<parent>/<repo>.worktrees/<branch as a folder name>`, beside the repository's own checkout, never inside it. That keeps it out of Hermes's sweep. The preview shows the exact folder. A folder that's already there is never made over (`path-exists`), and a `.worktrees` parent that is a link is refused.
- **Names and refs.** A branch must pass `git check-ref-format`, mustn't start with `-`, and mustn't be `hermes/hermes-…` or `pr-…`: Hermes's sweep deletes those branches with `git branch -D` once no worktree has them (`_prune_orphaned_branches`), so a branch kept after a removal could be lost. A base must resolve to a commit (`rev-parse --verify --end-of-options <base>^{commit}`). A new branch must not exist, and an existing one must exist and not be checked out in another worktree.
- **Plan, then create.** `worktreePlan` changes nothing. It answers with the folder, the branch, the commit it starts at and its subject, the setup steps, the submodules at that commit (not checked out), and how many changes the open checkout has. Those changes stay there: a worktree starts from a commit, never from them. A stamp covers the folder, branch, commit and setup steps. `worktreeCreate` recomputes the plan and refuses as `stale` if the stamp differs. A new branch is made with `git worktree add --no-track -b <branch> -- <path> <commit>`, so a branch made from `origin/main` never tracks `main`. An existing branch is checked out as it is (`git worktree add -- <path> <branch>`). Hooks (post-checkout) run as Git runs them, and their output is shown. The worktree is then locked: `git worktree lock --reason "hermes-chat <id>"`. A locked worktree isn't pruned, and `git worktree remove` refuses it without `-f -f`.
- **A create whose answer was lost.** The screen makes the worktree's `id` (a UUID) before sending. The record is written as `creating` first, then the worktree is added and locked, then the record becomes `ready`. Sending the same request again finishes what's left, or answers with the worktree already made; it never makes a second. A lost answer (timeout, ssh failure) is never sent again on its own. The screen asks the server (`worktreeList`), carries on if the worktree is there, and otherwise offers **Finish making it** or **Try again** with the same `id`. A record left `creating` with no worktree is listed under Not finished, with Finish and Forget.
- **Setup.** The supported setup is the one Hermes itself gives its worktrees: the repository's `.worktreeinclude`, a list of ignored files a worktree needs (`.env`, `node_modules/`). Each entry is copied from the repository's own checkout if it's a file, or linked if it's a folder, as Hermes does. An entry Git doesn't ignore (`git check-ignore`) is part of the source and is skipped: source changes reach a worktree only through a commit. Entries outside the repository, or that link out of it, are skipped too. The steps are fixed when the worktree is made, shown in the preview, and run one request each, so the screen shows each one land. A step that's done is never run again. A failed step keeps its error and stops the run, and the worktree stays, with **Retry** (the failed step and those after it) and **Open** (the worktree in the Repository screen). A folder linked where `.gitignore` matches only a real folder (`node_modules/`) shows as untracked, and the step says so. Running commands (installing dependencies, say) isn't supported: Hermes has no setup contract to run, and a script from the repository would run with the SSH user's rights outside any approval.
- **Listing.** `worktreeList` gives every worktree of the repository (`git worktree list --porcelain`), with its record if Hermes Chat made it, its staged, changed, untracked and conflicted counts, and how many commits HEAD has that no remote-tracking branch has (as of the last fetch: the screen never fetches). It also lists records with no worktree (Not finished) and removed ones. Worktrees made elsewhere, and the repository's own checkout, are listed apart and never offered for removal.
- **Same server.** The Repository screen's SSH target can name another computer than the one Hermes runs on, and the same folder can exist on both. So before a chat starts in a worktree, and before Hermes is asked which chats work in one for a removal, Hermes reads the worktree's record (`GET /api/fs/read-text` of the path the helper gave) and must find this worktree in it, under its random id and at the same folder. If it can't, nothing starts and nothing is removed, and the screen says Hermes may be on another computer. Checked against the deployed Hermes, which reads the file under `.git/`.
- **Chats.** A chat started from a worktree is created by Hermes with `cwd` set to the worktree and `cwd_explicit`, and kept only if Hermes answers with that folder (ADR 0017). Then, before anything is sent, `worktreeAttach` records it on the server. The record holds the connection and profile (the app's project scope), the stored session id, and its first message as a title. If the record can't be written, the session is closed, nothing is sent, and the message goes back in the composer, so a chat never works in a worktree that doesn't know about it. If the profile or the connection changed while the record was written, the chat isn't kept either, and it's taken off the record again. Detach removes one, after the owner confirms. The chat keeps working in the folder; only the worktree stops counting it.
- **Removal.** `worktreeRemoval` changes nothing. It lists every changed and untracked file, the ignored files that would be deleted with the folder, and the commits no remote has. It also gives what stops a removal: protected, any chat recorded, another tool's lock, an operation in progress, conflicted files, a checked-out submodule, or any other Git repository nested in it, tracked, untracked or ignored, a bare one included (their own changes and commits aren't in this repository, so nothing here could keep them). Nested repositories are found by walking the folder without following links. A folder with more than 200,000 entries isn't walked through, and isn't removed from here. The screen adds the chats Hermes itself has working in the folder or under it, from any client (`GET /api/sessions?cwd_prefix=<folder>&archived=include`; Hermes stores a chat's folder with its first prompt). Archived ones are listed but don't block. If Hermes isn't connected, or doesn't answer, the removal is blocked, because a chat working there can't be ruled out. The screen asks Hermes again just before removing. `worktreeRemove` then, under the record's lock, checks the blockers and the preview's stamp again. The stamp covers HEAD, the branch, the lock, the index's own entries (so a `git add -p` that changes nothing else counts), and every file and folder in the worktree with its size, modification time and mode, ignored ones and those inside ignored folders included. So an ignored `.env` written after the preview, or an edit inside `node_modules/`, stops the removal too. If there are changes, it keeps them at `refs/hermes-chat/recovery/<id>/<time>`, created only if absent, and reads that back. What's staged is one commit on top of HEAD (only when it differs from HEAD), and the working tree, untracked files included, is another on top of that. Both go through copies of the index (`write-tree`, `git add -A` into `GIT_INDEX_FILE`, `commit-tree`), so the worktree's own index is never touched. A detached HEAD with commits no branch or remote has is kept at such a ref too. Then the blockers and the stamp are computed again: a file written or staged while the changes were kept, or a chat attached meanwhile, stops the removal, and what was kept stays in its ref, named in the record (`keptRefs`). Where the changes went is written to the record (`removing`) before the folder goes. Only then does it unlock and run `git worktree remove`, with `--force` only when there were changes and they were kept. The window left is between that last check and Git deleting the folder; nothing is attached then, and Hermes has no chat working there. The branch is never deleted, nothing is reset, and no recovery ref is ever deleted. If the removal fails, the worktree is locked again. A removal cut off after the folder went is listed as Not finished, and **Finish removal** records it as removed, with what it kept. One cut off before the folder went is shown on its card, and **Remove…** previews it again and carries on. A removal whose answer was lost isn't sent again; the list shows what the server has.
- **Restore.** A removed worktree can be made again at its folder, on the branch it was on, only if the branch is still at the commit it was at. Then the kept working tree is put back (`git restore --source <kept> --worktree -- .`) and, if one was kept, the staged commit becomes its index (`git read-tree`). Its setup steps that were done are to run again, since their ignored copies went with the folder. If the branch moved, or another worktree (another record's, or another tool's lock) is at the folder now, nothing is made and nothing there is touched, and the kept changes stay in their ref. A restore is `restoring` until it's done: one cut off or refused part way is listed with **Finish restoring**, which carries on from where it stopped.
- **Protect.** A protected worktree can't be removed until it's unprotected.

## Where the record is, and who can change it

The record is `$GIT_COMMON_DIR/hermes-chat/worktrees.json` on the server, beside the repository's own Git data: version 1, `{v, worktrees: {[id]: {id, path, branch, newBranch, base, baseSha, setup[], state, protected, chats[], createdAt, createdBy, removed}}}`. It's in no working tree, so it's never committed, and every computer and window that opens the repository sees the same one. Every change happens under an exclusive `flock` on `hermes-chat/worktrees.lock`, from reading the record to writing it, and is written to a private temporary file, fsynced, and renamed over the old one. So attaching a chat and removing the worktree can't interleave. A second task's chat attached after the first task's preview makes that removal refuse (`blocked`). Reads take no lock. A record written by a newer Hermes Chat (`v` > 1) is shown and never written. Removing the repository removes the record with it.

On this computer, `hermes-chat.chat-worktrees` (webview local storage, per connection and profile) remembers which chats were started here in which worktree, so the chat can show its branch and folder. It's only for showing; the server's record is what counts.

## Consequences

- **Server needs** are those of the Repository screen (ADR 0110): ssh without a prompt, `python3` 3.8+ and `git` 2.31+. `git worktree lock --reason` and `git restore` are both older than that. A bare repository is reported as unsupported. Without ssh to the server there are no worktrees. Starting a chat in one needs Hermes connected, and so does removing one.
- **The helper is sent compressed.** With the worktree operations, the helper in base64 was over Linux's 128 KiB limit for one argument (`MAX_ARG_STRLEN`), on this computer and in the server's shell. The constant command is now `python3 -I -c 'import base64,zlib;exec(zlib.decompress(base64.b64decode("…")))'`, about 36 KiB. It is still one constant string; nothing in it comes from the owner.
- **Hermes's own sweep** never sees these worktrees (they're outside `.worktrees/`), and never deletes their branches (the names it deletes are refused). `git worktree prune` skips them while they're locked.
- **Late answers.** The worktree list is numbered: an older read's answer is dropped. The panel is keyed by target, checkout and connection-and-profile, so an answer for another repository or profile never lands in the one shown. Dialogs drop answers that arrive after they close. The removal preview is read once per dialog (and on Preview again), never because the app redrew, and no preview's answer replaces a removal under way.
- **The chat's branch** is the worktree's branch as Git last listed it when the chat starts, not the one it was made on.
- **Ordinary folders are unchanged.** Project folders, project defaults and the Repository screen's other features work as before. A chat started for a worktree takes the worktree as its folder over a project's.
- **Not covered:** chats that work in a worktree but were started elsewhere, in another profile than the one shown, aren't seen by the Hermes check; they're blocked only if recorded. Submodules aren't checked out in a new worktree. Ignored files are deleted with the folder (listed first, and covered by the stamp). Recovery refs are never cleaned up by the app. A Hermes whose file routes refuse paths under `.git/` (a locked files root, say) can't show it's on the same server, so chats can't start in worktrees and worktrees can't be removed from here.
- **Reviewed** by Codex (`gpt-6.1-sol`, high) in up to three rounds; the findings and what was done about them are in the pull request.
- **Verification limits.** The helper is tested by running the exact remote command through `sh -c` against real repositories (`src-tauri/tests/worktrees.rs`). The screen is tested against a fake of Rust's command and the repo's FakeHermes (`src/ui/worktrees.test.tsx`, `src/ui/worktreeChat.test.tsx`). The running app was checked against a throwaway sshd on this machine, synthetic repositories and a throwaway Hermes dashboard (`docs/screenshots/worktrees/README.md`), not against another server.
