# A connection has ordered routes, tried in turn, each checked for the same server before the password goes

A saved connection (ADR 0049) had one way to reach its server: one SSH target or one URL. The owner's server is reachable on the LAN at home, over Tailscale away, and over SSH from anywhere. When the saved way failed, the app failed to connect, and keeping a second connection for the same server split its drafts, queues, outbox, projects and persona edits in two (issue #191).

## Decisions

- **One connection, several routes.** A connection keeps an ordered list of **routes** (`src/hermes/routes.ts`). Each is a LAN address, a Tailscale address, a web address (https://, such as one behind Cloudflare Access), or an SSH target. Routes can be added, removed, moved up and down, and turned off without being deleted. Everything keyed by the connection (ADR 0049) stays keyed by its id, so drafts, queues, chats and the sign-in are one whatever route is used.
- **Tried in order, first that works.** Connecting tries the routes that are on, one after another, and uses the first that reaches Hermes and signs in (`routedPipe`). With more than one route on, each step of each route has its own limit, so a route that answers and then stalls gives way to the next within that step's limit, not the whole attempt's 60 seconds (issue #269): 5 seconds for ssh to connect (`QUICK_REACH`, `tunnel::open_within`), for a web address's name lookup, and for the dashboard's status; 10 seconds each for the sign-in, the chat connection's ticket and the `/api/ws` connect (`transport::StepLimits`, `open_route`); and Hermes's `gateway.ready` keeps its 15 seconds. The 60 seconds stay the bound on the whole attempt over one route (`CONNECT_TIMEOUT`). A connection with one route keeps the long timeouts and its route's own error, so nothing about it changes. A wrong password or too many sign-ins ends the attempt at once: the same Hermes would say the same over any route, and trying more would only spend sign-in attempts. When every route fails, the error lists each route and why.
- **Drops move to the next route.** The transport reconnects a dropped connection through the same pipe opener, which starts from the top of the list. So a dropped connection comes back over the next route that works, the chat state kept in memory, and the queue and outbox go on as after any drop (ADR 0018).
- **Health.** A route that failed in the last two minutes is tried after the others (`RouteHealth`), so reconnecting after a drop doesn't wait on a route known to be down each time. It is still tried, last. When each route last failed is kept with the connection (`routeFailedAt` in `hermes-chat.connections`: route ids and times, nothing secret), so a route that failed just before the app closed is tried last on the next launch too (issue #269). A success, or the route answering again, clears it; a time kept for a route the connection no longer has is dropped.
- **Offline after a failed launch keeps trying.** When launch can't connect, the app shows what this computer saved (Connecting while the first try runs, ADR 0089) and tries again after 1, 2, 4, 8 and 16 seconds as after any drop. After those it stays Offline but tries again every 60 seconds while it is open, until it connects, or until Hermes turns the password down (issue #269). Retrying a dropped connection is unchanged: Offline after those five tries, until the owner reconnects.
- **Going back.** While on a later route, the earlier ones are checked every 90 seconds without the password (`hermes_reach`: the tunnel or address opens and `/api/status` answers as the same Hermes). When one answers, the connection is closed and opened again, which takes the preferred route, but only when nothing is under way: no reply running, no Approval waiting, no message sending or queued, no chat loading (`Hermes.reroute`). Otherwise it waits for the next check.
- **Same server, before the password.** Before signing in over any route, Rust reads the dashboard's public `GET /api/status` (`transport::read_server`). It must be a Hermes status (it carries `version` or `auth_required`), or the route is the **wrong server** and nothing is sent. Hermes's status also names its install (`install_id`). The app keeps a hash of it on the connection (`server`, `transport::server_id`) the first time a route reports one, and every route after that must reach the same install, or it is the wrong server and gets nothing. The install id itself is never kept (ADR 0044 drops it from diagnostics); only a SHA-256 of it, salted with a fixed label. A server that names no install (older Hermes) passes, as before. An SSH route's host key is checked by ssh itself, as ever. Only a connection with more than one route is held to an install: one with a single route connects as it always did, so reinstalling Hermes doesn't lock anyone out who never added a route. Every route, single or not, must still answer as a Hermes dashboard before it gets the password. The status read and the sign-in after it use one HTTP client per route attempt (`transport::client`), so the sign-in and its ticket reuse the connection the status read opened (#271). Only the client is shared: the status check still runs, and passes, before the password or token is sent. The WebSocket opens its own connection.
- **Trust this server.** A reinstalled Hermes has a new install id, so every route says wrong server. A route's Test, and the connection test in setup, then offer **Trust this server**, which forgets the id the connection knew; the next sign-in learns the new one.
- **Plain http only on a LAN or Tailscale.** A plain http:// route is refused unless its host is, or resolves only to, this computer, a private or link-local range, or Tailscale (fd7a:115c:a1e0::/48 within fc00::/7, or 100.64.0.0/10 when this computer reaches it over Tailscale, ADR 0004) (`transport::check_plain_http`). This applies to every connection, including one made before routes: a plain http:// address on the public internet would send the password in the clear.
- **Secrets.** The username and password belong to the connection. A connection with several routes saves its password with the username and every route it was typed for (`{"v":2,"username":…,"routes":[…],"password":…}`). A route added later whose secrets the keyring couldn't save is **locked**: connecting with the saved password skips it until the password is typed again. Extra request headers belong to the web address that needs them, saved with its URL (`{"v":2,"routes":[{"url":…,"headers":[…]}]}`), and are given back only for that URL. A connection with one route saves both in the form it always had, so an older version still reads them.
- **Stored.** A connection keeps `routes` (id, kind, target, off) and `server` in `hermes-chat.connections` only once it has more than one route or a route of a kind its address alone wouldn't say. Its SSH-or-URL address is always its first route's, so everything that names a connection by its address (backups, chat links) keeps working. A connection from before has no list; its one route is its address.
- **Setup.** The Server step lists the routes. Each has a kind, an address (completed with http:// or https:// and port 9119 when left out), Test, up, down, Use and Remove, and its extra request headers when it is an address. Test reaches the route without the password and says reached, timed out, refused, wrong server or unreachable. The Sign in step's Test connection tests every route that is on with the password, in order, and says how each went, sign-in failed included. Save and connect needs one to work.
- **Seeing it.** With more than one route, the rail's connection tip says "Home server · via Tailscale", and Settings → Connection in use says which route and whether it is a fallback. The sign-in screen shows the routes in order instead of the address fields; they are changed in setup.
- **SSH for the rest.** The Terminal, the Repository screen and the Preview's server pages use the connection's first SSH route that is on, whatever route the chat connection uses (`sshRouteOf`, the `sshRoute` Rust keeps for server pages). Without an SSH route they fall back as before (ADR 0055).

## Considered options

- **Try every route at once and take the first preferred one that answers.** Not done: Rust holds one connection, and racing several sign-ins would send the password over every route at once. The short per-route timeouts keep a dead first route to a few seconds.
- **Separate connections for each route, grouped.** Rejected: it is what the owner had to do, and it splits the local data the issue wants kept together.
- **Trust a route because the owner added it.** Rejected as the only check: a LAN address is a different machine on another network, and the app connects on its own. The status check catches that before the password goes.
- **Pin each route to the addresses it resolved to.** Not done: Rust checks a plain http:// name's resolved addresses, but reqwest resolves again for the sign-in. A name whose DNS an attacker controls could answer differently the second time.

## Consequences

- The install id is public: anyone who can answer at a route's address and has read the real server's `/api/status` can claim to be it. The check stops the common case (another machine, another Hermes, a router's page), not a deliberate impostor on an unencrypted route. Use SSH, Tailscale or https:// where that matters; plain http:// LAN routes stay Unsecure.
- A route's Test without the password can't tell a wrong password; the Sign in step's test does.
- A connection whose every route is turned off can't connect; setup keeps at least one on.
- Health is saved with the connection, so it outlives a restart; it holds route ids and failure times only. The preferred-route checks are per run of the app.
- The step limits are fixed, not measured: a route slower than 10 seconds to sign in, on a connection with several routes, gives way to the next, though the whole attempt could have waited. A connection with one route still waits.
