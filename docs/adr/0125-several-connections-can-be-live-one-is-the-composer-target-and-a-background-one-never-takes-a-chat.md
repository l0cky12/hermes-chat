# Several connections can be live, one is the composer target, and a background one never takes a chat

**Status: proposed (issue #99). Nothing is built yet.** This ADR is design only. It would amend ADR 0112's "one is in use at a time", and touch ADR 0018 (queues) and ADR 0019 (the inbox). The open questions at the end need the owner before implementation starts.

To see work on another saved connection today, the owner switches to it. The switch closes the connection in use (ADR 0112), and Rust holds only one (`AppState`'s `Mutex<Option<Connection>>`, `src-tauri/src/lib.rs:159`). The server then parks the chats that connection had open, and reaps them 20 seconds later (`ws_orphan_reap_grace_s`). An Approval on the server the owner left can't reach this app until they switch back. Issue #99 asks for several connections live at once, each with its own status, and one composer target.

## What the server allows

A client receives a chat's events (`message.*`, `tool.*`) and its server requests only after it attaches to the chat with `session.resume` or `session.activate`. Across chats the server pushes only `sessions.changed`, with no payload. The one cheap read of what is running or waiting is `session.active_list`, which the client has to ask for. Its `waiting` means the chat has any server request open: an Approval, a clarify, a sudo or secret prompt, or a window-owned read.

What attaching does depends on the Hermes version:

- **Hermes 0.21.6 and later share a chat.** Since `de25545dce` (2026-09-07, first in release tag `v0.21.6`), attaching adds the client to the chat's `FanoutTransport`. Every attached client receives every frame, and every attached client that answers requests receives every server request. The first response settles the request, and that includes an error response. A chat with at least one client still attached is neither parked nor reaped. The owner's server runs `bf0203a` (2026-10-22), which has this. Some canary builds before 0.21.6 have it too. The app treats every version before 0.21.6 as moving a chat, which is the safe direction.
- **Older Hermes moves a chat.** Before fan-out, a chat had one transport, and attaching took the chat, with its stream and Approvals, from the client that held it. ADR 0019 refuses to resume chats for the inbox for this reason.

Three facts follow, and they constrain any client that attaches beside another:

- **An error answer ends the request for everyone.** The app answers every server request it can't show with -32601 today (`transport.ts`, `onServerRequest`). Hermes settles the request on that error, so a clarify the official app would have shown fails there too. Only code 4404 (`NOT_SHOWN_CODE`) on a window-owned request (`preview.read`, `preview.act`, `terminal.read`, `window.read`, `tour`) counts as one client declining, and only when the server's answer to `client.capabilities` says `declines_not_shown: true`.
- **Only `approval.respond` clears the other clients' cards.** Hermes withdraws an Approval with `request.cancel` when its approval queue settles it while the request is still open (`_emit_approval_request` in `tui_gateway/server.py`, `register_gateway_settle` in `tools/approval.py`). `approval.respond` settles it that way. A JSON-RPC response frame, which this app and the official desktop app both send today, removes the request before the queue settles it, so no `request.cancel` goes out and the other clients' cards stay up.
- **A client can't leave one chat.** On the dashboard's `/api/ws`, `session.close` ends the chat for every client, and a client's attachments end only when its socket closes. The canonical gateway protocol has `session.detach {session_id, subscription_id}` (`gateway/session_controls.py`), which the app doesn't speak (`docs/compatibility.md`).

So a background connection may attach only where that takes nothing from anyone, must not answer what it doesn't show, and must attach sparingly.

## Decisions

- **Live connections.** A saved connection (ADR 0112) is either idle or **live**. A live connection has its own socket, sign-in, route (ADR 0120), keyring entries, cache and reconnect loop. Connect and Disconnect are explicit controls on each saved connection in the rail's connection menu and in Settings → General → Connections. Connecting a connection is how the owner selects it for background watching. There is no separate watch toggle.
- **One composer target.** At most one live connection is the **composer target**. Only removing the target, or signing out of it, leaves none. The composer, voice, Server files, Settings and slash commands act on it. Every other live connection is a **background connection**. Switching the target is a pointer change. It closes nothing, reconnects nothing, and keeps the panes and the inbox's seen state of the connection the owner leaves. Today's switch remounts `Main` (`src/App.tsx`, `<Main key={connections}>`) and drops that state. A per-connection workspace map replaces the remount. ADR 0112's prompt before switching away ("something is under way") is no longer needed for a target switch, because nothing closes. It stays for Disconnect and for removal.
- **Rust holds a map.** `AppState`'s single slot becomes a map from the connection id to a live entry. The id is validated as `saved_password::account` already validates it (8 to 64 of `[a-z0-9-]`). `hermes_connect` returns a `Handle { id, gen }`, and every command that reaches the server names that handle: `hermes_send`, `hermes_request`, `hermes_send_file`, `hermes_get_limited`, `hermes_disconnect`, `token_keep`, `preview_server_open`, `display_open`, and every `dashboard()` user (speech, MCP, Files). A handle whose `gen` is older than the entry's gets `Closed`. So a late call from a connection that was closed and opened again never reaches the new one. The map is locked only to insert or replace an entry, never for a whole connect. Today the one slot stays locked for up to 60 seconds while a connect runs, and every command waits behind it.
- **Teardown is per connection.** Transfers, upload picks and screen sockets each use one global epoch today, bumped by any connect or disconnect (`lib.rs:246`, `:613`). They move into the live entry and end with its handle. Server pages are keyed by handle. `close_other_targets` becomes "close this connection's pages", so connecting B never closes A's pages, downloads or screen. Pages and screens stay open, labelled with their server, until they or their connection close.
- **Events carry identity by channel.** Each `hermes_connect` already gets its own Tauri `Channel<PipeEvent>`, owned by the one `Hermes` instance that dialled (`src/hermes/tauriPipe.ts`). Frames need no connection id. Rust gains a `closed` event when it drops a pipe itself, so the webview hears about every close. Today `Pipe::drop` aborts the task without one.
- **One `Hermes` per live connection.** `Hermes` (`src/hermes/transport.ts`) stays what it is now: one connection and one shown profile, with bare chat ids inside. It gains `readonly connection` and a role, `target` or `background`. A registry holds the live instances by connection id and the target pointer. Sign-in, Disconnect and removal run one after another per connection (`serial.ts` becomes one runner per id). Different connections never wait on each other.
- **Outside an instance, nothing names a chat by id alone.** A `ChatRef` is `{ connection, profile, chatId }`. Panes, inbox entries, focus requests, desktop notifications, chat links, the queue's drag state and Approval answers carry a `ChatRef`. The registry resolves it to the instance, then the instance uses the bare id. An Approval answer goes out on the socket of the instance that received the request, because request ids are unique only per socket.
- **What a background connection watches.** It keeps its socket and pings every 15 seconds. It reads `session.active_list` every 60 seconds and the other profiles' Unread pages every 120 seconds. These are new background intervals. The target keeps the timers it has today (`CHECK_EVERY_MS`, `INBOX_CHECK_EVERY_MS`, `LIVE_MIN_GAP_MS`). Across all background connections, at most 4 reads and attaches run at once, and each connection's timers are offset so they don't all fire together. Nothing polls while a connection is Offline. It also stays attached to the chats it held while it was the target, so their frames and Approvals keep arriving.
- **What a background connection attaches to.** On a server that shares chats (0.21.6 and later), it attaches to each chat that `session.active_list` reports as **waiting**, so an Approval card arrives with its content. It attaches with `session.activate {session_id, omit_messages: true}` on the row's live session id. That call isn't on Hermes's slow-handler pool. It returns the chat's open requests and no transcript. The transcript loads when the owner opens the chat. The entry goes under the profile the inbox's lookup found for the row (ADR 0019). A row whose profile isn't found isn't attached. A running chat that isn't waiting is shown as a count, not attached. On an older server it attaches to nothing new, because attaching would take the chat. There, a waiting chat it doesn't hold shows as waiting with no card, as other profiles' chats show today.
- **The attach bound.** A background connection attaches to at most 10 chats beyond the ones it held as the target. It can't leave a chat it no longer needs (see above), so at the bound it attaches to no more. Further waiting chats show as waiting with no card until its socket closes, on a drop or a Disconnect.
- **What a background connection never does.** It never sends a message, branches, searches or drains a queue, and never sends `session.create` or `session.close`. `Hermes` refuses these calls in the background role ("Make this server the target to work in it"), so the rule is enforced in the instance, not only in the UI. It shows Approval cards and answers no other server request. It declines a window-owned request with code 4404 only when the server says `declines_not_shown: true`. Every other request it leaves unanswered, so a client that shows it can answer it.
- **Reconnecting.** After a drop, a background connection attaches again to the chats `resumeOnReconnect` keeps today: those it held at the drop that were running a reply or had a card waiting. Without this, its held Approval cards would be lost, and the server would interrupt the owner's running reply once its turn sat idle for 600 seconds (`ws_orphan_activity_stale_s`). On a sharing server it then attaches to the waiting chats as above, within the bound. A drop on one connection changes nothing on another one: not its socket, its retry timers, its drafts, its queues or its chats.
- **Approvals.** An Approval on a background connection gets a Rail inbox entry and a desktop notification, both with the server's name ("Hermes on Work server is asking for approval"). The owner answers in the chat. Opening the chat makes its connection the target. The chat is still attached, so the card is still live. The inbox itself never answers (ADR 0019). The answer goes with `approval.respond`, so the card goes from every other client. When another client answers first, the card and the entry go on `request.cancel` if Hermes sends one. A client that answers with a response frame sends none, so a card also goes when `session.active_list` no longer reports its chat as waiting, or when the chat's next frames show the turn moved on.
- **Queues and the outbox.** A background connection's queues pause, and its outbox doesn't send. ADR 0018's "the chat's profile is shown" becomes "the chat's connection is the target and its profile is shown". When the connection becomes the target again, its queues load paused as they do after a switch today.
- **Server identity everywhere.** The chat header, Rail inbox entries, Approval cards, notifications, Preview pages, the Screen and the subagent tree show the connection's name with the profile whenever more than one connection is live. With one live connection the screens look as they do today.
- **Connection overview.** Settings → General → Connections gains a live view. For each live connection it shows the status (connecting, connected, reconnecting, offline, needs sign-in), the route in use, the last activity, and the counts of waiting, running, failed and unread work. The last activity is the newest `last_active` from `session.active_list`, or the last frame on the socket. The rail's connection button shows the same counts, summed, and marks any connection that is not connected. The tray badge is the sum across live connections.
- **The limit.** The owner sets the number of live connections, from 1 to 8. The default is 3. Rust refuses a ninth whatever the setting. At the limit, Connect is refused with the live connections listed, each with Disconnect. Nothing is closed to make room, because a silent close drops the Approvals of every chat that connection holds. Lowering the limit closes nothing. It applies to the next Connect.
- **One live connection per Hermes install.** Two of the owner's connections to one server would show every Approval twice, and on an older server they would take chats from each other. Connect is refused when another live connection has the same install hash (`server`, ADR 0120). A Hermes that names no install can't be checked. The app warns and allows it.
- **Storage.** `hermes-chat.connections` gains `live` (the ids to reopen at launch, in order) and `liveLimit`. `current` keeps its name and now means the composer target. Everything else already lives under the connection's scope (ADR 0112), so no drafts, queues, chats or keyring entries move. The connection migrated from before saved connections has an id like any other, so it is a key in the Rust map like any other. Only its keyring account name differs, as now. The restart snapshot (ADR 0060) holds every live connection's queues and drafts.
- **Launch and quit.** Launch opens the composer target first, as ADR 0089 describes. Then it opens the rest of `live` one at a time, with saved passwords only. A connection that needs a password shows **needs sign-in** and never opens a prompt by itself. Quit closes every connection. The server keeps running replies going, as it does today.
- **Removal while live.** Removing a live connection asks first, as ADR 0112 describes, and names what is under way on it. Then it disconnects that connection only. Then it follows ADR 0112's order: keyring entries first, then the local data. If the removed connection was the composer target, no connection is the target. The sign-in screen lists the live connections first, and picks none.

## Capability gaps in Hermes, and a proposed backend design

The design above works with the server as it is. These additions would remove its limits. None of them exist in the Hermes source read for this ADR (`~/.hermes/hermes-agent` at `b200f5bc`, which contains the deployed `bf0203a`).

1. **A flag for shared chats.** The app can tell 0.21.6 and later only by the version in `/api/status`. A `shared_sessions: true` in the answer to `client.capabilities` would say it directly, and would survive a fork with its own version numbers.
2. **Leave one chat on `/api/ws`.** The canonical gateway's `session.detach {session_id, subscription_id}` removes only one client from a chat. The dashboard's `/api/ws` has no equivalent. With it, a background connection could leave a finished chat and the attach bound would stop filling up.
3. **A watch that doesn't attach.** `session.watch {}` would make the socket receive `session.status {session_key, profile, status, last_active, request?: {id, method, summary}}` for every live session. This replaces `active_list` polling, and a waiting chat could say what it asks without anyone attaching.
4. **`session.active_list` rows name their profile.** The client then needs no `GET /api/sessions/{id}?profile=` lookups per check (ADR 0019). With N connections that cost is multiplied by N.
5. **`sessions.changed` with a payload, for every profile.** `{profile, session_id, status}`, sent for profiles the dashboard process doesn't serve too. The 120-second Unread poll could then stop.
6. **An install id on every `/api/status`.** The one-connection-per-install check would then work on every server.
7. **Work outside the dashboard process.** Replies run from the CLI, a messaging gateway or cron appear nowhere until they leave an Unread chat. A status broadcast for them would let the overview count them.

## Supported servers

- **Before 0.21.6**, a background connection keeps only the chats it held and attaches to nothing new. Waiting chats it doesn't hold show as waiting with no card.
- **Without `session.active_list`** (the call answers -32601), a background connection shows no running or waiting work. It shows its status and Unread chats, and the overview says it can't see running work there.
- **Without `client.capabilities`** (0.16.0 and older), Hermes sends no Approval cards on any connection (`docs/compatibility.md`, "Approvals"). A background connection to it can't show them either.
- **The legacy session protocol only.** A server that requires the canonical protocol can't be live, as today (`docs/compatibility.md`, "Chats and the session protocol").

## Considered options

- **Attach a background connection to every chat with work.** Rejected. A client can't leave one chat, so attachments only grow until the socket closes. Every attached chat sends every frame to this computer, and on an older server each attach takes the chat from the official app. Waiting chats are what the owner needs to act on.
- **Attach to nothing new, on every server.** Rejected for 0.21.6 and later. Attaching takes nothing there, and without it a waiting chat on a background server shows no card.
- **Drop a connection's chats when the owner switches away.** Rejected. It loses exactly the Approvals the owner most wants to see: those on chats they just left running.
- **One `Hermes` instance that manages every connection.** Rejected. Every map in the class is keyed by bare chat id, and the class is about 5,000 lines. One instance per connection keeps them apart by construction. The registry merges at the read side (inbox, overview, tray).
- **A connection id in every frame.** Not needed. Each connect already has its own channel, owned by one instance.
- **Keep Rust's one slot and poll background servers over REST from the webview.** Rejected. Cookies and secrets stay in Rust (ADR 0058). REST also misses every push, Approvals included.
- **A hidden webview per connection.** Rejected. Each would be another WebKitGTK view, and the inbox would still need a merge.
- **Close the least recently used connection at the limit.** Rejected. A silent close drops held chats' streams and Approvals. Refusing tells the owner what to do.
- **Drain queues on held background chats.** Not done by default (open question 2). The chat is attached, so a send takes it from no one. But "one composer target" reads as one place that sends, and a queued message that goes while the owner looks elsewhere is the surprise ADR 0018 avoids.
- **Move the composer target to another live connection when the target is removed.** Not done (open question 3). ADR 0112 never picks a connection for the owner.

## Consequences

- Each live connection costs one WebSocket, one HTTP client and its pool, and for an SSH route one `ssh` child and a loopback port. A background connection costs its server one `session.active_list` call a minute. That call runs on the server's slow-handler pool.
- On a sharing server, a chat a background connection is attached to isn't parked or reaped while it stays attached, even after the official app closed it. That lasts until the background socket closes.
- A background connection that stays up long enough reaches its attach bound, and new waiting chats then show without a card. Disconnect and Connect clear it. Gap 2 would remove this.
- An Approval on a sharing server shows in every attached client. The owner may see the same card in the official app and here. The first answer wins. An Approval from a background connection, answered here, goes with `approval.respond`, so the official app's card goes. An answer from the official app clears the card here on `request.cancel` when Hermes sends one. Otherwise it clears at the next `session.active_list` read, or when the chat's next frames show the turn moved on. Answers on the target go with `approval.respond` too (#318), and as a response frame only to a Hermes without it.
- Today's app answers every server request it can't show with -32601. On a sharing server, with the official app attached to the same chat, that ends the official app's clarify, sudo or secret prompt too. That bug exists with one connection and is tracked in #313. This design doesn't add to it, because a background connection answers nothing but Approvals.
- A background connection sees full content only for chats it holds or, on a sharing server, chats that are waiting. Everything else is a count from `session.active_list` until Hermes has a watch that doesn't attach.
- Answering an Approval on a background connection means opening its chat, which makes that connection the composer target.
- ADR 0019's reason for not resuming chats (resuming takes them) holds only before 0.21.6. This ADR doesn't change the inbox for the connection in use. Open question 9 asks whether to revisit it.
- Connections still don't sync between computers.
- The webview holds more live state, one `Hermes` instance and one workspace per live connection, bounded by the limit.

## Open questions for the owner

1. **The limit.** Is a default of 3 and a maximum of 8 right for this computer? Each SSH route costs an `ssh` process.
2. **Background queues.** Should a held chat's queue keep draining while its connection is in the background? This ADR says no.
3. **Removing the composer target.** Should the target move to the most recently used live connection, or should none be in use, as ADR 0112 says now? This ADR keeps "none".
4. **Notifications.** Should background connections send desktop notifications by default, or only when the owner turns them on per connection?
5. **Launch.** Should the live set reopen at launch, or should each run start with the composer target only? This ADR reopens it.
6. **The same install twice.** Refuse a second live connection to the same Hermes install, or allow it with a warning? This ADR refuses.
7. **Preview and Screen.** Should a server's Preview pages and Screen stay open when its connection goes to the background, or close when the target changes? This ADR keeps them open and labelled.
8. **What a background connection attaches to.** Waiting chats only, as this ADR says, or running chats too, so their replies stream in the background? Running chats cost more frames and longer attachments.
9. **The inbox on a sharing server.** Should the inbox of the connection in use also attach to waiting chats in other profiles, now that attaching takes nothing on 0.21.6 and later? That would change ADR 0019 and isn't part of this design.
10. **Backend.** Should the gaps above go to Hermes now, and which first? Gap 2 (leave one chat) and gap 3 (a watch that doesn't attach) remove the most limits.

## Implementation order, once accepted

Each step ends with the build, the tests, and the app working as before at a limit of 1.

1. **Rust map and handles.** Every command names a `Handle`. Teardown is per connection. The limit is fixed at 1. Rust tests: two handles stay apart, a stale `gen` is refused, a slow connect doesn't block another handle's send.
2. **The registry with one member.** `ChatRef` everywhere outside an instance, connection-prefixed inbox keys in memory, a per-connection workspace instead of the `Main` remount, a serial runner per connection. A switch still closes the old connection.
3. **Background role and the limit.** The role and its refusals, answering nothing but Approvals, the 4404 decline, attaching to waiting chats by server version within the bound, the polling budget, `live` and `liveLimit`, Connect and Disconnect, launch reopening `live`, and the one-per-install check.
4. **Identity and the overview.** Server names on chats, entries, cards, notifications and previews. The overview, the summed rail counts and tray badge, and chat links resolved against live connections.
5. **Removal, restart, docs.** Removal while live, the restart snapshot across connections, README, GLOSSARY and `docs/compatibility.md`.

## How it would be verified

The issue's acceptance checks map to runs with the `verify-hermes-chat` skill against two stand-in dashboards that use the same profile names and chat ids.

- Both connections live. A reply streams on one and an Approval waits on the other. Each event lands in its own server's chat. An answer reaches only the server that asked. Each server receives only its own password and headers (the stand-ins log them).
- Disconnect and reconnect one stand-in while the other streams and asks for an Approval. The other's stream, card and drafts don't change.
- Remove a live connection, reach the limit, lower it, and quit and relaunch with two live connections. Check what reopens and what is paused.
- A stand-in that reports a version before 0.21.6 gets no new attaches from a background connection.
- A background connection that receives a clarify sends no answer, and declines a `preview.read` with 4404 only when the stand-in reports `declines_not_shown: true`.
- Run the existing sending, recovery, Approval and profile-isolation tests with one live connection.

A stand-in can't prove how the real Hermes shares a chat. One run against a real 0.21.6 or later server with the official app attached to the same chat would check fan-out, first-answer-wins, `request.cancel` and the 4404 decline that this design depends on.
