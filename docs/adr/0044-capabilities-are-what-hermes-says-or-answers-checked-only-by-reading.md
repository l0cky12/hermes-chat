# Capabilities are what Hermes says or answers, checked only by reading

Hermes Chat works with more than one Hermes version, and each screen used to find out on its own, after it opened, whether the server had what it needed (#87). Nothing in the app said what the connected server is or what it supports, and new features (#73, #70, #72, #66) had no shared way to ask. Settings → Diagnostics now shows both, and the transport and every dependent screen read one typed contract: `src/hermes/capabilities.ts`.

## Decisions

- **One typed contract.** `CAPABILITIES` lists each feature (`CapabilityId`): what it needs from Hermes, how it is checked, the routes and JSON-RPC methods whose answers settle it, the writes it guards, what the app does without it, and its section of `docs/compatibility.md`. A new feature adds an entry and gets diagnostics, the gate, and the write guard from it. Every capability starts `unknown`.
- **Where an answer comes from**, in order of preference:
  1. *What Hermes says about itself.* `GET /api/health` (version, display build, commit), `GET /api/status` (release date and the sign-in gate), the `gateway.ready` frame (protocol generation), `client.capabilities` (the server→client requests it may send; `approval` among them means Approvals), and `gateway.capabilities` (feature flags such as `per_session_exclusive_submit`). Only those fields are kept, after a check of type, length and characters; one that looks like a secret to the redaction below is dropped, so it is never shown. `/api/status` also carries paths, process ids and an install id, and they are dropped.
  2. *The app's own traffic.* Every dashboard GET and JSON-RPC request the screens make goes through the transport, and its answer settles the capability its route or method belongs to, on the connection it went out on. An answer counts only when it is JSON, and of the shape the capability's check wants when it is that check's route or method, so a sign-in page or a changed shape settles nothing. A timeout or refusal settles nothing either. A change a screen sends that Hermes answers with no such route or method makes its capability not supported, so the next one isn't sent.
  3. *A check.* One read per capability: a dashboard GET, or a JSON-RPC method that only reads (`projects.list`, `commands.catalog`, `session.active_list`, and `learning.detail` for a name no entry has, which Hermes answers `ok: false`). Each check has an 8-second limit and the checks run side by side. They start 2 seconds after a connection opens, so the chat list loads first, and skip what the app's own requests settled meanwhile.
- **A version string is never proof.** Hermes has no flag for most routes, a git checkout reports `unknown`, and features arrive between releases. A feature flag or a real answer decides.
- **Four states.** *Supported*: Hermes answered (a route that answers with its own refusal, such as no such profile, is there). *Not supported*: Hermes has no such route (FastAPI's `404 Not Found`, Hermes's `404 No such API endpoint`, or a `405`) or no such method (JSON-RPC `-32601`). Approvals are not supported on a Hermes without `client.capabilities`: it asks in an older way this app doesn't read. *Unknown*: an answer that settles nothing, such as a `401` or `403`, a contract error, or an answer of the wrong shape. *Couldn't check*: no answer, such as a timeout, a drop, a `5xx`, or Hermes's own `5xxx` codes.
- **Each route and method counts on its own.** A capability is not supported while any route or method it needs was found missing, and only an answer from that same route or method takes that back: the file list answering doesn't make up for reading a file having no route.
- **Only Not supported holds a feature back.** A screen whose capability is not supported shows a note in its place (`CapabilityGate`): what is missing, what Hermes needs, when that was checked, a button to Connection diagnostics, and a link to the guide. The screen isn't rendered, so it reads and writes nothing. A screen already open when that is learnt (after a reconnect to an older build) stays, with the note above it, so an unsaved edit isn't lost; its writes are refused. In any other state the screen opens and finds out for itself, as before, and its answer updates diagnostics. The project menu says Hermes has no projects and offers no New project; the inbox, Settings → Toolsets' note about switches, and `/help` link to the guide when Hermes lacks what they need.
- **Writes are refused in the transport too.** While a capability is not supported, a dashboard `POST`, `PUT`, `PATCH` or `DELETE` on a route it guards, a JSON-RPC method that changes something (`projects.*` but list, get and the membership store no Hermes has yet, `learning.edit`, `learning.delete`, `command.dispatch`, `slash.exec`), a toolset switch once Settings → Toolsets found no switch route (its own write check, to a name no toolset has, still goes), or a Server files upload or save is refused before it is sent (`CapabilityUnsupportedError`, worded as the relay's own refusals so each screen reads it as certainly unsent). Reads still go, so an answer can show the feature is there after all.
- **Nothing is written to find out.** No check sends a REST write or a JSON-RPC method that writes. Toolset switches have no read to check them by; diagnostics shows them as unknown until Settings → Toolsets runs its existing write check (ADR 0021), which Hermes refuses at validation, and reports what it found.
- **Scope, refresh and concurrency.** One store per signed-in Hermes, in memory only: nothing is written to disk, and signing out discards it. Every check and observation carries the connection generation it went out on, and the store compares it with the transport's own count at each answer, so an answer for a connection since dropped, switched to another profile, or signed out is dropped even if it arrives first. On each reconnect (a profile switch opens a new connection) the store reads the facts again. It checks a capability again when the build changed (by commit, else build, else version), when that capability was last settled over 15 minutes ago (by its own time: reading the facts renews nothing), or when it was left unknown or couldn't be checked; otherwise it keeps what it knew. A check that started before a screen's own answer for the same capability can't replace that answer. Check again in diagnostics checks everything, and forgets what only a screen can check, so Settings → Toolsets checks its switches afresh. While disconnected, diagnostics shows what it last knew, marked as last checked.
- **What can be copied.** Copy report writes plain text. The webview never has the password or the extra headers' values; the report still goes through the Logs screen's redaction (ADR 0033), which takes out any user part of a URL and `ticket=`, `token=`, `key=`, `auth=` and `sig=` in URL queries (#348), and each state's reason is redacted when it is stored.
- **The canonical protocol stays refused.** A `gateway.ready` with `session_authority` still fails the connection with `ProtocolMismatchError`, until there is a tested adapter for it. Diagnostics can show a protocol only on a connection that is up, so it always shows the legacy one; the sign-in screen explains the canonical case.

## Capability gap in Hermes, and a proposed backend design

Hermes has no single answer to "which dashboard routes and JSON-RPC methods does this build have". `gateway.capabilities` covers a few behaviours, and `client.capabilities` covers server→client requests, but nothing lists routes or methods, so the app checks each one. A Hermes-side contract would let clients stop probing:

- `GET /api/capabilities` (signed in, read-only): `{ "contract": "capabilities/1", "build": {version, commit}, "protocol": "legacy" | "canonical", "routes": {"webhooks": "webhooks/1", "cron": "cron/1", …}, "methods": ["projects.list", …], "flags": {…} }`, with the same per-family contract strings `webhooks/1` already uses.
- `rpc.methods` on `/api/ws`, answering the method names this build dispatches.

When either exists, it goes first in the order above, and checks run only for families it doesn't name. Until then the app's checks are the contract, and a feature whose route can't be checked by reading stays unknown.

## Considered options

- **Read `/openapi.json` for the route list.** Rejected for now: it lists REST routes only, not JSON-RPC methods; it is large (108 KB to 311 KB on the builds tried); and a route listed there can still be blocked by a gateway in front of the dashboard, which a real read finds out.
- **Check every capability at every connect.** Rejected: a profile switch would repeat a dozen requests for a server that hasn't changed, competing with the chat list loading.
- **A version-to-feature table.** Rejected: a git checkout reports `unknown`, and features arrive between releases.
- **Hold a screen back while its capability is unknown or couldn't be checked.** Rejected: a slow or flaky check would then hide a working screen.
- **Keep the results on disk between launches.** Rejected: a server can be updated while the app is closed, and a check takes about a second.
