# MCP servers are managed per profile in their own Settings tab, and Rust edits one server in Hermes's whole map

The owner wants to add, create, edit, remove, turn on and off, test and sign in to the MCP servers Hermes connects a profile's agent to, without SSHing to the server (#221). The deployed Hermes (`f0d94882`, research checkout `~/.cache/hermes-src-168`, `hermes_cli/web_routers/mcp.py`) has a route for each, all taking `?profile=`, so no Hermes change is needed. An [mcpo](https://github.com/open-webui/mcpo) proxy (MCP servers exposed as OpenAPI) was mentioned alongside; it is a different thing and isn't part of this.

## Decisions

- **Its own tab, Settings → MCP servers**, after Toolsets, not inside it. Toolsets is a list of switches searched in place; MCP servers have forms, secrets and dialogs, and a server isn't a toolset (Hermes lists each as its own `mcp-<name>` toolset only once connected). Settings search names the tab and opens it, as it does for Skills and Memory, rather than mounting its forms among the results.
- **Any profile, from the same picker as Skills and Memory** (ADR 0118), starting on the profile in use and going back to it when the app switches profile. Every call names the profile in its query. The screen is keyed by the profile, and an answer that comes back for a profile no longer shown is dropped, so it can't land in another profile's list.
- **The list** is `GET /api/mcp/servers?profile=`: each server's name, how it runs (the command and arguments, or the URL), its on/off switch, its sign-in kind, the names of its env vars (never their values, which Hermes masks anyway), a note when its config filters its tools, and "from plugin X" for a server a plugin provides, which is read-only: Hermes refuses to change or remove one (409). A name outside this app's rule (an ASCII letter or digit, then up to 63 letters, digits, `_`, `-` or `.`) is listed but not changed from here, since it would need escaping in a path. Hermes doesn't list a tool count; the row shows the count the last Test found.
- **Add** is `POST /api/mcp/servers` from a blank form: stdio (command, arguments each in its own field, so an empty one or one holding a line break is kept exactly, env vars) or HTTP/SSE (URL, and no sign-in, a bearer token, or OAuth). Hermes keeps a bearer token in the profile's `.env` as `MCP_<NAME>_API_KEY` and puts `Authorization: Bearer ${MCP_<NAME>_API_KEY}` in the config. **From catalog** is `GET /api/mcp/catalog` and `POST /api/mcp/catalog/install {name, env, enable: true}`; the entry shows what it runs (and, for one that builds, the repository and bootstrap commands) before Install, and asks for the env values it declares. An entry that clones and builds installs in the background on the server; the screen says so and shows it once a read finds it.
- **Edit happens in Rust.** Hermes's only edit route is `PUT /api/mcp/servers`, which replaces the whole `mcp_servers` map, and its list masks env values, so the webview can neither build a correct map nor should it hold one. The webview sends one server's fields (`hermes_mcp_edit`, `mcp::Edit`), secrets it didn't retype left out. Rust (`Dashboard::mcp_edit`) reads the profile's config as written (`GET /api/config?profile=&include_defaults=false`, so `${VAR}` references stay references; the default read expands them and would write secrets into config.yaml), changes that one server (`mcp::edited`), keeps every key the screen doesn't show (`enabled`, `tools`, `timeout`, `oauth`, other headers), drops the other transport's keys when the transport changes, and writes the map back. Every other server goes back exactly as read. A rename moves the entry; Hermes keeps OAuth tokens by name, so the dialog says to sign in again. Rust then reads the config again, and calls the edit saved only if it is exactly the map sent. Anything that fails once something may have been written (the token, or the map) comes back as "not confirmed", never as "not changed", and the screen never settles an edit by the list afterwards, since the list can't show a secret.
- **A new bearer token on an edit** goes to `PUT /api/env?profile=` `{key: MCP_<NAME>_API_KEY, value}` first, from Rust only, then the map with the `${…}` header. Once the token is saved, a header already pointing at that variable uses it, so a refused map write after it is reported as "Hermes saved the new bearer token, but not the rest of the change". This is the one route used beyond the issue's list: Hermes's add route saves a token this way itself (`_save_bearer_auth_token`), and it has no MCP route that changes a saved token. Rust names the variable from the server's name; the webview can't pick which `.env` key is written.
- **Secrets are write-only.** No form is filled with a value from Hermes. An env var Hermes has shows its name and an empty field that says a blank keeps the saved value; the bearer token field is empty the same way. Typed secrets go when the dialog closes on a save, and are cleared from the dialog when Hermes may have taken them. No error shown can quote a secret: a refusal of the whole-map write is shown only when its `detail` holds none of the map's env or header values or the token, and otherwise as "Hermes refused it (its answer isn't shown, as it may hold a secret)".
- **Remove** asks first, in the row, and is `DELETE /api/mcp/servers/{name}`. The question says a bearer token or OAuth sign-in Hermes saved stays on the server (Hermes removes only the config entry). A server already gone counts as removed.
- **On/off** is `PUT /api/mcp/servers/{name}/enabled {enabled}`. A server turned off stays in the config, so turning it on needs nothing retyped.
- **Test** is `POST /api/mcp/servers/{name}/test`: Hermes connects on the server, lists the tools and disconnects. The row shows the tools (folded) and prompts and resources, or Hermes's reason, which it redacts. A change to a server clears its earlier result.
- **Sign in** (OAuth, shown for an HTTP server with `auth: oauth`) is `POST /api/mcp/servers/{name}/auth`. Hermes answers with a flow and the provider's authorization URL, which opens in the browser through the app's existing opener (`web_page::open_in_browser`, http(s) only). The screen then asks `GET /api/mcp/oauth/flows/{id}` every 2 seconds until Hermes says approved (it says how many tools it found, and reads the list again) or failed (Hermes's reason), and gives up after 5 minutes. **Stop**, closing the tab, or leaving Settings cancels a flow under way with `DELETE /api/mcp/oauth/flows/{id}`, so Hermes doesn't hold the server's sign-in slot until its own timeout. The provider returns to the dashboard's callback at the address Hermes sees the request on. Through this app that is the address the app reaches the dashboard by (for an SSH route, the tunnel's local port), so the sign-in finishes on this computer while the app is connected. A dashboard with a public URL configured uses that.
- **Every change is read back** (`GET /api/mcp/servers?profile=`) before the row says saved, as other settings do. A refusal (4xx) is shown in Hermes's words and changed nothing. A lost answer is settled by the read: saved if it shows the change, otherwise "Hermes didn't confirm it", with the list as Hermes has it now.
- **When a change takes effect** is said on the page: Hermes builds a chat's tools when it starts the chat, so chats started afterwards get the change, and a chat already going keeps the tools it started with. Toolsets' `no_mcp` turns every MCP server off for one platform's chats in the profile; the page reads it (Rust's toolset guards) and warns when it covers this app's chats (`cli`), noting that Hermes clears it whenever Toolsets saves a change.
- **What the relay passes** (`mcp::relayed`): `POST api/mcp/servers` with exactly `MCPServerCreate`'s fields minus `profile`, and exactly one of a command (with args and env, no auth) or an http(s) URL (auth none, header with a one-line token, or oauth); `PUT api/mcp/servers/{name}/enabled` with exactly `{enabled: bool}`; `POST api/mcp/servers/{name}/test` and `…/auth` with no body; `POST api/mcp/catalog/install` with only `name`, non-blank `env` values under env var names, and `enable`. `{name}` must match the name rule. `GET` and `DELETE` were already relayed for any `api/` path. `PUT api/mcp/servers` is never relayed from the webview.

## Considered options

- **Edit as remove + add.** Rejected: it loses `enabled`, the tools filter and every other key, and a failed add after the remove loses the server.
- **Build the whole map in the webview from `GET /api/config`.** Rejected: the webview would read and hold every server's secrets, and a relayed whole-map `PUT` would let any webview code rewrite every server.
- **Put MCP servers inside Toolsets.** Rejected above: different shape, and Toolsets is searched in place.
- **mcpo.** Out of scope: it exposes MCP servers to OpenAPI clients; Hermes talks MCP itself.

## Consequences

- MCP servers are managed for any profile from the app, with secrets that never come back to the screen.
- After an edit, config.yaml lists the profile's MCP servers in name order: Rust writes the map as a JSON object, which it keeps sorted.
- An edit made by another client between Rust's read and write is lost (Hermes's whole-map route has no precondition); the window is one request long, and the read after the write reports a map that isn't the one sent.
- A bearer token Hermes saved stays in the profile's `.env` after the server is removed, as Hermes's own remove leaves it.
- Verification: unit tests of the relay rules and the edit (`src-tauri/src/mcp.rs`), an HTTP stub test of `Dashboard::mcp_edit` (`src-tauri/tests/mcp_edit.rs`), and tests of the screen and its API against FakeHermes's MCP routes (`fakeMcp.ts`), written from the `f0d94882` source. The real app was driven against a throwaway `f0d94882` dashboard (2026-11-05) with a synthetic stdio server that exits without its env token and a synthetic streamable-HTTP server behind a bearer token: add (stdio with env, HTTP with token, OAuth), Test (tools found; a 401 with the wrong token), an edit that set the right token through Rust (Test then connected), a rename that left the env value blank (Test still connected, so the value was kept), the switch, add and remove in a second profile with the first unchanged, starting an OAuth sign-in (Hermes's reason shown, as the stand-in server has no OAuth), and the catalog's 66 entries. config.yaml kept `Bearer ${MCP_WEB_API_KEY}` and never held the token. A full OAuth approval and a catalog install against the real server weren't run: the first needs an OAuth provider, and the second probes an outside service.
