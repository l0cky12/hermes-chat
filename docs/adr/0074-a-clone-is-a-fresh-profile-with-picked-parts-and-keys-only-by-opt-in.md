# A clone is a fresh profile with the parts picked, and API keys go only by opt-in

Issue #91 asks for Clone profile: a new profile made from an existing one, without sharing credentials, chats, jobs or delivery channels by accident, with each optional category shown and the name checked before anything is written. The deployed Hermes (`f0d94882`, research checkout `~/.cache/hermes-src-168`) has one route that makes profiles, `POST /api/profiles` (`web_routers/profiles.py` `create_profile_endpoint`, body `ProfileCreate` in `web_models.py`). It builds the profile in a hidden staging folder and renames it into place, so a refusal or a failure while building leaves nothing. It refuses a taken, reserved or invalid name (400), and drops messaging channels from a copy unless asked. But its copy, `clone_from`, always copies `config.yaml` and `.env` (`profiles.py` `_CLONE_CONFIG_FILES`), which hold the source's API keys. Checked live on a throwaway `f0d94882` dashboard: a `clone_from` copy had the source's `OPENROUTER_API_KEY` in its `.env` and a provider `api_key` in its `config.yaml`, without the source's Telegram bot token.

## Decisions

- **The default is a fresh profile with the parts picked.** The create body carries only what Hermes takes without a source: `soul` (the source's SOUL.md, read just before), `description`, and `provider` with `model`. The source's own skills (Local, `provenance: agent`) follow one at a time through Settings → Skills' copy (`POST /api/skills?profile=`, ADR 0118), each read back. Each of the four is a checkbox, on by default when the source has it. The fresh profile gets Hermes's empty `.env`, its default settings and its built-in skills.
- **API keys go only with the full copy, which the owner turns on.** "Also copy API keys, memory and every setting (Hermes's full copy)" sends `{name, clone_from}` (and the description), Hermes's own copy. Turning it on shows a warning that the new profile gets the same keys, and the button says "Clone with API keys". It copies `config.yaml`, `.env`, SOUL.md, every skill folder, both memory files and the plugins; Hermes drops bot tokens and channel sections.
- **Never copied, either way:** chats, scheduled jobs, and messaging channels. Hermes's create never copies `state.db`, `sessions/` or `cron/` without `clone_all`, and the app never sends `clone_all`, `clone_channels`, `clone_from_default`, `mcp_servers`, `hub_skills`, `keep_skills` or `no_skills`. The Rust relay enforces this (`profile_create_allowed`): it passes `POST api/profiles` only as `{name}` with `soul`, `description`, `provider` and `model`, or `{name, clone_from}` with `description`, every value a string and the name a profile id other than `default`.
- **Shown before anything is written.** The dialog reads the source (its list row, SOUL.md and skills) and shows every category: what it would copy, from what, or why not. Memory, toolsets, MCP servers and the memory provider say "Not copied" in the default, with the reason: memory has no add-entry route (ADR 0118), and the rest live in `config.yaml` beside the keys.
- **The name is checked twice before writing.** As it's typed, against `GET /api/profiles` (Hermes's id rule, its reserved names, and the names it lists), and again from a fresh read just before the create. Hermes refuses a taken name itself too, so a profile made meanwhile is never replaced.
- **Stages, then a read-back of each category.** The dialog lists four stages (check the name, create, copy skills, read back) with their state. After the create it reads the profile back: the list must have it, SOUL.md must be what was sent, the listed model and description must match, and each skill copy is read back by the copy itself. A model Hermes wouldn't set (`model_set: false`) is shown in Hermes's words. Each category ends as copied, didn't copy, not copied, or "copied, not read back" (the full copy's `.env` and memory, which this app doesn't read). If anything didn't copy, the dialog says it's not a full clone.
- **Failure and retry.** A refusal (any 4xx, or a request never sent) made nothing, so the form stays to try again. Any other failure or a lost answer is settled by reading the list: if Hermes lists the name, the dialog reads it back, but writes nothing more to it (no skill copies), since it may be another client's profile made meanwhile, and says the skills weren't copied; if it doesn't, or the list can't be read, the dialog says it may still appear and offers Check again rather than a second create. Skills that didn't copy can be tried again alone.
- **Cleanup only of what this clone made.** "Delete <name>" (`DELETE /api/profiles/{name}`, then the list read back) is offered only when Hermes answered the create, so the profile is certainly this clone's. After a lost answer the profile may be another client's, and the dialog doesn't offer to delete it.
- **Opened only once read back.** "Open <name>" shows after the read-back, and switches profile through the switcher, which asks first when a reply or Approval would be left behind.
- **Where it lives.** "Clone a profile…" is at the bottom of the profile switcher's menu, where profiles are listed and switched (ADR 0001). The source starts on the profile in use and can be any profile Hermes lists. Settings' per-tab profile pickers (ADR 0117, 0118) show and edit a profile's parts; making a profile belongs with switching.

## Considered options

- **Use `clone_from` and strip the keys afterwards.** Rejected: the app can't edit `.env` (the file routes are read-only, ADR 0012), and the keys would sit in the new profile until the strip, where a running gateway could load them.
- **Make the full copy the default, with keys stripped by Hermes.** Not possible at `f0d94882`: no `ProfileCreate` field leaves `.env` or `config.yaml` out of a `clone_from` copy. A Hermes change would need one, for example `clone_secrets: false`.
- **Copy memory into the fresh profile through the file routes.** Rejected, as in ADR 0118: no lock and no add-entry route.
- **Copy toolsets and MCP servers one by one after the create.** Not built now. Toolsets have per-toolset routes (ADR 0021) and MCP servers a whole-map route (ADR 0121), but MCP servers carry their own secrets, and each would be one more stage to settle and read back. The dialog says they aren't copied; the full copy has them.
- **A Profiles tab in Settings.** Rejected for now: Settings' profile pickers show one profile's parts each, and nowhere in Settings makes or removes a profile. The switcher's menu already lists every profile.

## Consequences

- A default clone has no API keys. Its chats fail until keys are added for it in Hermes (`hermes -p <name> setup`, or the dashboard's Keys page), and the dialog says so.
- A new profile has no chat store (`state.db`) until a Hermes gateway serves it: a running default gateway that serves every profile picks it up (`_notify_multiplexer`), and otherwise its own gateway must start. Until then Hermes answers its chat list with 503 "Session store is not initialized. Start this profile's gateway to initialize it.", and Open shows that as the switcher's "Couldn't open", with Try again and Back (seen live on a dashboard with no gateway running). The clone itself is complete; this app doesn't start gateways.
- A clone's own skills are SKILL.md only, as Settings → Skills' copy is; the full copy has their whole folders.
- A clone never shares mutable state with its source: every copy is a new file in the new profile's folder. Editing the clone's SOUL.md or skills leaves the source's alone (checked live, below).
- On a Hermes whose `POST /api/profiles` lacks a field (older than `soul`, `description` or `provider`/`model` on `ProfileCreate`), Hermes ignores it, and the read-back shows that category as not copied instead of claiming it. A Hermes without the route at all answers 405, and the dialog says the server can't create profiles.
- Verification: the tests use a fake of these routes (`fakeHermes.ts` `createProfile`, `deleteProfile`) written from the `f0d94882` source. The same requests were sent live to a throwaway `f0d94882` dashboard with synthetic data (2026-11-05): a fresh create, a `clone_from` copy, the taken, invalid and reserved name refusals, an unknown source, and the files each left on disk under the throwaway `HERMES_HOME`.
